## 0. 结论摘要

一句话：**V2.1 的「双工作空间 + 工程理解/工程实施」在仓库里基本不存在。现有的是两条已经很成熟的链路——知识问答/研究链路，以及一个只能读写四类文件操作的可选执行子系统。Phase B–F 是增量建设，不是把已有模块接一根线。**

| 维度 | 现状 | 判断 |
| --- | --- | --- |
| 知识学习空间（answer / research / compare / extract） | 链路完整，四类意图共用同一条流水线 | 🟡 能用，但只有 `answer` 是认真实现的 |
| 双入口（Knowledge / Engineering） | 不存在；只有单入口 + 一个工作区胶囊 | 🔴 未实现 |
| 会话级 WorkspaceMode 与持久化 | 类型与字段都不存在；工作区路径只活在渲染层内存 | 🔴 未实现 |
| 工程任务识别（Analysis / Execution） | `classifyIntent` 只有五类，7 条工程回归语句实测 6 条判错 | 🔴 未实现 |
| 工程理解（读代码、架构、调用链） | 无代码检索、无符号索引、无工程上下文；分析类问题不读任何文件 | 🔴 未实现 |
| 工程实施（计划 → 审批 → 执行 → 验证） | 有完整审批与 grant 机制，但运行时只有 4 个文件工具 | 🟡 骨架可用，能力不足 |
| 多模型协作 | 网页 / 本地 Ollama / 云端 API 三类成员齐备，串并行与主导人机制成熟 | 🟢 已实现 |
| 辩论 / 裁判 / Claim / Revision / ArgumentGraph | 引擎、六策略、独立裁判、独立存储都在 | 🟢 已实现（但无「关掉辩论」开关） |
| 证据 | 网页引用能抽取，但只进辩论，不随知识问答落盘；无证据库 | 🟡 部分 |
| 兼容性 | 单 JSON 全量写、无 schema 版本、读时兜底 | 🟡 可用，扩展需谨慎 |
| 安全边界 | 工具白名单、路径校验、整计划审批、30 分钟 grant | 🟢 与 SECURITY.md 一致 |

## 3. 逐项能力审计

### 3.1 双入口产品结构：未实现

证据：

- `src/renderer/src/components/TaskSidebar.tsx`：只有一份 `conversations` 与一份 `tasks`，任务按 `workspaceLabel(task)` 分组，没有「空间」这一级。
- `src/renderer/src/components/TaskInput.tsx`：输入框下方三个胶囊——工作区、权限、研究设置。工作区是「选目录」，不是「切空间」。
- `src/renderer/src/App.tsx`：`const [workspace, setWorkspace] = useState('')`、`const [permission, setPermission] = useState<PermissionPreset>('workspace-write')`。两者都是渲染层状态。
- 全仓库搜索 `WorkspaceMode`、`workspaceMode`、`EngineeringTask`、`TaskRouting`：**零命中**。

### 3.2 会话级 WorkspaceMode 与持久化：未实现

- `src/shared/conversation.ts` 的 `interface Conversation` 字段为：`conversationId`、`title`、`intent`、`intentReason`、`status`、`channels`、`answered?`、`threads?`、`taskId?`、`createdAt`、`updatedAt`、`error?`、`executionConfig?`。**没有 `workspaceMode`，也没有 `workspaceRoot`。**
- 工作区路径只存在于 `App.tsx` 的 `useState`，渲染层没有 `localStorage` 持久化（全目录搜索 `localStorage` 零命中），应用重启即丢。
- 权限预设同样只在主进程内存里：`src/main/index.ts:126` `let permissionPreset: PermissionPreset = 'workspace-write'`，`permission:set` 只改这个变量，不落盘；重启回到「工作区内修改」。
- 唯一能被持久化复用的工程上下文，是 `AgentTask.workspaceRoot`——但它只属于已经进入执行的任务，知识会话无法「升级」成工程会话。

**对 Phase B 的影响**：会话级空间与工程目录必须新增字段并兼容老数据（老会话无此字段时按 `knowledge` 处理）。现有 `Conversation` 的持久化约定是「新字段一律可选 + 读时兜底」，可沿用。

### 3.3 意图识别：五类规则，缺工程两类

`src/shared/intent.ts`：

```ts
export type IntentKind = 'answer' | 'research' | 'compare' | 'extract' | 'workspace';
export function classifyIntent(text: string): Intent
```

规则只有四条，顺序为：改动动词 + 文件线索 → `workspace`；URL + 整理词 → `extract`；比较词 → `compare`；研究词 → `research`；否则 `answer`。

用 V2.1 第 6 节回归清单的语句实测（`out/shared/intent.js`，编译产物晚于源码，结果为当前代码行为）：

| 用户表达 | 期望（V2.1） | 实测 | 结论 |
| --- | --- | --- | --- |
| 分析当前项目结构 | Engineering Analysis | `research` | ❌ |
| 解释某个方法 | Engineering Analysis | `answer` | ❌ |
| 定位这个 Bug | Engineering Analysis | `answer` | ❌ |
| 评审这套架构方案 | Engineering Analysis | `research` | ❌ |
| 修改一个文件 | Engineering Execution | `workspace` | ✅ |
| 实现一个功能 | Engineering Execution | `answer` | ❌ |
| 重构这个模块 | Engineering Execution | `answer` | ❌ |
| 先分析再修改 | Analysis → Execution | `research` | ❌ |
| 对比 Envoy 和 Redis Proxy | compare | `compare` | ✅ |
| 研究 Java 虚拟线程 | research | `research` | ✅ |
| 整理这个网页 https://… | extract | `extract` | ✅ |

根因很具体：`WORKSPACE_VERBS` 只收「修改/编辑/创建/删除/运行…」，没有「实现」「重构」「修复」；`FILE_HINTS` 要求同时出现文件线索，「实现一个功能」「重构这个模块」都不满足；「分析/评审」被 `RESEARCH_HINTS` 先一步吃掉。

另外，V2.1 要求 `TaskRouting` 带 `source: 'user_selected' | 'rule'`，并要求「识别结果可见且可纠正」。当前：

- 可见：`Conversation.intent` + `intentReason` 会显示在会话标题旁（`ConversationView.tsx` 的 `intent-badge` 与「路由依据」一行）。
- 可纠正：**没有**。界面没有任何「改判意图」的入口。

### 3.4 知识空间四类任务：同一链路，只有 `workspace` 有分支

全仓库搜索 `kind === 'answer' | 'research' | 'compare' | 'extract'`：**零命中**。`ConversationRunner.start()` 里唯一的分支是 `if (intent.kind === 'workspace')`；其余四类一律进入 `run()` → `MasterAgent.research()` → 执行阶段 → 综合。

这意味着：

- `answer`：符合预期（原样发问，多通道，综合）。
- `research`：能跑，但没有「多轮深入」「补充检索」等研究特有行为，仍是单轮多通道。
- `compare`：靠多通道卡片并排 + 综合卡呈现，没有专门的对比结构（如逐维度对照表）。`Synthesis` 只有 `consensus / disputed / unique / gaps / overlap`。
- `extract`：`classifyIntent` 返回了 `url`，但 `Conversation` 不保存它，主进程也没有任何 `extract` 处理（搜索零命中）。**「提取网页内容」当前等同于「把带链接的问题发给所有通道」。**

这不是 bug，但与 V2.1 第 3 节「四类意图各有功能」的表述有差距，需要在 Phase B/C 里明确哪些是「本轮只做标签、不新增行为」。

### 3.5 工程理解：未实现

缺失证据（全部零命中）：`ProjectContext`、`projectContext`、`codeSearch`、`searchCode`、`symbolIndex`、`callGraph`。

现有能读工程的唯一路径，是执行计划里的 `fs.list` / `fs.readFile`：

- `src/agent/tools/filesystem.ts`：`list`（单层目录，最多 1000 项）、`readFile`（上限 256 KiB）、`mkdir`、`writeFile`。
- 没有递归遍历、没有按内容搜索、没有忽略规则（`node_modules`、`.git`）、没有语言/AST 解析、没有 Git 状态、没有文件指纹与行号定位。

后果是 V2.1 Phase E 的验收条件「用户要求分析工程架构时，系统实际读取工程文件并给出带文件位置的分析，不得仅凭模型猜测」**当前必然不通过**：分析类问题连工作区都不会选，直接进网页通道。

### 3.6 工程实施：骨架完整，能力只有文件读写

已有的部分（可复用，不建议重写）：

| 环节 | 实现 |
| --- | --- |
| 计划协议 | `desktop-agent/v1`：`PlanSchema`、`StepSchema`（`src/shared/contracts.ts`），工具只有四种 `fs.*` |
| 计划审批 | `AgentOrchestrator.approve()`：校验轮次/计划归属、`hashPlan` 内容哈希、10 分钟过期、`read-only` 时拒绝写入步骤 |
| 授权 | `TaskGrant`：`allowedTools`（≤4）、`maxSteps`（≤30）、`expiresAt`（`GRANT_TTL_MS = 30 分钟`） |
| 隔离执行 | `src/main/agent-manager.ts` 用 Electron `utilityProcess` 起 `src/agent/index.ts` |
| 权限校验 | `assertGrant()` + `resolveGrantedPath()`：越界、符号链接、绝对路径、非法片段全部拒绝；`open` 带 `O_NOFOLLOW`；新建文件用 `O_EXCL` |
| 写后验证 | `verifyWrittenFile()`：重新打开、sha256 比对 |
| 界面 | `PlanPreview.tsx` + `ExecutionLog.tsx` |

缺的部分（Phase F 的实质工作）：

- **没有 Shell / 测试 / Git / 删除 / 覆盖工具**（`SECURITY.md` §5 明确写「没有」）。
- 没有 diff / patch，写文件只能整份新建，不能改已有文件（`O_EXCL` 且无覆盖工具）——**「实现一个功能」「修 Bug」目前做不到**。
- 没有独立 Review 模型，也没有「失败 → 修复 → 再验证」的循环；一轮计划执行完就交报告。
- 审批粒度是整份计划，不是逐步；高风险操作没有额外确认。

### 3.7 多模型协作：已实现且是当前最强的一块

- `ProviderRegistry`（`src/main/providers/registry.ts`）、`SubAgentRegistry`（`src/main/agents/registry.ts`）、`MasterAgent`（`src/main/master-agent.ts`）。
- 网页通道：`src/main/adapters/providers/index.ts` 内置 `deepseek / chatgpt / kimi / gemini`；本地：`providers/ollama.ts`；云端：`providers/openai-compatible.ts`。
- `MasterAgent` 的硬规则与用户裁决一致：**所有已开启通道都问、问题原样发出**，不套提示词。
- 执行阶段选人：`src/main/execution/policy.ts` 的 `selectParticipants()` 把「回答成员」和「执行成员」分开；`ConversationRunner.resolveLead()` 按执行模式（web/local/cloud/hybrid）选主导人；`ownershipOf()` 保证「一类方式只用一类成员」。
- 六种辩论策略与三种执行模式是两个独立字段：`executionMode` / `strategy` / `debateStrategy`（`ConversationExecutionConfig`）。

与 V2.1 §8 的差距：没有独立的「Model Router」。当前没有人按任务类型自动选模型——选谁由用户在「研究设置」里定，或由 hybrid 主导选择器定。V2.1 若要求「按任务调用不同模型」，需要新增路由层，而不是改现有选人逻辑。

### 3.8 辩论 / 裁判：已实现，缺一个「关掉」开关

- `DebateOrchestrator`（`src/main/debate/orchestrator.ts`）、`STRATEGY_PROFILES` 六策略（`strategies.ts`：truth / adversarial / expert / assumption / solution / discovery）。
- `JudgeEngine`（`src/main/judge/engine.ts`）：优先独立模型，资源不足时允许参辩模型兼任并标 `sharedWith`；没有模型时用规则版并标 `backend: 'rules'`。
- `claims.ts` / `revision.ts` / `argument-graph.ts` / `evidence.ts` / `metrics.ts` / `history.ts`。
- 存储：`DebateStore` 每场辩论一个 JSON（不进主 journal，避免写放大）。
- 界面：`ResearchPanel.tsx` 四个页签（模式 / 协作 / 辩论 / 报告），六策略可选。

两个与 V2.1 的偏差：

1. **辩论是自动触发的**：主导人写完五段汇总后，`parseTopics()` 从【辩题】里取题，有题就开辩。`ConversationExecutionConfig` 与 `ResearchPanel` 里**没有 `debateEnabled` 之类的开关**（搜索零命中）。V2.1 §6 要求「用户可以手动开启」「用户明确关闭时不强制启动」，当前只能通过换执行模式间接影响，不能直接关。
2. 辩论只挂在会话链路里，没有「第二个空间」可接——Phase D 的「两个空间都能用」要等 Phase B 有空间之后才谈得上。

### 3.9 证据：有抽取，没有沉淀

- 网页引用：`src/shared/evidence.ts` 的 `PageCitation` / `digestCitations()`；`PageBrowserAdapter.ask()` 会把引用挂到 `SubAgentAnswer.citations`。
- 去向：只有辩论用到（`debate/evidence.ts` 把引用变成带来源的证据，AC-09/AC-10）。`ConversationMessage` **没有 `citations` 字段**，所以知识问答的引用不落盘，界面也不显示。
- 综合里的「证据」：`Synthesis.Claim.evidence` 是原话字符串数组，能指回原话片段，但不是结构化的 `Evidence`（没有来源、时间、可核验状态、独立性）。
- 没有 Evidence 表、没有跨会话索引、没有代码/执行证据（文件路径、行号、内容指纹、读取时间）。

这与 ARCHITECTURE 第 11 节的目标形态一致地「未完成」，也与 V2.1 §10「Evidence：追踪网页、代码和执行证据」有明确差距。

### 3.10 持久化与兼容

- `AgentStore`（`src/main/store.ts`）：`agent-store.json`，每次 mutation 全量序列化 + 原子 rename。数据量小的时候没问题，辩论/证据一多会线性变慢（`DATA_MODEL_AUDIT.md` 已指出）。
- 无 schema 版本号、无迁移；扩展靠「可选字段 + 读时兜底」（`normalizeExecutionConfig()` 是范例）。
- 老数据兼容示例：`Synthesis.fusion`、`finalOpinion`、`leadSummary` 都是可选字段，读不到就按旧卡片显示。

**对 V2.1 的启示**：Phase B 加 `workspaceMode` 必须走同一条路（可选 + 默认 `knowledge`），不要引入版本迁移。

### 3.11 安全边界：与文档一致

`SECURITY.md` 与实际代码对得上：

- 工具名枚举 `TOOL_NAMES`，grant 里 `allowedTools` 再校验一次。
- 路径：`resolveGrantedPath()` 拒绝绝对路径（除 full-access）、`..`、符号链接；`O_NOFOLLOW`；写后重解析。
- 计划：内容哈希 + 10 分钟过期 + 用户确认；`read-only` 计划里出现写步骤直接拒绝。
- 模型输出不当命令执行：计划是 JSON，经 zod 校验后按 allowlist 调工具，没有 `eval` / `exec`。
- 已知限制（文档自述）：整计划审批、非 OS 沙箱、TOCTOU 未完全消除、无签名审计日志。

如果 Phase F 要加 Shell / 测试 / Git，这一层必须同步扩展：新增工具要进 `TOOL_NAMES` 与 `StepSchema`，`assertGrant` 要按工具分级，审批要能逐步确认，否则「整计划审批」会变成一次批准执行任意命令。

## 5. 风险清单

### 5.1 产品风险

- **把「工程分析」做成聊天是最容易复发的错误。** 当前分析类问题不读文件，模型只能猜；如果 Phase C 只加意图标签、不加文件读取，就正好复现 `PRODUCT.md` 第 1 节批评的旧行为。
- **「双入口」如果只做成一个下拉框，等于没做。** V2.1 要的是两套默认行为（知识空间不要工作区、工程空间要项目上下文），不是给同一条链路加一个标签。
- **辩论自动触发**：若 V2.1 要求「默认不强制辩论」，必须给显式开关，否则一次提问可能连带两三倍模型调用与成本。

### 5.2 兼容风险

- 改 `IntentKind` 会在历史会话里留下旧值（`Conversation.intent` 已落盘）。必须扩值 + 读时映射，不能重命名。
- `Conversation` 加字段要可选；`agent-store.json` 无迁移机制。
- `docs/IPC.md` 已经落后于实现；再加 IPC 会让文档继续失真。Phase B 起应把 IPC 文档更新作为验收项。

### 5.3 安全风险（Phase F 前必须解决）

- 现有审批是「整计划一次批准」，且 `danger-full-access` 会移除应用层路径边界。加 Shell/测试/Git 后，一次批准等于授权一串任意命令。
- 测试执行会引入真实副作用（端口、临时文件、依赖安装），需要单独的工作目录与清理策略。
- 模型输出仍可能通过「写文件内容」实现注入式持久化（例如往仓库里写指令），需要把「读取的工程内容」标为不可信。

### 5.4 伪完成风险

`DEBATE_ACCEPTANCE.md` 声明 Phase 0–5 完成，但同时写明「阶段完成不等于质量达标」。V2.1 任务书也提醒「阶段验收不等于真实模型事实准确率已得到充分证明」。汇报进度时不能把「有引擎、有测试」说成「判断可靠」。

## 6. 复用点与分阶段改造建议

### Phase A（本次）：只交付本报告

无代码改动。进入 Phase B 前需要用户确认本报告对现状的判断，尤其是「工程能力几乎为零」这一条是否与预期一致。

### Phase B：双入口

复用：

- `TaskSidebar` 的分组能力（现在是按 workspace 分组，可改成按空间分组）。
- `TaskInput` 的三个胶囊（知识空间隐藏工作区胶囊；工程空间保留）。
- `Conversation` 的可选字段约定。

新增：

- `WorkspaceMode = 'knowledge' | 'engineering'`，落在 `Conversation.workspaceMode?`，缺省 `knowledge`。
- 工程空间选择项目后，把 `workspaceRoot` 也存到会话上（现在只有 `AgentTask` 有）。
- 顶栏显示当前空间与项目；切换空间不丢历史（会话列表按空间过滤而不是拆库）。

### Phase C：工程任务识别

复用：

- `classifyIntent` 的「规则优先 + reason 可读」思路；`test:intent` 的测试形状。
- `Conversation.intentReason` 与 `intent-badge` 的可见性。

新增：

- `classifyEngineeringIntent(text): { kind: 'analysis' | 'execution' | 'clarify'; reason }` 纯函数，覆盖修改/实现/修复/重构/分析/解释/定位/评审/先分析再修改。
- `TaskRouting` 类型（`workspaceMode` + `taskKind` + `reason` + `source`）。
- 界面可改判：识别结果旁给一个「不是这个」的入口。
- 识别结果不改变权限：`permissionPreset` 仍是独立输入。

### Phase D：辩论接入

复用：整套 `debate/*`、`JudgeEngine`、`ResearchPanel`。

新增：

- `ConversationExecutionConfig.debate: 'auto' | 'on' | 'off'`（或等价字段），默认 `auto`；`off` 时 `runExecutionStage` 跳过第二步。
- 工程空间里「方案评审」复用同一引擎，但辩题来源从「答案分歧」扩展到「方案取舍」。

### Phase E：工程理解

复用：`resolveGrantedPath`、`assertGrant`、`UtilityProcess`、`PlanPreview`。

新增（顺序建议）：

1. `fs.tree`（递归、忽略规则、深度/数量上限）。
2. `fs.search`（按内容/文件名，返回路径 + 行号 + 片段；必须先有忽略规则，否则 `node_modules` 会拖死）。
3. 证据结构：`{ path, line, hash, mtime, readAt }`，落进会话证据表（不要求 SQLite，先按会话一个 JSON 文件即可）。
4. 工程上下文：会话级 `workspaceRoot` + 最近读过的文件清单。

不建议一开始上 AST、向量库、全量调用图——V2.1 §Phase E 也明确说「不要未经论证就引入」。

### Phase F：工程实施

复用：计划协议、审批、grant、UtilityProcess、`verifyWrittenFile`。

新增（按风险从低到高）：

1. `fs.writeFile` 的「覆盖已有文件」变体（带内容哈希前置校验，防并发改坏）。
2. `fs.patch`（unified diff 或按行替换），比整份覆盖安全。
3. `test.run`（限定命令 allowlist、工作目录、超时、输出截断、真实退出码）。
4. 独立 Review 模型（用 `JudgeEngine` 的形状，但评审对象是 diff）。
5. 「修复 → 再验证」循环（最多 N 轮，每轮都要新审批）。

每一步都要同步扩展 `TOOL_NAMES`、`StepSchema`、`assertGrant`、`PermissionPreset` 语义与 `SECURITY.md`。

### Phase G：回归

现有 540 条用例 + V2.1 的 K/E/D/S 清单；新增用例至少覆盖：双入口切换、识别可改判、分析读文件、写入拒绝、测试真实执行。

## 7. 推荐顺序与进入条件

顺序按任务书：**A（已完成）→ B → C → D → E → F → G**。两点补充：

1. **不要先做 F。** 没有工程理解就做代码修改，等于让模型在没读代码的情况下改代码；V2.1 结尾也写了这一点。
2. **B 与 C 可以拆成两个可验收的小步**：B 只做「结构与持久化」，C 只做「识别与可改判」，不要合在一次提交里。
