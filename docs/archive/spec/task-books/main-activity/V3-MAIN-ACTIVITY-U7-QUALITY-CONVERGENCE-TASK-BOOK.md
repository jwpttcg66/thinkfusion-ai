## 一、目标

把已落地的「任务结果」面板打磨成**可信、清晰、无重复、可追溯**的协作结果工作台。

用户应能直接回答：

1. 最终结论是什么？
2. 哪些核心观点支持 / 反对 / 补充？
3. 有没有真实争议，裁决是什么？
4. 评审问题如何处理，验证是否通过？
5. 证据能否定位到真实消息或事件（不是伪造 id）？

## 四、工作项与验收

### P0-1 展示去重

- `CollaborationResultPanel` 已接线时，`ConversationView` / `TaskConversation` 不得再完整复述结论、结构化分歧裁决条、评审问题清单、验证汇总。
- 时间线仍保留事件顺序；可用短标记指向「见上方任务结果」。
- `compactProcess` 生效：协作过程层**默认收起**。

**验收：** 同一任务主活动区不出现两份完整结论 / 两份完整评审清单。

### P0-2 来源真实性

- 禁止 `messageId: evidence:${index}` 等伪造 id。
- `evidenceRefs` / `sourceRefs` 只携带真实 `messageId` / 事件定位，或仅 `label`（无 id）。
- 面板至少展示可读来源标签；可点击跳转可在后续迭代补齐，但不得假装已定位。

**验收：** `test:collaboration-result` 断言意见证据引用不含 `evidence:` 伪造前缀；空证据保持空数组。

### P1-1 核心意见质量

- 区分：核心观点 / 普通完成回答 / 补充 / 真实反对；不得把所有 `member.completed` 一律当核心意见且全部 `neutral` 无说明。
- 意见超过展示上限时必须有「展开全部」入口。

### P1-2 Debate 统一表达

- General / Knowledge / Engineering 在结果面板使用同一套争议 → 主张 → 交锋 → 裁决区块。
- 允许底层仍是 DebateSnapshot vs PlanDebate；用户侧只看到一套表达。

### P1-3 Review 语义

- 结构化问题尽量带理由、建议、目标对象；关键词分级仅作降级，不得当作完整评审语义。

### P1-4 三场景真机

| 场景 | 最低证据 |
| --- | --- |
| Engineering | 结果面板 + 评审 disposition 写回 + 无重复结论（可延续既有冒烟并收紧断言） |
| General | 真实多通道问答；面板结论/意见/争议与时间线不重复 |
| Knowledge | 真实知识场景至少一次；同上 |

U6 既有「Engineering 单路径冒烟」保留为历史证据；整体 VERIFIED 以本阶段三场景为准。
