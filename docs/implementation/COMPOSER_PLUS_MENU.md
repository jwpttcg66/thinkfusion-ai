# 输入框的「＋」：往这一问里加东西

> 2026-11-09。参照 WorkBuddy 输入框左下角的「＋」——一个按钮，一组「往这一段
> 对话里加什么」的入口：添加文件、引用对话中的文件、模式、专家、技能、连接器。

## 1. 原来缺什么

输入框里能改的只有三样：项目目录、权限、研究设置（第三个胶囊）。其余设置都
在侧栏和设置面板里，「这一问带哪份文件」「这一问用哪个空间」在提问的那一刻
没有入口。往一个网页聊天框里贴一份 CSV，只能自己复制粘贴。

「＋」补的就是这一段：**提问那一刻，这一问能带什么、按什么空间跑**。

## 2. 六项，每一项都是真的

| 菜单项 | 做什么 | 落到哪 |
| --- | --- | --- |
| 添加文件 | 系统文件选择框（可多选），返回引用；正文在**发送那一刻**读 | `attachment:choose` → `src/main/attachments.ts` |
| 引用对话中的文件 | 列出这条会话带过的文件，点一下重新挂到这一问 | `Conversation.attachments` |
| 模式 | 知识 / 工程两个空间；网页 / 本地 / 云端 / 混合四种主导 | `workspace:set`、`conversation:config` |
| 专家 | 高级开发工程师的开 / 关 | `expertise:set` |
| 技能 | 工程设计与实施的开 / 关 | `expertise:set` |
| 连接器 | 内嵌的网页来源，点一下切页；内置插件入口 | `app:set-source`、设置面板 |

不做「敬请期待」的入口：没有后端支撑的菜单项就是假的。

## 3. 附件不是提示词

这是这个功能最容易走错的地方。`AGENTS.md` 第 1 条：不给用户的问题套固定提示词。
附件这条路同样成立：

- 没有附件时，发出去的字符串与原来**逐字相同**（`check-prompt-policy` 与
  `check-attachments` 都盯着）；
- 有附件时，用户原话在最前面、一个字不改，附件跟在后面，每份一个标题行
  （`【附件 1】name（体积，全文 / 已带前 N 字）`）；
- 附件是用户自己挑的，他知道自己挑了什么。这不是我们替他写的话术。

## 4. 读盘在发送那一刻

挑文件时只读元信息（名字、路径、体积），正文不进渲染层、不进会话存档：

- `Conversation.attachments` 只存引用；
- 发送时 `readAttachmentTexts` 重新读盘。文件在挑完之后被改掉就是新内容，
  被删掉就**整条提问不发**并明确报错（不会留下一条「问过了」的空会话）。

限制都是为了不让一次提问把输入框撑爆：

| 限制 | 值 | 理由 |
| --- | --- | --- |
| 文件数 | 6 | 再多，网页输入框和模型上下文都装不下 |
| 单份字数 | 12 000 | 一份日志读完还有余量 |
| 合计字数 | 48 000，按份均分 | 先到先得会让后两个文件变成零头，看起来像没生效 |
| 单份体积 | 4 MB | 超过通常是选错了文件（视频、安装包），直接说 |

二进制文件（前 4 KB 有 NUL）一律拒绝：读成 UTF-8 是替换字符，模型只会照着幻觉。

## 5. 能力插件化的落点

附件读取登记成主进程能力 `file.attach`（只读）。清单从 60 条变成 61 条，
设置页可见、可停用；**停用时提问会明确报错**，不会悄悄少几份附件。

`ConversationRunner` 拿的是注入的 `readAttachments`，实际执行走
`mainCapabilities.execute('file.attach', …)`；插件本身的实现本体由
`capabilityContext.readAttachments` 注入。宿主初始化早于 `registerIpc`，
所以中间用一个模块级钩子 `attachmentReader` 接上。

### 只读用户亲手挑的文件

IPC 输入一律当不可信（这个仓库一贯的约定）。附件是一条新的读盘通道：不设边界，
渲染层里任何一段代码都能让主进程读 `~/.ssh/id_rsa` 再发给网页。

所以 `trustedAttachmentPaths` 只认两处来源：

- 本次运行里在「添加文件」对话框里挑过的路径（`pickedAttachments`）；
- 这条会话已经存着的引用（`Conversation.attachments`）——「引用对话中的文件」
  在重开应用之后仍然能用，靠的就是它。

不在来源里的路径直接报错，不静默丢掉：悄悄少几份附件会变成「界面说有、实际没发」。

## 6. 专家与技能：一份开关

「＋」里的专家 / 技能开关与「设置 · 专家与技能」写的是同一份
`userData/expertise.json`，不是第二套状态。设置面板关闭时输入框那份会重新读一次，
两处不允许各说一套。

菜单里也照实写清楚：这两项**只在工程空间生效**；技能还受场景判定约束——
「这个文件多少行」这类读数问题即使开着也不会加载（`expertise/trigger.ts`）。

## 7. 测试

```
npm run test:attachments   # 拼装、读盘、限制、抄进提问链路
npm run test:capabilities  # 清单 61 条、file.attach 注册与停用报错
npm run test:runner        # 老路径：没有附件时问题逐字发出去
npm run test:prompt-policy # 固定提示词仍不存在
```

## 8. 带附件时怎么路由（2026-11-09 修）

真机踩到过：工程空间里上传一份 `.md`，正文只写「这个方案」，发送后停在一句
「这次没有直接执行：没有明确的分析或实施动词，需要用户确认」。文件已经挑了、
也读进正文了，却因为规则里找不到动词而原地不动。

现在的规则（`shared/workspace.ts` 的 `routeTask`）：

| 输入 | 判定 |
| --- | --- |
| 没有任何动词 + 带附件 | `engineering_analysis`，理由写「随这一问附了 N 个文件，按只读分析处理」 |
| 没有任何动词 + 不带附件 | 仍是 `clarify`（不猜） |
| 命中改动词（修改/实现/重构…）+ 带附件 | `engineering_execution`（按用户说的走） |
| 同时命中只读词与改动词 + 带附件 | 仍是 `clarify`（`signals` 非空就不让附件替用户解冲突） |

两条边界没变：附件只把「没有动词」抬到**只读**分析，绝不凭空放行实施；
问题原文、知识空间、答辩/汇总链路一律不动。附件正文仍然只进模型那条提问
（`composeQuestionWithAttachments`），不进路由判据。

界面的路由预览（输入框上那个「工程分析 / 待确认」小标）用同一个函数、同一份
`attachmentCount`，所以发送前看到的就是发送后的判定。
