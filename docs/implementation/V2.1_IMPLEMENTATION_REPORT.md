分支：`0.1.2`　基线：`47e1926`（V2.1 两份 docx 进入 main 之后）

## 0. 一句话

按任务书 Phase B–G 在现有工程上增量落地：加了双工作空间、工程任务识别、辩论开关、真实工程读取与证据、覆盖写与真实测试、独立评审；**没有重写 ConversationRunner / MasterAgent / DebateEngine / Judge / Runtime 的任何既有协议**。

## 1. 硬约束（先写，免得以后被悄悄放宽）

1. **第一轮回答仍来自所有已开启且可用的网页通道，用户问题原样发出。** 工程证据不进第一手提问，只在执行阶段的汇总材料里出现。新增测试 `check-runner.mjs` 里专门断言了这一点。
2. **执行方式归属规则不变。** `web` 只用网页、`local` 只用本地、`cloud` 只用远程、`hybrid` 先决定一类再只用那一类；V2.1 新增的成员都走既有 `selectParticipants` / `ownershipOf`。
3. **知识空间行为零改动。** `start({text})` 不带 `workspaceMode` 时走原来的 `classifyIntent` 五类分支；45 条 runner 用例里有一条专门守这条。
4. **识别不等于授权。** `engineering_execution` 只是把话交去生成计划；写不写仍由 `PlanPreview` 审批、`TaskGrant`、`assertGrant` 决定。
5. **老会话不需要迁移。** 所有新字段都是可选；读不到 `workspaceMode` 一律按知识空间。

## 3. Phase C：工程任务自动识别

`src/shared/workspace.ts` 是纯函数层：`classifyEngineeringIntent()`、`routeTask()`、`normalizeWorkspaceState()`、`normalizeDebateMode()`。

- 规则覆盖：分析 / 解释 / 定位 / 评审 → Analysis；修改 / 实现 / 新增 / 重构 / 修复 / 删除 / 跑测试 → Execution；「先分析再修改」记两阶段但本轮只读；同时命中两类词或完全认不出 → `clarify`，不擅自进高权限。
- 优先级：用户本轮手动指定 > 工作空间 > 工程上下文（有没有项目）> 规则。
- **可见且可纠正**：输入框上方实时显示「本次判为 X · 依据」，旁边三颗按钮「自动 / 按分析 / 按实施」可当场改判。会话头部也显示空间与路由结果。
- 与旧 `classifyIntent` 并存：知识空间仍用五类旧值，历史数据不受影响。

V2.1 的 7 条工程语句在 `check-workspace.mjs` 里逐条断言，全部判对（审计时是 6 条判错）。

## 4. Phase D：辩论接入与开关

- `ConversationExecutionConfig.debateMode?: 'auto' | 'on' | 'off'`，缺省 `auto` = 老行为。
- `off`：主导人只汇总，不生成辩题、不交锋、不出最终意见。
- `on`：主导人没找到分歧时拿原问题兜一个辩题。
- `ResearchPanel` 新增「辩论开关」下拉；`ConversationRunner.runExecutionStage()` 按开关走。
- 两个空间共用同一条会话链路和同一个 `DebateOrchestrator`，不需要第二套引擎。

**D-02 工程分析开辩**：工程分析走的是同一条 `runExecutionStage()`，工程证据只是汇总材料的一部分，辩论照旧由主导人给的辩题决定——所以「工程分析 + 辩论」本来就是通的，本轮补的是真机证据（见验收报告 s4）。

**D-03 方案评审辩论（新）**：任务书 Phase F 要求「任务拆分与方案评审（辩论可选）」。
`src/main/engineering/plan-review.ts` 三个纯函数：

| 函数 | 作用 |
| --- | --- |
| `shouldDebatePlan(mode, plan)` | `off` 不辩；`on` 一定辩；`auto` 只在「≥3 步」或「含写入/测试」时辩（Auto 不得无声扩大调用） |
| `planDebateTopics(plan)` | 从计划本身取风险：覆盖写、有写入没测试、步骤过多；最多 3 条 |
| `summarizePlanDebate({rounds, topics})` | 取最后一轮立场，失败的成员点名；空辩论明写「不能据此判断」 |

编排顺序改为「计划 → 方案评审 → 审批」：`handleAnswer()` 先把计划卡片发出去（状态仍是 `plan_ready`，此时审批会被拒绝），再跑辩论，最后才进 `awaiting_approval` 并补发 `plan.debated`。辩论**只用本地/云端模型**：此刻正有一条网页在当计划生成器，让辩手钻进同一条会话会把计划请求和辩论请求搅在一起。一个 API 成员都没有时如实记「未经评审」，不假装辩过。

## 5. Phase E：工程理解

新增 `src/main/engineering/project.ts`：`scanProject(root, question)` 真实读授权目录，产出 `EngineeringEvidence[]`（`path` / `line` / `excerpt` / 整文件 `sha256` / `mtime` / `readAt` / `why`）。

- 有界：深度 6、文件 500、单文件 256 KiB、总量 2 MiB、片段 8 行；截断会写进 `warnings`。
- 排除：`node_modules`、`.git`、构建产物、符号链接、二进制、`.env`、密钥/证书/凭证类文件名。
- 证据落进 `Conversation.engineeringEvidence`，界面有独立证据卡；`engineeringMaterial()` 把它拼进**主导人汇总**材料，结论必须写明 `路径:行号`。
- 读不到目录时进入 `awaiting_user`，如实说明原因，不让模型凭常识猜架构。

**结构关系（新）**：`src/main/engineering/analysis.ts`，对应产品定义 4.1 的 Symbol Search / Dependency / Change Impact：

| 能力 | 做法 | 边界 |
| --- | --- | --- |
| 符号索引 | 正则识别 `function` / `const fn =` / `class` / `interface` / `type` / `export` | 明确标「按正则识别」，不冒充 AST |
| 调用点 | 文本匹配 + 排除定义行本身 | 明写「可能包含同名函数」 |
| 模块依赖 | 解析 `import ... from` / `require()`，相对路径按已知文件集合解析 | 不解析别名（`@/`），解析不到就标外部 |
| 变更影响 | 反向依赖链（谁 import 了我），可传递 | 只覆盖静态 import |
| 架构概览 | 按目录聚合文件数与主要符号 | 不做语言/框架识别 |

结果进 `ProjectScan.analysis`，拼在证据之前，整段都带【工程证据…不是模型推测】抬头。

Runtime 侧新增两个只读工具（`src/agent/tools/project-read.ts`）：`fs.tree`（递归列目录）、`fs.search`（内容搜索，返回 `路径:行号` 与命中行），让执行计划能先看清结构再决定改哪个文件。

## 6. Phase F：工程实施

`TOOL_NAMES` 从 4 个扩到 7 个，前四个名字与语义一个没变：

| 工具 | 作用 | 安全边界 |
| --- | --- | --- |
| `fs.writeFile` + `overwrite` / `expectedHash` | 改已有文件 | 必须回填先前 `fs.readFile` 的 sha256；不一致拒绝；同目录临时文件 + 原子 rename，不截断原文件 |
| `fs.tree` | 递归目录 | 忽略依赖/凭证，条目上限 |
| `fs.search` | 内容搜索 | 纯子串匹配、命中/文件数上限 |
| `test.run` | 真实执行测试 | 固定命令→固定 argv 映射，`shell:false`，无参数插值，最小环境变量（不带 API Key），120s 超时，输出 64 KiB 上限，真实退出码/耗时/工作目录写进报告；非零退出码记为失败步骤 |

配套改动：`StepSchema` / `PlanSchema`（覆盖写必须带 hash）、`TaskGrantSchema.allowedTools` 上限 7、`allowedToolsForPreset`、`assertGrant`（`read-only` 只允许四种只读工具，明确拒绝 `test.run`）、`src/agent/index.ts` 分发、`SECURITY.md`。写入类工具（`mkdir` / `writeFile` / `overwriteFile`）**自己再挡一次只读授权**：工具是导出的，只靠调用方自觉等于把「只读」变成约定而不是约束。

**独立 Review**：`src/main/engineering/review.ts`。优先用非规划的本地/云端模型读执行报告，产出结论与问题清单；没有可用模型时退回规则版并如实标 `backend: 'rules'`。规则版硬检查：失败步骤、测试退出码、改了文件却没有真实测试。结果通过 `review.ready` 事件在任务页显示。

**修复任务闭环（新）**：`buildReportPrompt()` 增加可选 `review`。有评审问题时提示里多一段「这一轮的定位是**修复任务**」：逐条对应问题、不重做已成功步骤、改完必须重新验证。编排器把评审结论直接交给 `continueAfterReport()`，并记一条日志说明「已并入下一轮计划请求（仍需你重新批准）」。**仍不自动执行**——第二轮计划要重新审批，这是安全模型的要求，不是没做。

## 6.1 知识空间的专属行为（K-03 / K-04）

以前 `compare` / `extract` 只是分类器贴的标签，执行链照旧按普通问答汇总，用户拿到的还是一段散文。

- **compare**：`lead-stage.ts` 的 `taskInstructions('compare')` 要求主导人「按被比较对象逐项对比（维度 × 各方观点）再给结论」，并在【分歧】里写明「各自在什么条件下成立」。
- **extract**：`src/main/knowledge/page-extract.ts` 真实抓取用户点名的网页（`fetch` + 手写正文抽取），产出 `PageEvidence`（标题、正文、字符数、整段 sha256、HTTP 状态、说明）。正文只进汇总材料，第一手提问仍是用户原话；抓不到就明说「没有正文可依」，不假装读过。SSRF 防护：只允许 http/https、拒绝内网/回环/元数据地址、限制重定向与体积。

## 6.2 Model Router

`src/shared/model-route.ts` 的 `routeModels()`，对应产品定义第 8 节「选择合适模型」。它在**提问之前**给出这一轮的参与名单与理由，写进 `Conversation.modelRoute`，界面上以「路由：N 个回答者 / 谁主导」显示。

- 回答者永远来自网页通道——执行模式只决定回答之后谁汇总/质疑/裁决，不改变「谁来回答」。
- 用户选定的模式不被推翻：`web` / `local` / `cloud` 各自只用同类成员；只有 `hybrid` 才由这一层综合决定（短结论走本地、工程实施与长链条走云端、都没有则降级网页）。
- 降级必须说出来（`degraded`），并在理由里写明。
- `estimatedCalls` = 回答者数 + 1 次汇总，把「多模型」的成本摊开给人看。
- 只记录、不改选人：真正问谁仍由 `poolFor` / `executorIdsFor` 决定，路由算错不会连带改坏提问链路。

## 8. 明确没有做的（诚实边界）

- 没有引入 AST 解析器、向量库或全量调用图。V2.1 Phase E 也要求「不要未经论证就引入」；当前是正则 + 静态 import 解析，结论里都写了识别方法。
- 没有**自动**修复闭环：评审结论会并进下一轮计划请求，但第二轮必须重新审批。全自动循环会绕开审批粒度，是当前安全模型不允许的。
- 没有证据库 / 跨会话检索（ROADMAP P5）。工程证据、网页正文都只属于本条会话。
- 方案评审辩论只用本地/云端模型：网页通道此刻在当计划生成器，同一条会话里塞辩论请求会把计划和辩论搅在一起。
- 阶段完成不等于真实模型事实准确率达标（`DEBATE_ACCEPTANCE.md` 已写明）。
