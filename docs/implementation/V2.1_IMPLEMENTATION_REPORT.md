## 0. 一句话

按任务书 Phase B–G 在现有工程上增量落地：加了双工作空间、工程任务识别、辩论开关、真实工程读取与证据、覆盖写与真实测试、独立评审；**没有重写 ConversationRunner / MasterAgent / DebateEngine / Judge / Runtime 的任何既有协议**。

## 1. 硬约束（先写，免得以后被悄悄放宽）

1. **第一轮回答仍来自所有已开启且可用的网页通道，用户问题原样发出。** 工程证据不进第一手提问，只在执行阶段的汇总材料里出现。新增测试 `check-runner.mjs` 里专门断言了这一点。
2. **执行方式归属规则不变。** `web` 只用网页、`local` 只用本地、`cloud` 只用远程、`hybrid` 先决定一类再只用那一类；V2.1 新增的成员都走既有 `selectParticipants` / `ownershipOf`。
3. **知识空间行为零改动。** `start({text})` 不带 `workspaceMode` 时走原来的 `classifyIntent` 五类分支；45 条 runner 用例里有一条专门守这条。
4. **识别不等于授权。** `engineering_execution` 只是把话交去生成计划；写不写仍由 `PlanPreview` 审批、`TaskGrant`、`assertGrant` 决定。
5. **老会话不需要迁移。** 所有新字段都是可选；读不到 `workspaceMode` 一律按知识空间。

## 3. Phase C：工程任务自动识别

`src/shared/workspace.ts` 是纯函数层：`classifyEngineeringIntent()`、`routeTask()`、`normalizeWorkspaceState()`、`normalizeDebateMode()`。

- 规则覆盖：分析 / 解释 / 定位 / 评审 → Analysis；修改 / 实现 / 新增 / 重构 / 修复 / 删除 / 跑测试 → Execution；「先分析再修改」记两阶段但本轮只读；同时命中两类词或完全认不出 → `clarify`，不擅自进高权限。
- 优先级：用户本轮手动指定 > 工作空间 > 工程上下文（有没有项目）> 规则。
- **可见且可纠正**：输入框上方实时显示「本次判为 X · 依据」，旁边三颗按钮「自动 / 按分析 / 按实施」可当场改判。会话头部也显示空间与路由结果。
- 与旧 `classifyIntent` 并存：知识空间仍用五类旧值，历史数据不受影响。

V2.1 的 7 条工程语句在 `check-workspace.mjs` 里逐条断言，全部判对（审计时是 6 条判错）。

## 4. Phase D：辩论接入与开关

- `ConversationExecutionConfig.debateMode?: 'auto' | 'on' | 'off'`，缺省 `auto` = 老行为。
- `off`：主导人只汇总，不生成辩题、不交锋、不出最终意见。
- `on`：主导人没找到分歧时拿原问题兜一个辩题。
- `ResearchPanel` 新增「辩论开关」下拉；`ConversationRunner.runExecutionStage()` 按开关走。
- 两个空间共用同一条会话链路和同一个 `DebateOrchestrator`，不需要第二套引擎。

## 5. Phase E：工程理解

新增 `src/main/engineering/project.ts`：`scanProject(root, question)` 真实读授权目录，产出 `EngineeringEvidence[]`（`path` / `line` / `excerpt` / 整文件 `sha256` / `mtime` / `readAt` / `why`）。

- 有界：深度 6、文件 500、单文件 256 KiB、总量 2 MiB、片段 8 行；截断会写进 `warnings`。
- 排除：`node_modules`、`.git`、构建产物、符号链接、二进制、`.env`、密钥/证书/凭证类文件名。
- 证据落进 `Conversation.engineeringEvidence`，界面有独立证据卡；`engineeringMaterial()` 把它拼进**主导人汇总**材料，结论必须写明 `路径:行号`。
- 读不到目录时进入 `awaiting_user`，如实说明原因，不让模型凭常识猜架构。

Runtime 侧新增两个只读工具（`src/agent/tools/project-read.ts`）：`fs.tree`（递归列目录）、`fs.search`（内容搜索，返回 `路径:行号` 与命中行），让执行计划能先看清结构再决定改哪个文件。

## 6. Phase F：工程实施

`TOOL_NAMES` 从 4 个扩到 7 个，前四个名字与语义一个没变：

| 工具 | 作用 | 安全边界 |
| --- | --- | --- |
| `fs.writeFile` + `overwrite` / `expectedHash` | 改已有文件 | 必须回填先前 `fs.readFile` 的 sha256；不一致拒绝；同目录临时文件 + 原子 rename，不截断原文件 |
| `fs.tree` | 递归目录 | 忽略依赖/凭证，条目上限 |
| `fs.search` | 内容搜索 | 纯子串匹配、命中/文件数上限 |
| `test.run` | 真实执行测试 | 固定命令→固定 argv 映射，`shell:false`，无参数插值，最小环境变量（不带 API Key），120s 超时，输出 64 KiB 上限，真实退出码/耗时/工作目录写进报告；非零退出码记为失败步骤 |

配套改动：`StepSchema` / `PlanSchema`（覆盖写必须带 hash）、`TaskGrantSchema.allowedTools` 上限 7、`allowedToolsForPreset`、`assertGrant`（`read-only` 只允许四种只读工具，明确拒绝 `test.run`）、`src/agent/index.ts` 分发、`SECURITY.md`。

**独立 Review**：`src/main/engineering/review.ts`。优先用非规划的本地/云端模型读执行报告，产出结论与问题清单；没有可用模型时退回规则版并如实标 `backend: 'rules'`。规则版硬检查：失败步骤、测试退出码、改了文件却没有真实测试。结果通过新的 `review.ready` 事件在任务页显示。**Review 只建议，修复不会自动执行**——下一轮计划仍需用户重新审批。

## 8. 明确没有做的（诚实边界）

- 没有引入 AST 解析器、符号索引、向量库或全量调用图。V2.1 Phase E 也要求「不要未经论证就引入」；当前做到「真实文件读取 + 路径行号 + 内容指纹 + 关键词检索」。
- 没有自动修复闭环。Review 判定「需修复」后，需要用户重新提问/审批生成新计划。自动循环会绕开审批粒度，是当前安全模型不允许的。
- 没有按任务自动选模型的 Model Router。选谁仍由用户在研究设置里定，或由 hybrid 主导选择器定。
- 没有证据库 / 跨会话检索（ROADMAP P5 仍未做）。工程证据只属于本条会话。
- 没有真机验证多个网页通道同时登录时的完整端到端；本轮回归是离线代码级 + 界面结构级。
- 阶段完成不等于真实模型事实准确率达标（`DEBATE_ACCEPTANCE.md` 已写明）。
