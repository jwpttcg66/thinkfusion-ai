# 辩论的三种主导方式

## 归属规则（2026-11-06 用户裁决，最高优先级，覆盖下文旧定义）

起因是「网页主导为什么需要本地模型」——用户判定**这个设计本身有问题**，并给出规则，要求以后一律按此执行：

> 本地模型主导才使用本地模型，网页主导就完全使用网页，云端的话才使用远程 api；
> 如果只配置一个模型，那就一个模型主导；混合就是综合决定使用那个方式。

逐条落地：

| 执行方式 | 汇总 / 交锋 / 最终意见由谁做 | 明确禁止 |
| --- | --- | --- |
| `local` 本地主导 | 只用本地模型（Ollama） | 不调用云端 API，不把网页当辩手 |
| `web` 网页主导 | 只用网页通道 | **不引入本地 / 云端模型** |
| `cloud` 云端主导 | 只用远程 API 模型 | 不用本地模型，不把网页当辩手 |
| `hybrid` 混合 | 先**综合决定采用上面哪一种方式**，再严格只用那一类 | 不把三类成员混在同一场里各出一部分力 |

- **只有一个可用模型 / 网页通道时，就由它一个主导**：允许同一成员在不同轮次分饰质疑与修正（自辩），如实写进 `plan.warnings`，不再以「可用辩手不足两位」为由跳过整场。
- 「主导」定义的是**这一轮由哪一类成员执行**，不是「谁主持流程」；流程仍由 `DebateOrchestrator` 这段 TypeScript 驱动。
- 网页通道之间仍然互相看不到，且提问链路硬规则不变（**用户原话原样发页面、不套角色行与引导语**）。网页主导的交锋沿用「把材料拼成一条用户消息递进页面」的既有机制（`inlineLeadInstructions`），由承担主导的网页通道在拼接内容里完成质疑与修正，不靠本地模型补位。
- 第一轮回答仍按提问链路硬规则：**所有已开启且页面可用的网页通道都问**。归属规则管的是回答之后的执行阶段，不改写「谁回答」。

> 下文 2026-11-04 的记录里「`web` 由本地/云端成员读取全部观点后交叉质疑」「`hybrid` 网页与本地/云端都在第一轮独立发言」「没有两位辩手就不辩」等描述，均已被本节覆盖，保留仅作历史背景。

## 先说清楚「主导」指什么

**流程不是模型主持的。** 轮次、停止、发言顺序全由 `DebateOrchestrator`（一段 TypeScript）驱动，这一点对应项目书 8.1 与架构第 130 行。三种模式改变的是另一件事：**基准观点由谁给、其他成员围绕谁展开**。记录里用 `lead.drivenBy: 'orchestrator'` 把这件事写死，避免以后被读成「某个模型在主持」。

## 三种模式

| 模式 | 主辩（基准观点） | 第一轮发言 | 后续交锋 | 网页通道 |
| --- | --- | --- | --- | --- |
| `local` 本地主导 | 第一个可用本地模型（可指定；没有本地时取云端） | 本地 / 云端成员 | 同一批成员 | **完全不参与**，内容不往网页发 |
| `web` 网页主导 | 第一个可用网页通道（可指定） | 所有可用网页通道 | 本地 / 云端成员读取全部网页观点后质疑、修正 | 只第一轮，只收到用户原话 |
| `hybrid` 混合 | 不设主辩 | 网页 + 本地 / 云端全部成员 | 本地 / 云端成员 | 只第一轮，只收到用户原话 |

> 本地模型（Ollama）**是辩论的合法参与者**：`local` 靠它给基准观点，`web` / `hybrid` 靠它做交叉质疑。云端 API 只是可选成员——三种主导方式都不要求配 Key，没有云端时本地模型就是交锋者。会话里本地模型仍不算「来源」，那是会话汇总的规则，和辩论无关。

`web` 与 `hybrid` 的差别：网页主导时本地/云端成员**不提供**自己的独立观点，只检验网页观点；混合时它们也在第一轮给出独立观点，且没有主辩。两者都不依赖云端；页面上限是「网页之间看不到彼此的回答」，所以没有本地/云端成员时只跑第一轮独立回答，不空转后续轮次。

## 怎么选的

1. **候选由 health() 实时判定**（`index.ts` 的 `debateCandidates()`）：网页通道问 `SubAgent.health()`，本地/云端问 `ProviderBackedSubAgent.health()`，不可用原因一并带给界面。
2. **用户在界面勾选**参与成员，默认勾选所有可用成员；不可用的显示但禁用，不静默混进名单。
3. **主辩可指定**：`local` / `web` 提供「自动 / 具体成员」下拉；不选时按模式取第一个可用成员，理由写进 `lead.reason`。`hybrid` 不提供，因为它不设主辩。
4. `planLead()` 是唯一的选人判据（纯函数，在 `debate/lead.ts`），主进程算好 `LeadPlan` 交给编排器。界面不做第二套预判，主进程也不信任界面传来的名单——不可用的一律剔除并记进 `plan.excluded`。
5. 主导者、选人理由、整体说明、限制、被排除成员**全部落盘**（`DebateState.lead` / `plan`），历史辩论里随时查得到。老文件没有这些字段，读的时候补成「未记录」，不假装成某个模式。

## 修掉的一个真问题

Phase G 的 `eligible()` 只检查 `extraAgents` 里有没有这个 id，于是**没配 API Key 的 `openai:gpt-4o-mini` 也被算作可用成员**。真机读 `getProviderHealth()` 显示 `openai.available = false`，但名单里照样有它：界面能发起，实际每轮都失败，一场双边辩论静默变成单边。现在候选以 `health()` 为准，界面和主进程用同一份结果。

## 网页成员的边界（提问链路硬规则）

网页成员的 `SubAgentTask` 里**只有 `question` 原话**，没有 `context`、没有 `system`。页面上不会出现「请质疑以下观点」这类包装文字，也看不到别人的回答。它们只在第一轮发言：让页面每轮回答同一句原话，得到的只是重复独立回答，不是交锋。这个限制写进 `plan.warnings`，界面照实显示。

`local` 主导在本机只有一个本地模型时允许「自辩」——同一模型在不同轮次分饰质疑与修正角色。这不是两个独立模型的意见，`plan.warnings` 明确写出来，不冒充。`web` / `hybrid` 没有可读上下文的成员时只保留第一轮，`warnings` 写明「没有交叉质疑」，不空转后续轮次。

## 网页侧数据清理

辩论是独立子系统，不往 `Conversation` 登记，因此**不能用 `deleteConversation`** 清理网页侧记录。每条网页发言存了 `threadUrl`，`debate:cleanup-web` 按地址调 `registry.deleteConversation` 删站点侧会话，再 `newConversation` 把页面移回新对话；没有地址的成员列进 `noAddress`，不假装已删。`debate:remove` 删除本地辩论记录（正在跑的不让删）。界面都有按钮。

## 仍然受限的

- 云端真机仍没验（没有 API Key），所以 `cloud` 类型成员从未真正发言。
- 只有 1 个本地模型，`local` 主导只能是自辩；要有两个真正独立的本地意见，得再装一个模型或配上云端 Key。
- 项目书 8.3 定义了 `reviewer` / `judge` 两种角色，当前 `DebateRole` 只有 `proposer / critic / peer`；Judge 是 Phase H 的独立子系统，接线用规则版，不在辩论角色里。

## 综合卡显示什么（2026-11-06）

一张综合卡按顺序显示四块，缺哪块就整块不显示，不拿别的块顶上：

| 块 | 数据 | 说明 |
| --- | --- | --- |
| 主导人汇总 | `synthesis.recommendation` | 辩**前**写的五段：【结论】【一致】【分歧】【存疑】【辩题】。按标记分段，一段一块 |
| 辩后裁判 | `debate:get` 的 `verdict` | 五档结论、逻辑/证据/反例三维、可追溯率与无效轮次 |
| 辩论过程 | 同一份辩论记录的 `rounds` | 默认收起的 `<details>`：每轮谁立论、谁质疑、谁修正，失败原因照样列出 |
| 辩后最终意见 | `synthesis.finalOpinion` | 主导人读完辩论记录后的裁定，和辩前汇总是两件事 |

`recommendation` **不再被最终意见覆盖**。以前是 `verdictText ?? summaryText`，辩论一跑成功，五段汇总就被顶掉，界面上「分歧」「辩题」整段消失，只剩最后一段话——用户看到的就是「辩论、分歧、总结都没了」。两者解决的是不同问题，不能互相替代。

辩论如果没跑起来（没有辩题、辩手都不可用、引擎失败），综合卡照样显示汇总，系统消息写明原因，不假装辩过。

### 辩题的噪声

网页主导的汇总回答末尾会粘上站点自己的追问（ChatGPT 的「你喜欢这种回复风格吗？」）。如果【辩题】段写的是「无」，读回来就成了「无你喜欢这种回复风格吗？」——按行拆是一条合法辩题，白跑一场两三分钟的辩论。`parseTopics` 现在把「无/没有/无需/不辩 + 标点或站点追问」直接判为不辩，同时保留「无服务器架构…」这类真正的「无X」构词。
