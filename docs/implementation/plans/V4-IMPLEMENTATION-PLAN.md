# 第一部分：实施总纲

## 1.1 本计划的制定依据

本计划以 ThinkFusion V4.0.0 总体架构为目标，以现有 V3 代码为工程基础。

本次审计确认，Main 已经包含相当多的工程能力，包括：

- Goal 与任务规划基础。
- TDL 任务分解。
- ECO 工程上下文探索。
- DMOCA 动态协作。
- Debate 与 Plan Review。
- Verifier 与 Evidence。
- Context Manager 与上下文检查点。
- AgentOrchestrator 和任务执行机制。
- 暂停、取消、中断与恢复。
- 工作流和多模型协作。
- 工程任务 UI 和过程事件投影。

本计划不要求重新实现这些能力，而是先核实真实代码调用链，再统一职责、生命周期和数据流。

**审计范围说明：** 本轮已核对最新 Main 提交、部分核心实现文件、状态文档、长任务契约、历史整改计划和验收材料。由于尚未逐一读取所有源文件、测试及真机原始报告，本计划属于基于现有证据的实施规划，不把抽样核对表述为已经完成的全仓库逐文件审计。进入具体开发前，必须补齐相应文件级调用链和验收证据。

## 1.2 六项核心工程能力

ThinkFusion 的六项核心工程能力是：

1. 理解：理解用户意图、项目、系统结构和实际约束。
2. 分析：识别问题、风险、依赖、现状和可行性。
3. 设计：形成系统设计、技术方案和工程决策。
4. 规划：将目标转化为可执行、可验证的任务。
5. 开发：组织模型、工具和 Agent 完成工程工作。
6. 验证：核实实现是否满足要求，并判断是否真正达到用户目标。

这六项能力不是六个独立产品，也不是必须顺序执行的固定流水线。

它们应当由统一的工程运行机制根据当前目标、任务状态和证据动态调用。

## 1.3 三种工作场景

ThinkFusion 必须支持三种工作场景：

| 场景 | 主要用途 |
|---|---|
| General | 普通知识问答、分析、讨论和信息处理 |
| Knowledge | 知识理解、资料研究、知识组织和持续积累 |
| Engineering | 软件工程项目理解、设计、开发、验证和交付 |

要求：

- 系统自动识别场景。
- 用户可以修正识别结果。
- 三种场景共享基础模型、上下文、事件和协作能力。
- 不强制三种场景使用相同的执行流程。
- Debate 可以在任何场景按需启用。
- 场景切换不能丢失已有上下文和任务状态。

## 1.4 本次实施的核心原则

1. 不重建第二套 Goal、Task、Execution、Evidence 或 Runtime。
2. 优先复用 V3 已有生产能力。
3. 长任务基础能力必须在第一阶段具备。
4. Native-First，External-Enhanced。
5. Debate、多模型和审核按需触发。
6. 用户目标优先，禁止无边界扩大任务。
7. 所有完成结论必须由验收条件和证据支持。
8. 不允许模型自称完成就直接把任务标记为完成。
9. 用户可以随时暂停、继续、取消或修改目标。
10. 工程状态、执行状态和上下文状态必须可恢复。
11. 不能把模拟测试当成真实工程验收。
12. 不能把模块存在当成生产能力已经闭合。

# 第二部分：V4 总体实施架构

## 2.1 六层逻辑架构

### 第一层：用户交互层

职责：

- 用户对话。
- 项目入口。
- General、Knowledge、Engineering 场景入口。
- 目标创建与修改。
- 长任务管理。
- 任务暂停、继续和取消。
- 用户授权和审批。
- 执行轨迹展示。
- 结果和交付展示。

### 第二层：目标与项目管理层

负责管理：

- Goal
- Project
- Requirement
- Acceptance Criteria
- Goal Version
- Project Context

要求：

用户提出目标后，系统必须识别用户真正希望制造或实现的东西，而不是直接把自然语言拆成一串命令。

### 第三层：Engineering Runtime

这是 V4 的核心运行控制层。

统一由以下职责组成：

| 组件 | 职责 |
|---|---|
| Goal Controller | 管理目标、目标版本和目标变化 |
| Decision Controller | 判断当前阶段和下一步行动 |
| Task Scheduler | 任务分解、依赖、调度和局部重规划 |
| Execution Supervisor | 执行生命周期、暂停、取消、重试和恢复 |
| Context Manager | 上下文准备、压缩、恢复和重建 |
| Verification Controller | 验收、证据审查和完成判定 |

这些是逻辑职责，不要求拆成六个独立进程。

第一阶段优先模块化单体，保持清晰接口和独立测试。

### 第四层：工程能力执行层

包含：

- Native Agent。
- 外部 Agent Adapter。
- 模型调用。
- 工具执行。
- 文件操作。
- Shell。
- Git。
- 测试执行。
- 代码编辑。
- 工程工作流。
- 多模型协作。

### 第五层：工程理解与验证层

包含：

- 工程文件理解。
- 符号和调用关系。
- 项目结构。
- 技术栈识别。
- 需求分析。
- 架构分析。
- 方案比较。
- 风险分析。
- 代码审核。
- 测试验证。
- Evidence 生成。

### 第六层：持久化与运行基础设施

包含：

- Goal 和 Project 持久化。
- Task 和 Execution 持久化。
- Event Journal。
- Evidence Store。
- Checkpoint。
- Memory。
- Context Archive。
- Permission 和 Approval。
- 运行状态恢复。

# P1：统一 Engineering Runtime 与长任务基础闭环

**优先级：最高，V4 第一阶段核心。**

这是 V4 最重要的基础工程阶段。

## 4.1 目标

把已有的 Goal、TDL、ECO、DMOCA、Orchestrator、Context Manager、Verifier 等能力组织成统一的持续工程运行机制。

核心不是增加更多 Agent，而是让系统真正知道：

- 用户想实现什么。
- 当前目标是否变化。
- 当前任务做到哪里。
- 当前 Execution 正在做什么。
- 已经产生了什么证据。
- 下一步应该做什么。
- 当前任务是否应该继续、暂停、重试、重新规划或结束。

## 4.2 P1-01：统一 Goal 生命周期

要求：

1. Goal 创建。
2. Goal 理解。
3. Goal Contract 生成。
4. Acceptance Criteria 生成。
5. Goal Version 管理。
6. Goal 修订。
7. Goal 变化影响分析。
8. 受影响任务失效。
9. 重新规划。
10. Goal 完成判定。

必须保证：

目标变化不能只更新一段文本，而要影响相关 Requirement、Task、Execution 和 Evidence 的有效性。

## 4.3 P1-02：统一 Task 生命周期

Task 至少需要明确：

- 创建。
- 分析。
- 分解。
- 待执行。
- 执行中。
- 等待依赖。
- 等待用户。
- 暂停。
- 失败。
- 阻塞。
- 验证中。
- 完成。
- 取消。

Task 必须支持：

- 父子关系。
- 依赖关系。
- 局部失败。
- 局部重试。
- 局部重规划。
- 任务合并与拆分。
- 目标版本绑定。
- 验收条件绑定。

不能把 Task 简单等同于一次模型调用。

## 4.4 P1-03：独立 Execution 生命周期

一个 Task 可以有多个 Execution。

例如：

Task：实现用户认证。

Execution 1：分析当前认证架构。

Execution 2：实现登录接口。

Execution 3：执行测试。

Execution 4：修复失败。

Execution 5：重新验证。

Execution 必须保存：

- 执行 ID。
- 所属 Task。
- 使用的 Agent 或模型。
- 输入上下文。
- 工具调用。
- 执行结果。
- 资源使用。
- 失败原因。
- 产生的 Evidence。
- 开始与结束时间。

同一 Task 的多次执行必须能够区分，不能覆盖之前的事实。

## 4.5 P1-04：Decision Controller

统一决策入口。

根据：

- 用户目标。
- 当前 Goal Version。
- Task Graph。
- 当前执行状态。
- 已有 Evidence。
- 工程状态。
- 风险。
- 预算。
- 用户授权。

判断下一步动作。

允许的动作包括：

- CONTINUE
- ANALYZE
- DESIGN
- DEBATE
- PLAN
- EXECUTE
- VERIFY
- REPAIR
- REPLAN
- WAIT_USER
- PAUSE
- COMPLETE
- CANCEL

注意：

Decision Controller 是统一决策出口，不是第二个任务调度系统，也不能替代 Goal Controller 或 Task Scheduler。

## 4.6 P1-05：长任务持续运行

必须把长任务从“一次性运行计划”升级为持续推进机制。

基本循环：

理解用户目标
→ 分析项目现状
→ 识别问题
→ 设计方案
→ 必要时辩论
→ 制定任务计划
→ 执行任务
→ 验证结果
→ 修复问题
→ 复核用户目标
→ 决定下一轮
→ 持续推进。

每一轮都必须产生可检查的状态变化。

不能要求一次模型调用完成整个项目。

## 4.7 P1-06：Checkpoint 与恢复

Checkpoint 必须记录：

- Goal 和版本。
- Project 状态。
- Task Graph。
- 每个 Task 状态。
- Execution 状态。
- 已完成工作。
- 未完成工作。
- 失败和阻塞。
- Evidence 引用。
- Decision 历史。
- 工程上下文版本。
- 上下文压缩状态。
- 副作用记录。
- 用户授权状态。
- 下一步动作。

恢复流程：

读取 Checkpoint
→ 验证数据完整性
→ 检查 Goal Version
→ 检查 Task 状态
→ 检查 Execution 状态
→ 检查副作用
→ 检查工程文件状态
→ 重建 Context
→ 必要时重新规划
→ 等待用户授权或继续执行。

不能只恢复聊天摘要。

## 4.8 P1-07：用户中途干预

支持：

- 暂停。
- 继续。
- 取消。
- 修改目标。
- 修改约束。
- 增加要求。
- 删除要求。
- 指定执行策略。
- 指定模型或 Agent。
- 审批危险操作。

用户修改目标后，系统必须分析影响，而不是简单追加一条聊天消息。

## 4.9 P1-08：真实长任务验收

至少完成一次持续两小时以上的真实工程任务。

验收必须包含：

1. 真实代码仓库。
2. 多个 Goal 或 Requirement。
3. 多个 Task。
4. 多次 Execution。
5. 多个模型或 Agent 参与的实际样本。
6. 至少一次执行失败。
7. 至少一次修复。
8. 至少一次上下文压缩。
9. 至少一次暂停。
10. 至少一次应用重启。
11. 恢复后继续执行。
12. 用户中途修改要求。
13. 最终测试。
14. 最终交付。
15. Evidence 与目标验收对应。

两小时指真实工程运行的墙钟时间，不是模拟延时，也不是一个长时间模型请求。

**P1 完成条件：** 能在真实项目中持续推进工程任务，暂停后恢复，目标变化后重规划，最终通过证据判定是否达到目标。

# P2：统一质量治理、AQC、Issue Registry、Budget 与反空转

## 5.1 目标

建立统一质量治理体系，防止系统陷入无效讨论、无效审核、重复辩论和无进展修复。

不新建第二个 Runtime。

## 5.2 P2-01：AQC 统一质量控制

AQC 负责：

- 评估当前决策质量。
- 识别证据不足。
- 识别争议。
- 识别风险。
- 判断是否需要审核。
- 判断是否需要 Debate。
- 判断是否需要重新规划。
- 判断是否需要用户确认。

AQC 不负责：

- 创建第二套 Task。
- 取代 Decision Controller。
- 自己管理 Execution。
- 直接决定用户目标。

AQC 应向 Decision Controller 提供质量评估和建议。

## 5.3 P2-02：Issue Registry

统一管理问题对象：

- Issue ID。
- 来源。
- 关联 Goal。
- 关联 Requirement。
- 关联 Task。
- 关联 Execution。
- 严重程度。
- 证据。
- 责任归属。
- 当前状态。
- 修复计划。
- 验证结果。

Issue 状态：

OPEN → TRIAGED → PLANNED → FIXING → VERIFYING → RESOLVED

必要时支持：

- REOPENED
- DEFERRED
- REJECTED
- DUPLICATE

Issue 不能变成第二套 Task 系统。

需要修复的问题应关联已有 Task，或者由 Task Scheduler 正式创建修复任务。

## 5.4 P2-03：统一 Budget Manager

统一预算范围：

- 模型调用次数。
- Token。
- 模型费用。
- 执行时间。
- 工具调用次数。
- 重试次数。
- Debate 预算。
- Review 预算。
- Repair 预算。
- 并行任务数量。
- 外部 Agent 资源。

预算必须支持：

- 任务级预算。
- Goal 级预算。
- Execution 级预算。
- 模型级预算。
- 用户配置。
- 预算告警。
- 超预算暂停。
- 用户批准后继续。

未知费用和未知 Token 必须标记为未知，不允许伪造精确数字。

对于 OpenCode Go 等订阅服务，必须遵循用户明确选择的服务和实际权限，不允许默认启用额外付费渠道。

## 5.5 P2-04：反空转机制

反空转不是简单限制调用次数。

必须识别：

- 是否产生了新事实。
- 是否新增了有效 Evidence。
- 是否解决了 Issue。
- 是否改变了 Decision。
- 是否缩小了不确定性。
- 是否推进了 Task。
- 是否满足了验收条件。

如果连续多轮没有实际进展：

1. 识别无进展原因。
2. 检查是否重复调用模型。
3. 检查是否重复讨论。
4. 检查是否缺少上下文。
5. 检查是否缺少权限。
6. 检查是否需要换模型或工具。
7. 检查是否应该请求用户决策。
8. 必要时暂停当前任务。

## 5.6 P2-05：Debate 与 Review 按需触发

Debate 只在存在有意义的争议时触发。

例如：

- 事实相反。
- 数字冲突。
- 范围不同。
- 架构方案冲突。
- 关键风险判断不同。

不能为了让流程看起来完整而每轮都辩论。

审核也必须按风险和任务类型决定。

低风险、明确任务不应被强制进入多轮审核。

## 5.7 P2 验收

- Debate、Review、Verifier 有明确分工。
- 质量评估有统一出口。
- Issue 可以关联真实 Evidence。
- Issue 修复由统一 Task Scheduler 管理。
- Budget 可以限制资源消耗。
- 反空转可以识别真实无进展。
- 无争议任务不会被强制拉长流程。

---

# P3：Goal–Requirement–Task–Execution–Evidence 闭环

## 6.1 目标

让用户目标可以分解、执行、验证和最终交付。

## 6.2 实施任务

### P3-01：Requirement 管理

Requirement 必须包含：

- 来源。
- 目标关联。
- 描述。
- 约束。
- 优先级。
- 验收标准。
- 版本。
- 当前状态。

### P3-02：Acceptance Criteria

每个重要 Requirement 必须具备可判断的验收条件。

验收条件可以是：

- 文件存在。
- 接口行为正确。
- 测试通过。
- 性能指标满足。
- 架构约束满足。
- 用户确认。
- 真实环境行为满足。

不能把所有需求都简化成模型文本判断。

### P3-03：Evidence 统一管理

Evidence 至少包括：

- 文件证据。
- Git 证据。
- 测试证据。
- 工具执行证据。
- 运行日志。
- 结构化报告。
- 用户确认。

每项 Evidence 必须记录：

- 来源。
- 时间。
- 关联对象。
- 生成方式。
- 有效范围。
- 可信程度。
- 是否已过期。

### P3-04：Goal Completion

Goal 完成必须检查：

- 所有必要 Requirement。
- 所有强制 Acceptance Criteria。
- 关联 Task。
- Execution 结果。
- Evidence 有效性。
- 未解决 Issue。
- 风险和约束。
- 用户确认要求。

最终状态至少支持：

- MET
- PARTIAL
- NOT_MET
- BLOCKED
- NEEDS_USER_CONFIRMATION

不能仅凭模型总结判定 MET。

### P3-05：目标变化传播

目标修改后：

1. 创建新 Goal Version。
2. 比较新旧目标。
3. 识别受影响 Requirement。
4. 识别受影响 Task。
5. 判断已有 Evidence 是否失效。
6. 判断是否需要重做。
7. 形成新的任务计划。
8. 请求必要的用户确认。

## 6.3 验收标准

- Goal 可追踪到 Requirement。
- Requirement 可追踪到 Task。
- Task 可追踪到 Execution。
- Execution 可追踪到 Evidence。
- Evidence 可支持 Acceptance Criteria。
- 最终 Goal 状态可以解释。
- 目标修改后能够正确传播影响。

# P4：General、Knowledge、Engineering 三场景统一

## 7.1 目标

让三种场景使用统一基础设施，同时保留各自的专业行为。

## 7.2 P4-01：场景识别

识别：

- General。
- Knowledge。
- Engineering。

依据：

- 用户意图。
- 项目上下文。
- 当前会话状态。
- 用户指定的工作方式。
- 输入内容特征。

允许用户修正。

不能因为用户提到代码就必然进入 Engineering，也不能因为用户上传文档就必然进入 Knowledge。

## 7.3 P4-02：General

支持：

- 普通问答。
- 分析。
- 推理。
- 信息整理。
- 多模型协作。
- 按需 Debate。
- 按需 Review。

必须验证普通问答不会被工程任务流程拖慢。

## 7.4 P4-03：Knowledge

支持：

- 文档读取。
- 多资料研究。
- 事实提取。
- 知识关系组织。
- 来源追踪。
- 时效判断。
- 知识冲突识别。
- 跨会话知识复用。
- 按需 Debate。

Knowledge 的结论必须保留来源和证据。

## 7.5 P4-04：Engineering

支持：

- 项目读取。
- 代码理解。
- 需求分析。
- 系统设计。
- 技术选型。
- 任务规划。
- 代码开发。
- 测试验证。
- 代码审核。
- 真实交付。
- 长任务恢复。

## 7.6 P4-05：统一基础设施

三种场景共享：

- Model Provider。
- Model Pool。
- Context Manager。
- Memory。
- Event。
- Evidence。
- Budget。
- Debate。
- Review。
- Permission。

但每种场景使用不同的入口策略和上下文范围。

## 7.7 验收标准

General、Knowledge、Engineering 必须分别完成真机验收。

不能使用一个场景的测试结果代表另外两个场景。

# P5：Native-First 与 External-Enhanced

## 8.1 目标

ThinkFusion 在不依赖外部 Agent 的情况下，能够独立完成基础软件工程任务。

外部 Agent 是增强能力，不是系统运行的必要依赖。

## 8.2 P5-01：Native Engine

逐步形成自身的基础能力：

- 项目发现。
- 文件读取。
- 代码搜索。
- 符号定位。
- 调用关系分析。
- 工程上下文收集。
- 需求分析。
- 任务规划。
- 代码编辑。
- Shell 执行。
- 测试运行。
- Git 操作。
- 结果验证。

可以使用成熟底层技术，不要求重新发明：

- Tree-sitter。
- LSP。
- ripgrep。
- Git。
- 编译器和测试框架。

## 8.3 P5-02：Java 代码理解

这是当前值得重点补强的能力。

现有 ECO 的 Java 结构扫描存在正则级限制。

需要评估并实施：

- Java AST。
- 类和接口。
- 方法和字段。
- Import。
- 类型引用。
- 方法调用。
- 跨文件符号关系。
- Maven / Gradle 项目识别。
- Java 8 / 11 / 21 项目兼容。

建议：

先采用 Tree-sitter Java 建立统一语法结构，再通过 LSP 或 JDT 补充类型解析、符号绑定和调用关系。

不要为了实现 AST 就一次性引入复杂的全量 Java 分析服务。

验收重点是实际项目理解效果，不是解析器本身有多少功能。

## 8.4 P5-03：External Agent Adapter

支持外部 Agent：

- OpenCode。
- 其他兼容 Agent。
- 未来 ACP 适配器。

要求：

- Agent 启动。
- 状态读取。
- 输出采集。
- 工具结果采集。
- 任务关联。
- 超时和中断。
- 失败恢复。
- 权限边界说明。

外部 Agent 必须映射到统一 Task、Execution 和 Evidence。

## 8.5 P5-04：权限统一

必须明确：

TaskGrant 不能自动代表外部 Agent 内部所有工具操作都受 ThinkFusion 控制。

只有在外部 Agent 提供可用权限 API、受控工具包装或隔离执行环境时，才可以宣称权限统一。

否则必须在 UI 和任务记录中明确显示权限边界。

## 8.6 P5 验收

- 断开外部 Agent 后，Native 仍能完成基础工程任务。
- 外部 Agent 可以作为增强执行器接入。
- 两者使用统一任务与证据体系。
- 不伪造外部 Agent 的权限控制能力。
- Java 工程理解能通过真实项目样本验收。

# P6：工程工作台与全链路可观测性

## 9.1 目标

让用户能够清楚知道 ThinkFusion 正在做什么、为什么这样做、做到了哪里、产生了什么结果。

## 9.2 工作台结构

左侧：

- 工作空间。
- 项目。
- 当前任务。
- 长任务列表。
- 任务状态。

主区域：

- 当前任务对话。
- 当前进度。
- 任务阶段。
- 重要决策。
- 工具执行。
- 交付结果。

独立页面：

- 对话。
- 轨迹。
- 统计。

## 9.3 多模型展示

多个模型参与时：

- 每个模型输出独立展示。
- 角色和贡献明确。
- 中间草稿与最终结论区分。
- 评审意见可以追踪。
- 决策依据可以查看。

不能把多个模型输出混在一个不可区分的对话气泡中。

## 9.4 长任务实时进度

对话主区域必须显示：

- 当前阶段。
- 已完成任务。
- 正在执行任务。
- 等待任务。
- 失败任务。
- 当前阻塞。
- 下一步动作。
- 用户需要处理的事项。

不能只显示一个旋转图标，让用户不知道系统是否还在工作。

## 9.5 中途干预

用户可以在运行期间：

- 查看执行内容。
- 暂停。
- 取消。
- 修改目标。
- 修改任务。
- 追加要求。
- 审批操作。

界面动作必须与真实 Runtime 状态一致。

## 9.6 P6 验收

分别在三种场景验证：

- 任务状态展示。
- 过程事件展示。
- 多模型输出分离。
- 执行结果展示。
- 轨迹完整性。
- 统计准确性。
- 用户中途干预。
- 暂停恢复。

# 第五部分：实施管理与质量要求

## 11.1 代码审计先于任务实施

每个任务开始前必须完成：

1. 定位生产代码。
2. 定位实际调用链。
3. 检查已有测试。
4. 检查相关真机证据。
5. 确定已有实现与缺失边界。
6. 决定继承、适配、重构或新增。
7. 明确不允许重复建设的模块。

禁止只根据文档描述直接新建代码。

## 11.2 任务书要求

每个实施任务必须包含：

- 任务 ID。
- 业务目标。
- 架构归属。
- 当前代码状态。
- 目标状态。
- 具体文件范围。
- 数据模型变化。
- IPC/API 变化。
- 状态机变化。
- 调用链变化。
- 测试要求。
- 真机验收要求。
- 回退方案。
- 完成证据。

## 11.3 自动化测试

至少包括：

- 类型检查。
- 单元测试。
- 状态机测试。
- 生命周期测试。
- 数据持久化测试。
- 恢复测试。
- 工具中断测试。
- 任务依赖测试。
- 目标版本传播测试。
- Evidence 完成判定测试。
- 场景隔离测试。
- UI 投影测试。

## 11.4 真机验收

必须使用真实 Electron 应用和真实运行环境。

不能用：

- 纯 Mock。
- 仅有类型定义。
- 仅有 IPC 单元测试。
- 仅有事件重放。
- 仅有模拟等待时间。

替代生产验收。

## 11.5 生产证据

每个重要功能至少记录：

- Git SHA。
- 操作环境。
- 测试时间。
- 输入。
- 操作过程。
- 关键事件。
- 执行结果。
- 产物。
- 测试结论。
- 未覆盖边界。

## 13.5 核心验收五：Native-First

## 13.6 核心验收六：用户可观测与干预

10. 用户中途干预可靠。

# 第九部分：最终实施决议

ThinkFusion V4.0.0 不以重写 V3 为目标，也不以增加 Agent 数量为目标。

它要完成的是一次核心工程体系的统一：

从用户目标出发，持续理解项目、分析问题、设计方案、组织任务、执行工程工作、验证结果，并根据真实证据不断调整。

V3 已经形成的代码资产应尽可能继承。

真正缺失的部分才新增。

职责不清的部分进行适配。

存在重复和冲突的部分才重构。

**最终产品目标只有一个：帮助用户开发出自己想要制造的系统。**

所有架构、模块、模型、工具和流程，都必须服务于这个目标。
