# 一、项目总体目标

## 1.1 核心目标

ThinkFusion V3 不应只是一个能够调用多个模型、执行工具和生成工程计划的 AI 应用。

它需要成为一个以用户真实目标为中心的持续工作系统：

1. 理解用户真正希望完成什么。
2. 将用户目标转化为明确、可验收的目标契约。
3. 根据目标进行任务分解和依赖规划。
4. 动态决定需要哪些模型、工具和协作方式。
5. 根据风险和信息价值决定是否辩论、审核和验证。
6. 执行任务并持续收集真实证据。
7. 根据执行结果决定继续、修复、重新规划、重新设计或询问用户。
8. 判断用户目标是否真正达成。
9. 支持暂停、中断、恢复和跨会话持续工作。
10. 将真实执行过程和最终结果完整呈现给用户。

最终形成：

**用户目标 → 目标理解 → 目标契约 → 任务分解 → 动态协作 → 执行 → 证据验证 → 质量控制 → 目标符合度 → 下一轮决策 → 最终交付。**

## 1.2 产品设计原则

### 原则一：目标驱动，而不是流程驱动

系统不能为了完成固定工作流而执行任务。

每个阶段都必须服务于用户目标。

当局部问题可以局部修复时，不得无故重新执行完整流程。

### 原则二：证据驱动，而不是模型自我声明

模型说完成，不代表任务完成。

工具执行成功，不代表目标达成。

测试通过，也不代表所有成功标准都满足。

最终结果必须以可追溯的实际证据为依据。

### 原则三：动态质量控制，而不是固定辩论和审核

辩论、审核、验证和模型数量由风险、争议、证据和决策价值决定。

不能因为进入某个阶段，就机械地增加模型调用。

### 原则四：最小必要动作

系统应当选择能够解决当前问题的最小动作。

例如：

- 事实错误：重新分析。
- 局部代码错误：局部修复。
- 任务分解错误：重新规划。
- 设计无法满足目标：重新设计。
- 目标理解错误：重新进行 Goal Reasoning。
- 真实争议：定向辩论。
- 无新问题、无新证据：停止重复流程。
- 需要用户决定：等待用户。

### 原则五：所有重要过程可追溯

目标、任务、模型贡献、工具调用、证据、问题、决策、版本和最终结论必须能够建立关联。

# 二、V3 全局架构

## 2.1 总体架构

系统采用五层核心架构，并由横向能力提供持续支持。

### 第一层：Goal Contract Layer（目标契约层）

负责理解用户目标并维护目标契约。

核心能力：

- Goal Reasoning
- Goal Contract
- Goal Criteria
- Goal Revision
- Goal Fit
- Goal Change Impact

每个目标至少需要明确：

1. 用户意图。
2. 最终期望结果。
3. 目标价值。
4. 成功标准。
5. 隐含约束。
6. 可行性与风险。

信息来源必须区分：

- USER_EXPLICIT：用户明确提出。
- MODEL_INFERRED：模型推断。
- SYSTEM_DERIVED：系统根据工程事实推导。
- NEEDS_CONFIRMATION：等待用户确认。
- ACCEPTED_ASSUMPTION：已接受的假设。

重大目标变更必须保留原始版本和变更记录。

### 第二层：Goal Decomposition Layer（目标分解层）

负责把目标转换为可以独立执行、验证和集成的任务。

核心能力：

- TDL 多层任务树。
- L0–L3 分层分解。
- 任务依赖。
- Criterion 到任务的映射。
- 任务验收标准。
- 局部重新规划。
- 子任务集成。

每项强制成功标准都必须有任务承接关系。

任务分解不能只根据模型生成的摘要判断是否合理。

### 第三层：Cycle Engine Layer（循环决策层）

负责控制任务持续推进。

核心循环：

Goal Reasoning
→ Analysis
→ Design
→ Design Debate（按需）
→ Planning
→ Implementation
→ Verification
→ Review
→ Review Debate（按需）
→ Conclusion
→ Goal Fit
→ Next Decision

循环不是固定执行全部节点。

系统可以根据任务类型、风险和证据跳过不必要阶段，但必须记录跳过理由。

Cycle 与 Round 必须严格区分：

- Cycle：一次完整的目标推进循环。
- Round：某个执行、修复或审核阶段的内部轮次。

不能将修复轮直接当作新的完整目标循环。

### 第四层：Collaboration Layer（动态协作层）

负责模型、Agent 和角色的动态选择。

核心能力：

- DMOCA 动态模型参与者选择。
- ECO 上下文准备与充分度检查。
- 模型贡献记录。
- 贡献版本管理。
- 争议处理。
- 方案综合。
- 决策快照。

模型正式参与任务前，必须获得完成当前角色所需的上下文。

不能让没有读取工程材料的模型直接参与工程方案裁决。

模型数量由任务复杂度、风险和信息增量决定，不固定要求所有模型参与。

### 第五层：Execution & Evidence Layer（执行与证据层）

负责实际工具执行和结果验证。

核心能力：

- AgentOrchestrator。
- Tool Execution。
- TaskGrant 与 Approval。
- Execution Report。
- Evidence。
- Verifier。
- Checkpoint。
- Runtime Recovery。

必须区分：

- 执行完成。
- 验证通过。
- 目标达成。

三者分别具有独立状态和证据。

## 2.2 横向支撑能力

### AQC：Adaptive Quality Control

动态质量控制。

决定：

- 是否需要辩论。
- 是否需要审核。
- 是否需要独立审核。
- 需要几个模型。
- 审核哪些内容。
- 需要哪些验证。
- 是否允许继续修复。
- 是否需要用户介入。

AQC 不负责执行工具，不替代 Orchestrator，也不建立第二套 Runtime。

### Long Task Management

负责：

- 长任务持久化。
- 暂停与取消。
- 中断。
- 检查点。
- 恢复。
- 状态核对。
- 故障恢复。
- 预算管理。
- 无进展检测。

### Memory / Compaction

两者必须保持职责分离。

Memory：保存跨会话可复用的稳定信息。

Compaction：压缩当前任务上下文，维持长任务运行。

Evidence：记录实际执行事实。

任何摘要都不能替代原始执行证据。

# 三、统一决策与质量控制体系

## 3.1 AQC 风险等级

采用四级质量控制：

| 等级 | 典型场景 | 质量控制策略 |
| -- | --------------------- | ------------------- |
| L0 | 简单问答、只读查询 | 主模型处理，必要时轻量核对 |
| L1 | 小范围修改、简单文档 | 自动验证优先，不默认辩论 |
| L2 | 普通功能、跨文件工程任务 | 必要时定向辩论，独立审核关键结果 |
| L3 | 核心架构、权限、安全、数据迁移、不可逆操作 | 严格证据、定向辩论、独立审核和用户确认 |

风险判断因素：

- 影响范围。
- 复杂度。
- 失败成本。
- 不可逆程度。
- 需求歧义。
- 证据完整度。
- 模型意见冲突。
- 目标变化影响。

风险等级不能仅根据工具数量或计划步数决定。

## 3.2 Debate 触发规则

只针对真实争议触发。

争议类型：

1. 事实冲突。
2. 方案冲突。
3. 目标冲突。
4. 风险冲突。

以下情况不触发辩论：

- 只是表达方式不同。
- 多个模型重复相同观点。
- 没有实际决策差异。
- 没有新增事实或证据。
- 争议已经得到充分解决。

默认辩论流程：

独立分析 → 定向挑战 → 主导模型回应 → 综合决策。

出现重大新证据或决策变化时，才允许追加轮次。

## 3.3 Review 分级

Verification：

使用客观工具进行验证，例如文件回读、类型检查、测试、构建和运行断言。

Targeted Review：

只审核本次改动及直接影响范围。

Independent Review：

重大架构、安全、数据、权限或跨模块风险才启动独立审核。

不能把每次 Review 都升级为全工程审核。

## 3.4 Issue Registry

建立统一问题管理模型。

问题状态：

OPEN
→ IN_PROGRESS
→ RESOLVED
→ VERIFIED

其他状态：

- ACCEPTED_RISK
- DEFERRED
- REJECTED
- DUPLICATE

问题记录至少包含：

- issueId
- fingerprint
- category
- severity
- affectedFiles
- criterionIds
- evidenceRefs
- status
- resolution
- verificationEvidence

规则：

1. 同一问题必须去重。
2. RESOLVED 不代表 VERIFIED。
3. 已验证问题不能无依据重新打开。
4. 只有代码变化、回归或反证才能重新打开。
5. 问题必须关联目标标准或明确说明不影响目标。

## 3.5 信息增量判断

每次辩论、审核和修复结束后，记录：

- New Facts
- New Evidence
- New Issues
- Resolved Issues
- Decision Change
- Goal Impact

如果这些内容均没有变化，则本轮属于低价值操作。

连续出现低价值操作时，停止当前重复流程，转为局部处理或等待用户。

## 3.6 预算与停止规则

分别设置：

- Work Budget
- Cycle Budget
- Debate Budget
- Review Budget
- Issue Repair Budget

建议初始策略：

| 任务级别 | 辩论策略 | 审核策略 | 修复策略 |
| ----- | --------------------- | --------- | -------- |
| L0–L1 | 默认不辩论 | 自动验证 | 局部修复 |
| L2 | 最多一轮定向挑战，必要时追加一轮 | 主审核 | 默认一次修复尝试 |
| L3 | 最多两轮有效争议处理，重大新证据可重新裁定 | 独立审核与严格验证 | 失败后重新评估 |

预算耗尽不能自动视为通过。

重大风险没有解决时，进入 BLOCKED 或 WAIT_USER。

# 四、统一状态与决策出口

Cycle Engine 需要具备明确的决策出口。

| 决策 | 适用情况 |
| ------------ | ------------- |
| COMPLETE | 目标标准已满足并有充分证据 |
| REPAIR | 局部问题可以修复 |
| REANALYZE | 事实、认知或分析存在错误 |
| REDESIGN | 当前设计无法满足目标 |
| REPLAN | 任务分解或执行路径不合理 |
| CLARIFY_GOAL | 目标存在关键歧义 |
| WAIT_USER | 需要用户选择或授权 |
| BLOCKED | 依赖或风险阻止继续 |
| ABORT | 用户取消或明确终止 |

结论状态需要独立管理：

- ACCEPTED
- ACCEPTED_WITH_RISKS
- NEEDS_FIX
- NEEDS_REVIEW
- NEEDS_REDESIGN
- NEEDS_ANALYSIS
- UNRESOLVED
- BLOCKED
- ABORTED

不能仅凭模型生成的最终文本决定 COMPLETE。

# 五、版本一致性与恢复体系

## 5.1 统一版本语义

必须统一以下对象的版本关系：

- Goal Contract Version
- Criterion Version
- WorkTask Goal Version
- ECO Context Version
- Model Contribution Version
- Decision Snapshot Version
- Evidence Version / Source Reference

所有版本判定使用统一规则。

## 5.2 已完成与未完成任务的不同处理

未完成任务：

必须满足当前目标版本，或明确标记为 stale 并重新规划。

已完成任务：

可以保留原始目标版本，但必须重新判断其成果是否满足当前 Criterion。

历史证据：

保留原始来源和版本，不得自动升级为新目标下的有效证据。

决策快照：

依赖的目标、任务或模型贡献失效时，不得继续作为当前有效决策。

## 5.3 暂停和中断

必须区分：

- PAUSE_REQUESTED
- PAUSING
- PAUSED
- CANCEL_REQUESTED
- CANCELLING
- CANCELLED
- INTERRUPTED
- RESUMABLE
- BLOCKED

暂停必须真正控制执行，而不只是修改任务状态。

对于在途 shell.run：

1. 停止分发新的执行步骤。
2. 向运行中的进程发出中断请求。
3. 等待并记录进程终止结果。
4. 无法安全中断时明确报告。
5. 核对文件、副作用和实际执行结果。
6. 创建可恢复检查点。

恢复前重新核对目标契约、任务树、工具执行状态和证据。

# 六、分阶段实施计划

## P0：版本一致性与长任务中断恢复

**优先级：最高**

目标：先保证目标变化和任务恢复不会产生错误状态。

工作内容：

1. 审计 version.consistency 与 goal-recovery。
2. 建立统一版本兼容判定规则。
3. 区分已完成任务和未完成任务的版本继承。
4. 核对 Goal Contract、Criterion、TDL、ECO 和决策快照。
5. 修复在途 shell.run 暂停中断。
6. 统一暂停、取消、中断、恢复状态。
7. 增加异常退出与副作用核对。
8. 补充恢复后的真机测试。

交付：

- 统一版本一致性规则。
- 版本核对实现。
- 工具中断实现。
- 长任务状态机修订。
- 自动化测试。
- 真机恢复验收记录。

验收标准：

- 旧目标任务不会被错误当成新目标任务。
- 已完成任务能够保留历史成果并接受新目标检验。
- 暂停请求不会被错误显示为已经暂停。
- 在途工具中断结果可追溯。
- 应用崩溃后可以正确恢复或明确阻断。

> P0 的详细任务、现状证据、验收与回退见
> [`active/P0-VERSION-RECOVERY-TASK-BOOK.md`](active/P0-VERSION-RECOVERY-TASK-BOOK.md)。

## P1：AQC 动态质量控制与反空转

目标：避免辩论、审核和修复无限重复。

工作内容：

1. 审计现有 DMOCA、Plan Review、Review、repair-loop。
2. 定义 AQC 统一决策接口。
3. 建立风险等级与质量控制策略映射。
4. 统一 Debate 触发规则。
5. 统一 Review 分级。
6. 建立 Issue Registry。
7. 建立跨 Cycle 信息增量判断。
8. 建立分层预算。
9. 实现无进展停止与最小必要动作。
10. 在 UI 中展示触发理由、预算和停止理由。

交付：

- AQC 决策模块。
- Issue Registry。
- Debate / Review 策略接口。
- Budget Manager。
- 信息增量检测。
- 无进展停止机制。
- 端到端测试。

验收标准：

- 无真实争议时不启动辩论。
- 相同问题不反复生成。
- 相同失败命令不会无限重试。
- 轻量任务不会自动进入高强度审核。
- 高风险问题不能因预算耗尽自动通过。
- 每次质量控制都能解释为什么执行或跳过。

## P2：Goal–TDL–Cycle–Evidence 目标证据闭环

目标：保证每个目标标准都有任务承接和有效证据。

工作内容：

1. 完善六维 Goal Reasoning。
2. 完善 Goal Contract 来源和确认状态。
3. 完善 Criterion 唯一身份和版本管理。
4. 建立 Criterion → WorkTask → Evidence 映射。
5. 完善 TDL 任务覆盖检查。
6. 完善证据类型和可信度管理。
7. 完善 Goal Fit 逐条判断。
8. 将 Goal Fit 结果接入 Cycle Decision。
9. 目标变化时计算影响范围。
10. 建立完整目标达成追溯链。

证据类型：

- MODEL_CLAIM
- TOOL_RESULT
- FILE_READBACK
- BUILD_RESULT
- TEST_RESULT
- RUNTIME_RESULT
- INTEGRATION_RESULT
- USER_ACCEPTANCE

交付：

- Goal Reasoning 完善。
- Criterion 追踪模型。
- Evidence 关联机制。
- Goal Fit 判定规则。
- 目标变化影响分析。
- 端到端测试。

验收标准：

- 每条强制标准都有任务承接。
- 每条强制标准都有符合要求的证据类型。
- 模型声明不能替代工具证据。
- 执行完成不能直接推导目标达成。
- 目标达成必须逐条 Criterion 验证。

## P3：General / Knowledge / Engineering 三场景统一验收

目标：三个场景使用统一的目标、质量控制和证据规则，同时保持各自的工作方式。

General：

- 普通知识问答。
- 意图识别。
- 必要时多模型协作。
- 用户按需开启辩论。
- 答案质量与事实核对。

Knowledge：

- 深度调查。
- 多来源证据整理。
- 观点冲突处理。
- 知识沉淀。
- 跨会话记忆和上下文恢复。

Engineering：

- 项目读取。
- 架构理解。
- 方案设计。
- 工程计划。
- 工具执行。
- 审核和修复。
- 目标达成和交付。

交付：

- 三场景统一验收矩阵。
- 场景识别测试。
- 多模型协作测试。
- 辩论按需触发测试。
- 真实会话验收报告。

验收标准：

三个场景均能正确识别工作类型、选择执行路径、控制协作成本并正确结束任务。

## P4：长任务与动态多模型协作完善

目标：复杂任务可以长期持续执行，支持中途变化和故障恢复。

工作内容：

1. 完善子任务独立上下文。
2. 完善 ECO 充分度检查。
3. 完善动态模型参与者选择。
4. 完善贡献与版本绑定。
5. 完善子任务独立验收。
6. 完善依赖变化后的局部重规划。
7. 完善检查点和恢复。
8. 完善 Compaction。
9. 明确串行、逻辑并行和物理并行。
10. 评估真正并行执行的安全边界和资源预算。

交付：

- 子任务上下文管理。
- 模型贡献有效性管理。
- 长任务恢复完善。
- 子任务集成验证。
- 并行能力说明和测试。

验收标准：

- 未读取必要上下文的模型不能参与正式工程裁决。
- 失效贡献不能作为当前有效依据。
- 子任务失败不会无故重启全部任务。
- 长任务恢复后能够保留目标、证据和进度。
- 系统不会把逻辑并行错误显示成物理并行。

## P5：UI 可观测性与最终生产验收

目标：让用户能够理解、控制和追溯整个工作过程。

工作内容：

1. 保持连续文档式对话流。
2. 展示 Goal Contract 和目标符合度。
3. 展示任务分解和执行进度。
4. 分开呈现不同模型的输出。
5. 展示真实工具调用和执行结果。
6. 展示辩论议题和最终裁决。
7. 展示 Issue 生命周期。
8. 展示验证证据。
9. 展示预算和停止原因。
10. 支持暂停、中断、恢复和用户介入。
11. 完善最终交付摘要。
12. 完成完整真机端到端验收。

UI 入口：

- 对话
- 输出
- 轨迹
- 统计

这些入口应继续使用统一任务数据，不得形成第二套任务状态系统。

最终交付需要展示：

- 用户目标。
- 已完成任务。
- 交付文件。
- 验证结果。
- Criterion 满足情况。
- 未解决问题。
- 已接受风险。
- 最终结论。

# 九、统一验收体系

### A. 单元与模块验收

验证纯函数、状态机、版本判定、问题去重和决策规则。

### B. 集成验收

在真实 Electron 应用中使用实际模型、真实工具和持久化数据完成操作。

- 模型超时。
- 模型返回无效内容。
- 工具失败。
- 重复失败。

- 应用强制退出。
- 重启恢复。
- 旧版本任务。
- 证据缺失。
- 预算耗尽。
- 用户中途修改目标。
- 子任务失败。
- 多模型贡献失效。

每个阶段形成：

- 实施记录。
- 变更文件清单。
- 自动化测试结果。
- 真机验收记录。
- 未解决问题。
- 风险清单。
- 阶段完成判定。

# 十一、最终生产验收标准

ThinkFusion V3 完成生产闭环后，必须能够通过以下完整场景：

用户提出一个具有多个成功标准的工程目标。

系统能够：

1. 理解并整理用户真实目标。
2. 明确哪些信息是用户指定、哪些是模型推断。
3. 在必要时向用户澄清。
4. 建立版本化 Goal Contract。
5. 分解任务并确保成功标准有对应任务。
6. 根据风险选择模型和协作方式。
7. 判断是否需要辩论或审核。
8. 执行真实工具操作。
9. 收集并验证执行证据。
10. 发现问题并创建 Issue。
11. 选择局部修复、重新规划或重新设计。
12. 避免重复辩论、审核和修复。
13. 支持用户中途暂停、修改目标和恢复任务。
14. 在目标变更后正确处理旧任务和旧证据。
15. 对所有成功标准逐条进行验证。
16. 生成真实交付物和最终结论。

最终结论必须准确区分：

- 任务执行完成。
- 技术验证通过。
- 用户目标达成。
- 存在已接受风险。
- 尚有未解决问题。

只有所有强制成功标准均有有效证据支持时，才能判定目标完全达成。

## 我的实施建议

这份计划书确定的是全局方向，但实际开发不要六个阶段同时铺开。我建议按三个核心交付批次组织：

1. **第一批：P0 + P1。** 先解决错误恢复、执行中断和质量控制空转。
2. **第二批：P2。** 让目标、任务、证据和最终结论真正闭合。
3. **第三批：P3–P5。** 进行三场景、长任务、协作和 UI 的生产级验证。

尤其需要强调：现有 `repair-loop.ts`、DMOCA、Plan Review 等实现应该优先复用。AQC 是治理这些现有能力的统一决策层，不是再造一套辩论系统。

**建议下一步从 P0 开始，先制作一份基于最新代码的 P0 详细实施任务书，再逐批实施和验收。**
