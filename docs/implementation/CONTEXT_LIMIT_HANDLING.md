# 网页会话上下文满了怎么办

日期 2026-11-06。ChatGPT 在那条「java 和 go 谁更适合做服务器」的会话里弹了一条横幅：

> **上下文窗口已达上限**
> 开启新聊天，并带入自动生成的当前对话摘要；或升级套餐，继续当前对话，让每次聊天都能容纳更多上下文。
> 〔新聊天〕〔升级至 Go〕

这条会话已经装不下下一问了。以前遇到它会有三种坏结果，都发生在用户看不见的地方：

1. 横幅被当成**回答**收下来——`messageCount` 在 ChatGPT 上是 0（站点没有消息钩子），读的是转录尾巴，而横幅就躺在尾巴上；
2. 或者等满 3 分钟，报「没有确认到属于本轮的新回答」，真正的原因（会话满了）反而丢了；
3. 更糟：这一问发出去被站点退回，用户在界面里看到的是「综合中」一直转。

## 现在的处理

| 时机 | 行为 |
| --- | --- |
| 探测到横幅 | `PageProbe.contextFull = true` → `ChannelStatus.contextFull = true`，detail 写「这条会话的上下文已满，下一次提问会先开一条新会话」。通道**仍然算可用**——输入框还在，换会话就能答 |
| 提问前 | 状态里 `contextFull` 为真 → 先 `newConversation()`，再问 |
| 发送后才出现横幅 | `submit` / `waitForAnswer` 立刻抛 `ContextLimitError`，不再确认提交、不再等超时；`PageBrowserAdapter` 换一条会话**重问一次**（只一次） |
| 换会话失败 | 当场失败并说明：会话满了、自动开新会话没成功、请手动点「新对话」。绝不把问题发进那条注定被退回的会话，也不白等 |

成功的回答里 `attribution.note` 会带一句「上下文已满，已自动开新会话后重问」，这是留痕，不是给用户看的提示。

## 怎么认出来

站点文案不是选择器，所以按站点声明（`ProviderProfile.contextLimit`），只有 ChatGPT 填了，因为只有它被实测过：

```ts
contextLimit: ['上下文窗口已达上限', '上下文长度已达上限', 'context window is full', 'context limit reached']
```

探测分两步，为的是不花钱：

1. 先看整段转录里有没有这几个字（一次字符串比较，零成本）；
2. 命中了才逐元素 `innerText` 找它所在的块，且只认**短块**（≤300 字）并且不是消息容器（`[data-message-author-role]`、`article`、`.markdown`、`.prose`）。

短块这一条是必要的：回答正文里完全可以出现这句话（比如让它解释什么叫上下文窗口），而一段正文比一条横幅长得多。

## 真机验证（2026-11-06）

在用户那条上下文已满的 ChatGPT 会话上（`chatgpt.com/c/6aed343d…`）：

- 探测：`contextFull: true`，横幅落在 `footer-A8ZvKV …` 这个短块里（90 字），祖先都超 300 字被挡住，说明长度门槛是有效的；
- 提问前状态：`{"contextFull":true,"detail":"这条会话的上下文已满，下一次提问会先开一条新会话"}`；
- 发一条真问题（「用一句话说明 TCP 为什么需要三次握手」）：自动换到新会话 `chatgpt.com/c/6aed755a…`，**answered**，回答正常；
- 提问后状态 `contextFull: false`；
- 清理：`deleteConversation` 返回 `{cleaned:["chatgpt"], reset:["chatgpt"]}`，会话列表只剩用户自己那条。

## 边界

- **换会话会丢掉站点侧的历史。** 追问「那它呢」这类指代，在新会话里没有上下文可指。这一轮没做「把前几轮拼成一条消息重发」：网页通道只发用户原话是一条硬规则（拼上下文会污染回显剥离，把提问认成回答）。真遇上「追问被重置后答得莫名其妙」，再单独设计。
- 只认已实测的站点文案。Kimi / Gemini / DeepSeek 没实测过，就不填——宁可维持旧行为，也不猜一句可能命中正文的话。
- 横幅是「已满」，不是「快满」。快满时的提示（如果有）不在这一轮里。

## 测试

`scripts/check-adapter.mjs` 新增 5 条：

- 横幅 → 状态报「满」但页面不算坏；
- 横幅 → 等待立刻结束（不到 1 秒），不烧满超时；
- 提问前自动换会话，回答照常返回，`note` 留痕；
- 发送后才出现横幅 → 换会话后重问一次，第二次成功；
- 换不了会话 → 明确失败，问题一个字都不发。

另外把 `PROBE_SCRIPT` 加进了「每个页面脚本都能编译」那条用例——它是拼出来的字符串，转义写坏不会有编译错误。

## 第二轮真机复盘：判定被「草稿」挡住（2026-11-06 15:55 / 15:57 两次失败）

第一次修复上线后，同一条会话又连失败两次，卡片上写的是：

> ChatGPT：页面 chatgpt 不可用：ChatGPT 这条会话的上下文已满，自动开新会话也没成功
> （页面没有清空，仍在原会话里）。在右侧页面点一次「新对话」，再问一次。

而右侧页面**其实已经清空了**，正停在新会话的「我们从哪开始？」，输入框里挂着一句更早
留下的问句（`用表格对比 HTTP 和 HTTPS 的三点区别，最后列两条注意事项。`）。两件事是
同一条因果链：

1. 换会话要证明「页面真的换了」，判据是 `isEmptyNow()`：转录 0 条 + 地址不是原来那条。
2. 应用重启后 `lastThreadUrl` 是空的（这个进程还没答过话），于是走到旧判据的兜底分支：
   「转录 0 条 **且输入框是空的**」。
3. ChatGPT 会把草稿恢复到输入框里——它把「新会话」这个槽位的草稿记在本地，点「新对话」
   的那一刻正好把它放回来。于是页面明明是新会话，判定说「仍在原会话里」。
4. `resetThread()` 如实抛错，这一问从头到尾没有发出去，整场少掉 ChatGPT 的回答。

两次失败都是这个形状，第二次连用户新问题都没机会发：输入框里挂着的还是上一轮的句子。

### 修法

- **判据换成地址**：`threadIdOf(url)` 取路径最后一段（`/c/<uuid>`、`/app/<hex>`、
  `/chat/<uuid>`）。地址里带着会话 id 才算「还在某条会话里」；站点自己的新会话界面
  （根地址、`/app`）不管输入框里挂着什么，都已经是新会话。草稿不是历史。
- **换完会话顺手清一次草稿**：`clearLeftoverDraft()` 在三条成功路径（already-empty /
  click / reload）之后清掉输入框里的残留。它不是历史，挂在框里却像「上一问还留着」，
  用户看到的就是「历史遗留」。
- **失败理由写它看见的东西**：`页面没有清空（/c/…，可见消息 N 条，输入框 M 字）`，
  不再一律说「仍在原会话里」——页面其实清空时，那句话会把人指向已经做过的动作。

### 真机验证（同一台机器，同一条满会话）

- 把 ChatGPT 页面带回那条满会话（横幅「上下文窗口已达上限」在位）后提问；
- 自动点「新对话」→ 新会话 `chatgpt.com/c/6aed8c3d…`，ChatGPT **answered**（46–57 字）；
- 输入框里那句残留被清掉，没有再出现；
- 清理：`deleteConversation` 之后 ChatGPT / Gemini 侧都不再有这条测试会话，两个页面
  回到新会话界面、输入框为空。

## 顺带修掉的一个假失败：Kimi 未登录

同一轮里 Kimi 一直报：

> SEND_UNCONFIRMED：20000ms 内未观察到页面提交迹象…（输入框仍保留 25 字，已尝试：
> click:send, enter, click:retry, …）

真因不是发送，而是**未登录**：页面上盖着 `.login-modal-next-mask`（手机号 + 验证码），
`elementFromPoint` 在发送键中心返回的是这层遮罩，所有点击都被吃掉；登录弹层关掉时，
输入框和发送键仍然在、键还亮着、字也写得进去，点发送依旧什么都不发生——访客不能提问。

所以 `KIMI_PROFILE.signedOut` 现在声明三个现场：`.login-modal-next-mask`、
`button.login-button`、`.next-sidebar-history-list__login`。认出来之后：

- `getChannelStatuses()` 报 `loggedIn:false / available:false`，说明写「Kimi 未登录：
  在右侧这条通道的页面里登录一次」；
- 提问阶段直接拒绝，不再往一个不会应答的页面里写字，也不再烧那 20 秒；
- 汇总卡的系统消息变成「Kimi 未参与提问：Kimi 未登录…」。

**这是如实报告，不是修好了 Kimi。** 它现在确实需要用户手动登录一次；登录之后还是原来的
路径。
