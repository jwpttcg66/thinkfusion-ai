# 工程分析里让模型自己读文件

日期 2026-11-09。用户原话：「读取文件，模型不是应该调用本地能力，没看到调用本地能力，
输出也是糟糕的。」

## 1. 原来错在哪

工程空间的第一手回答是一次 `generate()`：程序先扫工程、切出 8 个证据片段，连同
用户原话一起塞给模型，模型只能对着这几段说话。

真机现场：附一份 `制定辩论主题方案.md` 问「这个文件有多少行」，两个本地模型
（deepseek-r1:14b、gpt-oss:20b）都答「无法确定」，引用的还是无关的
`codex-auth-helper-main/landing-page/index.html:8`。

这不是模型笨，是它**没有工具**：

- 证据是程序按关键词挑的，跟这句话可能一点关系都没有；
- 附件正文有 12000 字上限，被截断的文件**数不出总行数**；
- system 里写着「只依据这些证据回答」，附件被理解成「用户的附注」，直接排除；
- 模型想读整份文件时，没有任何通道。

## 2. 现在的做法

模型可以**请求读一次文件**，宿主真去读，把结果递回去，模型再给结论。

```
用户原话 + 工程证据  ──►  模型
                            │ 需要更多内容时，只回一行：
                            │ {"tool":"fs.stat","args":{"path":"log.txt"}}
                            ▼
                      宿主执行 project.read（只读、范围受限）
                            ▼
       原证据 + 【你请求的本机能力】+【读取结果】 ──► 模型  ──► 结论
```

走**文本协议**而不是各家模型的 function calling：本地 Ollama 上的模型对工具调用
支持参差不齐，而「看不懂就照旧回答」必须是无损的——认不出 JSON 时，这段提示不产生
任何副作用，行为与改之前完全一致。

### 能请求什么

| 能力 | 参数 | 回什么 |
| --- | --- | --- |
| `fs.stat` | `path` | 字节数、**总行数**、sha256 前 12 位、修改时间 |
| `fs.readFile` | `path`、`offset`、`limit` | 先报总行数/字节，再给带行号的指定行段（默认第 1 行起 200 行） |
| `fs.search` | `pattern`（正则）、`path` 可选 | `相对路径:行号: 内容`，最多 40 处 |
| `fs.list` | `path` | 目录内容，最多 200 项 |

`fs.readFile` 永远先给总行数——「有多少行」这类问题不再需要模型自己数，也不会被
截断的正文骗。

## 3. 三道边界

1. **只读。** 没有写、删、改、执行命令。请求名只认这四个（`READ_TOOL_NAMES`），
   `fs.writeFile`、`shell.run` 之类一律不认。
2. **范围硬。** 路径先 `realpath`，再判断是否在「工程目录子树」或「这一问的附件」
   之内，符号链接绕不出去。模型读不到 `~/.ssh`，也读不到 `/etc/hosts`。
3. **有预算。** 一次回答最多额外一轮（`MAX_TOOL_ROUNDS = 1`）。认不出请求 → 零
   额外开销；读失败 → 把原因当结果递回去，让模型改口或如实说读不到；第二轮还在
   请求 → 用它的原文收尾，不再循环。

## 4. 用户看得到

每次真的调用了能力，转录里会多一行：

> Ollama（本地）· r1 调用了本机能力：fs.stat log.txt

没有这一行，就和「凭猜测回答」没有区别——用户没法判断结论到底有没有落在文件上。

## 5. 顺带修的两处

- **附了文件时 system 要说明附件也算依据。** 原来「只依据这些证据回答」会把附件
  排除掉，真机上就是这么把文件里写明的数字否成「无法确定」的。现在按附件数量追加
  一句「用户随这一问附了 N 个文件……同样是可引用的依据」。
- **解析器死循环。** 第一版 `parseToolRequest` 用
  `lastIndexOf('{', cursor - 1)` 往前退，`cursor` 到 0 时负数被钳成 0，原地打转；
  一句「共 {3} 行」就能把进程吊死。现在按括号深度配平切片（跳过字符串内的括号），
  到头就 `break`。这条是测试自己抓出来的。

## 6. 测试

```
npm run test:engineering-tools   # 12 条
```

覆盖：认请求（正常回答/花括号/非白名单一律不认）、`fs.stat` 报整份行数、
`fs.readFile` 带行号且先报总数、`fs.search`/`fs.list`、工程目录之外读不到、
附件在目录之外但允许读、链路闭合（请求→真读→结果进第二问→结论→转录里有记录）、
预算用完不再循环、正常回答零额外调用、`project.read` 已登记进 `CAPABILITY_CATALOG`。

## 7. 已知代价

1. 请求了一次读文件的成员会**多等一轮推理**（本地 14B 约 10–30 秒）。
2. 模型可能请求一个不存在的路径——回的是「读不到」而不是报错，回答里会写清楚。
3. 只覆盖工程空间的**第一手**。汇总 / 交锋 / 最终意见仍然只吃材料和各家回答，
   没有工具；要给主导人也配上，是下一步的事。
4. 大文件（> 64MB）只回统计，不回正文。
