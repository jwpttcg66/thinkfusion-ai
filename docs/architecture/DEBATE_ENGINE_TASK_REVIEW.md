# 任务书审计（文档本身）

对象：`docs/spec/DEBATE_ENGINE_TASK_V1.0.md`（原文 docx 同目录）。
目的：在动手前先把这份文档**当成契约读一遍**——哪些条款可判定、哪些与本仓库
现实对不上、哪些地方文档自己没说清。仓库侧的映射见
`DEBATE_ENGINE_AUDIT.md`，两份不重复：那份回答「落在哪个文件」，这份回答
「这句话到底要求什么、能不能照做」。

结论先说：**这份文档可以当契约用，但不能逐条照抄。** 它的价值在 15 条验收
标准（AC-01~AC-15）和 10 条回归场景——都能判定真假；它的风险在假设了一个
「有服务端、有检索、有预算统计」的系统，而这是个单机 Electron 应用。

## 1. 可以当契约的部分

| 条款 | 为什么可判定 |
| --- | --- |
| AC-01~AC-15 | 每条都是一个能写成断言的状态，不是「体验更好」这类形容词 |
| §14.2 TF-D-001~010 | 给了具体场景与期望结果，能直接改写成测试用例 |
| §5 / §5.1 数据结构与枚举 | 字段和取值都列了，能对着写类型 |
| §6.1 主流程十二步 | 有顺序、有输入输出，能拆成函数 |
| §6.4 停止条件 | 明确列出「什么时候可以停」，没有留「看情况」 |

三条红线值得单独记：**不用票数判真伪**（§1.2 / AC-12）、**允许 inconclusive**
（AC-13）、**结论必须可追溯到 Claim 与 Evidence**（AC-09）。这三条决定了很多
设计取舍，后面任何简化都不能碰它们。

## 2. 文档假设 vs 本仓库现实

这六处不是文档写错了，是它没有（也不可能）对这份代码做审计。照做之前必须换算。

| 文档假设 | 本仓库现实 | 处理 |
| --- | --- | --- |
| §9 用表/集合 + 迁移，`debate_*` 十几张表 | 没有数据库。`AgentStore` 是一个 JSON，辩论是每场一个 JSON 文件 | 一个 `DebateState` 对象承载全部实体；不分表 |
| §12 提示词放 `prompts/debate/*.md` | 提示词是 TypeScript 字符串常量（`lead-stage.ts`、`judge/engine.ts`、`orchestrator.instructions()`） | 不改成 md。理由：md 要读文件、处理路径、打包，收益是零 |
| §7.3 / AC-09 要求证据带 URL、定位、抓取时间、内容指纹 | 页面驱动只取 `innerText`；`href` 只用于侧栏历史行，从没读过回答里的引用锚点 | **真缺口**。要做得先扩页面提取，见 §5 待拍板 |
| §10 预算含 Token 与费用 | 没有任何 token 计数；本地 Ollama 与网页通道都拿不到用量 | 只做时间预算与轮数预算，Token/费用不假装有 |
| §7.1 裁判应独立于被裁判者 | 单机常常只有 1 个本地模型 + 网页通道 | 允许兼任，但 `JudgeVerdict.sharedWith` 写明；规则版标 `backend: 'rules'` |
| §14.2 的 10 个回归场景要有确定结果 | 答案来自真模型，同样输入不保证同样输出 | 回归只能做成「固定回放」：把一次真实发言录成 fixture，断言结构而不是断言结论 |

## 3. 文档内部需要澄清的六处

1. **AC-02「首轮隔离」与 §6.1「共同上下文」冲突吗？**
   §5 的 `DebateSession.question` 之外，§6.1 说每个参与者「只看到原始问题和
   **共同上下文**」。共同上下文包含什么，文档没定义。本仓库里会话内辩论的第一轮
   会看到网页回答（`DebateConfig.seed`）——按「基准材料」理解不违反隔离，
   按「其他参与者的首轮答案」理解就违反。**需要你拍板**（见 §5）。
2. **两个 `confidence` 不是一个东西。**
   §5 的 `DebateClaim.confidence` 是「这条主张有多可信」，§7 的裁判置信度是
   「这个判断有多可信」。同名不同义，很容易在实现时被当成一个字段复用。
3. **ClaimStatus 由谁判定？**
   §5.1 给了 `supported / challenged / revised / withdrawn / unresolved`，
   但没写「谁把它从 proposed 改成 supported」——裁判？对方？还是提出者自己？
   本版只用到 `proposed / challenged`（后者＝卷进了争议），把判定留给 Phase 3
   的裁判，避免自己发明规则。
4. **AC-04 要四类争议，§5.1 却给了七类。**
   AC-04 只要求「直接矛盾、定义差异、范围差异、证据冲突」四类；枚举里还有
   `causal / assumption`（第七类 `definitional` 在 AC 里叫「定义差异」）。
   本版实现三类（factual / scope / evidence_conflict），`definitional` 规则判不了，
   不放进类型里充数。缺的几类得有模型参与才做得出来。
5. **停止条件有两条互斥路径。**
   §6.4 说「争议收敛就停」，§10 说「最多 3 轮」。两条同时满足时谁优先、要不要
   留一轮收尾，文档没写。本仓库现有实现是：收敛即停，否则打满轮数。
6. **事件流的阶段顺序不一致。**
   §9 把 `debate_events`（幂等、可恢复）写成基础能力，§15 却把它放在 Phase 2
   之后。没有事件流，Phase 2 的「修订记录」只能靠整份快照对比——本仓库现在就是
   这样（整份覆盖写）。

## 4. 建议的实施顺序（与文档 Phase 不完全一致）

文档的六阶段是对的，但 Phase 2 里混了三件成本差很多的事。建议按这个顺序拆：

| 顺序 | 内容 | 对应条款 | 理由 |
| --- | --- | --- | --- |
| ✅ Phase 1 | 主张抽取、争议检测、挑战指向具体两句 | AC-03/04/05 | 已完成，见 `docs/implementation/PHASE-1-DEBATE-CLAIMS.md` |
| Phase 2a | 会话内辩论可选策略与轮数（现在写死 standard/2） | AC-01 | 一行配置的事，先让策略真的能选 |
| Phase 2b | 修订决策 `accept/defend/revise/withdraw/inconclusive` | AC-06 | 要在发言上再加一层，得先有 2a 的轮次控制 |
| Phase 2c | 轻量事件流（每轮追加，不重写整份） | AC-14 | 需要先定「哪些事件值得记」，否则记一堆没人读的日志 |
| Phase 3 | 裁判三维（逻辑/证据/反例）+ 五档 verdict | AC-11/12/13 | 依赖 Phase 1 的 claim，否则裁判只能对着整段话打分 |
| Phase 4 | 界面：策略选择、主张与证据链展示 | AC-01 的 UI 部分、§13 | 结构没稳定前先做界面，改一次画一次 |
| Phase 5 | TF-D 回归（固定回放） | AC-15 | 要有稳定的结构字段才写得出断言 |

**明确不做**（本版）：Token/费用预算（没有数据来源）、证据检索与同源识别
（没有检索能力，见 §5）、定义差异检测（规则判不了）。

## 5. 需要你拍板的三件事

1. **首轮喂网页回答算不算破坏隔离？**
   现在会话内辩论的第一轮会把网页回答当基准材料递给辩手。按「基线材料」不算，
   按「其他参与者的首轮答案」就算。我按「不算」实现，并在类型注释里写明。
2. **要不要为 AC-09 去做引用链接抓取？**
   要做的话改的是页面驱动：从回答气泡里取 `<a href>` 与引用编号，落成
   `{url, fetchedAt, fingerprint}`。风险中等（三家页面结构都不一样，可能要各写
   一套选择器），收益是「证据可追溯」从口号变成字段。
3. **TF-D 回归接受「固定回放」吗？**
   真模型不可重复，只能录一次发言再回放。接受的话 Phase 5 才有意义；不接受，
   这 10 条就只能当人工检查清单。

## 6. 结论

- 文档的**验收标准**可以直接当开发清单；**架构图与目录**只能当参考。
- 它缺的不是想法，是「在没有服务端、没有检索、没有 token 计量的环境里怎么落地」
  这一层；本仓库的审计补的就是这一层。
- 按 §4 的顺序推进，每阶段一个提交、一次测试、一份 `docs/implementation/PHASE-*.md`，
  与仓库现有 Phase B~J 的文档习惯保持一致。
