## 1. 定位：真正的工程环境，不是工程辩论

工程空间不是一个「围绕代码辩一场」的流程，而是一个能持续工作的环境：

- 先**读懂**：代码在哪、调用关系是什么、改动会影响什么；
- 再**设计**：方案、取舍、测试策略；
- 然后**改动**：在受控的工作区里改代码、跑测试；
- 最后**验证与评审**：真实执行结果、独立评审、可回退。

辩论可以在工程空间里发生（例如方案评审、争议后的交叉审查），但它是**按需行为**，
不是开场白，也不是交付物。

## 2. 能力地图

| 能力 | 现有基础 | 目标 |
| --- | --- | --- |
| 工程理解 | `engineering/project.ts` 读盘、`engineering/analysis.ts` 符号/调用/依赖 | 结论带 `路径:行号`，识别方法可解释 |
| 代码搜索 | `fs.search` / `fs.find` / `fs.tree` | 模型驱动的按需搜索，不预建全量语义索引 |
| 源码读取 | `fs.readFile` 分页 + 行号 | 大文件可控读取，不整段塞给模型 |
| 架构分析 | 模块依赖、入口、变更影响 | 影响面与风险清单 |
| 技术方案 | 计划 + 方案评审 | 方案带取舍、测试策略与回退 |
| CLI Agent 协作 | `cli-agents.ts`、Qoder / Claude | 作为参与者接入统一能力模型 |
| 代码修改 | `fs.edit` / `fs.writeFile` / `fs.move` | worktree 隔离，按任务分工作区 |
| 测试验证 | `test.run`、`ExecutionReport` | 执行断言进入证据包 |
| 独立评审 | `engineering/review.ts`、`plan-review.ts` | 评审者不跟实现者绑定 |
| Git / Worktree | `test:worktree` 等 | 分支、提交、diff、快照、回滚是一等能力 |

## 3. 任务生命周期

```
Intake → Understand → Evidence → Plan → Approve → Execute → Verify → Review → Deliver
```

| 阶段 | 做什么 | 产物 | 失败处理 |
| --- | --- | --- | --- |
| Intake | 确认目标、仓库、范围、权限 | `EngineeringTask` | 目录/权限不明先问 |
| Understand | 搜索、读取、符号、依赖、影响面 | 事实清单（带位置） | 读不到就停，不猜 |
| Evidence | 冻结代码事实与仓库状态 | `EvidenceRef[]`（code） | 记录不可用原因 |
| Plan | 方案、步骤、测试策略、回退 | 执行计划 | 计划不过评审就修，不硬跑 |
| Approve | 人确认计划与权限 | 审批记录 | 拒绝即停 |
| Execute | 在 worktree 内改动、跑测试 | diff + `ExecutionReport` | 失败按步回滚或停 |
| Verify | 关键结论绑定真实执行 | attestation / verdict | 未跑过的测试标未验证 |
| Review | 独立评审改动与风险 | 评审结论 | 意见回到计划 |
| Deliver | 改动、diff、测试、风险、回退 | 交付包 | 缺证据项显式列出 |

## 4. 任务状态与证据：不是「辩论基线」

工程任务需要一个明确的**前后状态**，但这属于工程任务的状态管理，不属于辩论：

`EngineeringTaskState` 的唯一权威定义见 [ENGINEERING_CONTRACT §1](ENGINEERING_CONTRACT.md)；
本节不重复字段。

原则：

- 状态由**工程任务**创建和持有，任何协作行为（包括辩论）只能引用，不能代替它创建；
- 快照、diff、测试报告、执行断言都进入统一证据层，带哈希与时间；
- 「工作区脏」「测试没跑」「权限不够」必须显式记录，不能作为沉默前提。

## 5. 动态分工，而不是固定角色

| 角色 | 职责 | 由谁担任 |
| --- | --- | --- |
| Explorer | 搜索、读取、建立事实清单 | 有读工具的模型 / CLI Agent |
| Designer | 方案、取舍、测试策略 | 强推理模型 |
| Implementer | 在 worktree 内改代码 | 有写工具的执行者 |
| Verifier | 跑测试、核对断言 | 执行运行时 / 独立 Agent |
| Reviewer | 独立评审改动与风险 | 不参与实现的模型 |

角色是任务属性：同一个模型可以在理解阶段做 Explorer、在评审阶段做 Reviewer。
引擎按能力、上下文与独立性要求分配，不预先写死「谁是辩手、谁是裁判」。

## 6. Agentic Search 与代码智能

原则：**工具提供事实，模型负责理解。**

- 不做覆盖所有语言的完整语义引擎；优先做轻量索引 + 按需工具：
  搜索、读取、符号、引用、定义跳转、诊断；
- 索引可以增量、可以降级；降级时明确说「按文本搜索，不是语义结果」；
- LSP / Tree-sitter 作为可选事实源，不可用时退回文本搜索，不假装有语义；
- 模型决定下一步读哪里，而不是系统一次性把仓库灌进上下文。

---

## 7. CLI Agent 协作

CLI Agent（Qoder / Claude 等）是工程空间的一等参与者，但不是「另一个 Runtime」：

- 能力描述：可读写文件、可跑命令、可访问网络、并发上限；
- 每个 CLI Agent 的任务在自己的 worktree / 分支内执行，不共享工作区；
- 输出归一化成 `Observation` 与 `EvidenceRef`，进入同一套证据；
- 失败、超时、权限拒绝都显式记录，不静默换人重跑。

---

## 8. Git 与 Worktree 管理

- 一个任务一个 worktree / 分支；并发任务不共享目录（与 AGENTS.md 第 5 条一致）；
- 合并前必须验证：相关测试、typecheck、已合入功能不回归；
- diff、快照、回滚是产品能力：用户能看见改了什么，也能退回去；
- 不自动 push；推送由用户执行。

---

## 9. 安全与治理

| 边界 | 规则 |
| --- | --- |
| 只读优先 | 理解阶段不产生写操作 |
| 授权 | 计划必须人审批；TaskGrant 有范围与期限 |
| 执行 | 独立 Runtime；每步重新校验授权 |
| 工具 | 白名单；写入默认进废纸篓；不可回收操作需完全权限 |
| 证据 | 执行断言进 Item Hash；篡改可发现 |
| 回退 | 快照 + diff + 回滚路径随交付物给出 |

---

## 10. 交付物

- 工程分析：事实、位置、影响面、识别方法；
- 改动方案：步骤、取舍、测试策略、回退；
- 代码改动：diff、提交、worktree 信息；
- 测试报告：命令、退出码、断言、失败项；
- 评审结论：风险、阻断项、建议。

每个「已修复 / 已通过」都必须能追到执行断言；没有证据的结论标为「未验证」。

## 12. 判据

- 对一次改动，能回答：改了哪些文件、为什么、影响面多大、哪条测试证明、失败怎么回退；
- 只读分析不产生写操作；写入必须先有计划与审批；
- 「已通过」必须带执行断言，伪造或篡改能被发现；
- 并发任务各有 worktree，合并前验证通过；
- 关掉辩论，工程空间仍能完成理解、改动与验证。

---

## 13. 不做什么

- 不在工程任务开场强制创建「辩论基线」；
- 不把工程任务套进固定的「分析 → 质疑 → 修订 → 裁判」提示词次序；
- 不为工程任务新建第二套审批、Runtime 或证据格式；
- 不追求「本地语义引擎覆盖所有语言」；模型 + 工具优先；
- 不自动合并、不自动 push、不做无授权的破坏性操作。
