## 4. 真机发现的问题与修复

### 4.1 Kimi 排队提示弹层吃掉发送点击

- 现象：三家都问了，只有两家回答；Kimi 白等 180 秒报 `ANSWER_TIMEOUT`，理由里完全没提弹层。
- 真因：页面弹出 `.modal-mask` + `.modal-container`，正文「和Kimi聊天的人太多了，订阅会员可进入优先队列」，输入框仍能写字、发送键仍亮，点击被遮罩吃掉。
- 修复：`ProviderProfile` 新增 `dismissText`，Kimi 声明 `['我知道了']`；写输入框和点发送前，在「有可见 modal/mask/dialog + 控件可见 + 文案逐字相等」三重条件下点掉它。绝不点「去升级」，不把用户带进付费流程。

### 4.2 站点把页面转到付费墙时的错误理由误导

- 现象：修掉弹层后仍失败，理由变成 `SEND_UNCONFIRMED（输入框仍保留 35 字）`；实际页面已被站点转到 `https://www.kimi.com/membership/pricing?from=paywall_unknown`。
- 修复：`ProviderProfile` 新增 `blockedPaths`，Kimi 声明 `['/membership/pricing']`；`getStatus()` 与 `submit()` 都识别该路径，一旦命中立即停，并说明「站点把页面转到了会员/排队页面……这不是登录失效，是站点账号侧的限制」。
- 同时给 `SEND_UNCONFIRMED` 补上「页面地址」，以后再出现同类问题，理由本身就能指出页面去了哪里。

### 4.3 按用户授权更换网页源

Kimi 连续三轮被站点推到付费墙（登录态正常，账号侧限流），不是应用能绕开的。按用户指示「可以更换网页源」：

- 启用 DeepSeek 网页源（原本禁用），实测已登录、页面就绪、可正常回答；
- 暂时关闭 Kimi 通道，避免每一问都白等 20 秒；
- 换源后知识问答耗时从 92～300 秒降到 24 秒。

Kimi 恢复后，在通道列表里重新打开即可，代码侧的识别与关闭逻辑都保留。

### 4.4 `listDebates()` 会把 CDP 连接打断（未修，记录在案）

通过 CDP 调 `window.agentAPI.listDebates()` 时，WebSocket 立即被关闭（应用与页面都还在，其他调用正常）。怀疑是返回体过大导致 `Runtime.evaluate` 传输被中断。本轮的辩论验证改用 `synthesis.fusion.debateId` 与系统消息取证，不再依赖该调用。**这是一个待查项**，不影响用户路径（界面不调用它）。

### 7.1 这一轮真机抓到的三个真问题（都已修）

**① 结构分析算完就丢了（Phase E 形同虚设）**
s13 第一轮：证据 6 条正常，但递给主导人的材料里**没有** `【结构概览】/【调用点】`。
根因：`scanProject()` 算了 `analysis`，`Conversation` 只存 `evidence`，
`engineeringMaterialFor()` 用存的证据重建材料时把 analysis 丢了。修法：会话新增
`engineeringAnalysis`，材料拼接带上它。修后 s13 10/10，材料里能看到
`【调用点】connectionPool → src/service.ts:4`。**这条正是「真机才算数」的价值：单测
全绿，能力却没有到达模型。**

**② 一个占位符让整个任务当场死亡**
s14 第一轮：模型在同一份计划里给 `expectedHash` 填了「读取后回填」，schema 拒绝，
用户看到的是 `[{"validation":"regex","path":["steps",1,"args","expectedHash"]}]`，任务直接失败。
修法三层：
- 提示词写明「改已有文件要分两轮：这一轮只读，下一轮再写」，并警告不要填占位值；
- `describePlanIssues()` 把 zod 路径翻成「覆盖已有文件必须带 64 位十六进制的 sha256…
  先只输出 fs.readFile 计划，下一轮拿到 sha256 再写」；
- 新增 `repairPlan()`：失败原因交回模型自修，最多 2 次（`inputType: 'plan_repair'`）。
真机验证：修后第一轮仍给了不合法计划，但**自修一轮就拿到可执行计划**，任务继续。

**③ 站点人机验证被当成「回答」**
s14 后续几轮：DeepSeek 在连续提问后弹出「点击图中最小的蓝色三棱柱」，输入框照样能写、
发送键照样亮；点下去页面把**题目本身**当回答吐回来（17 个字），应用报「回答中没有找到
协议块」，然后 20 秒超时，用户完全看不出原因。
修法：`ProviderProfile.challengeText`（DeepSeek / ChatGPT 各声明自己的短语），探测阶段
认出来就判「这一页现在问不了」，`getStatus()` 与 `sendMessage()` 都立刻停，理由写明
「请在右侧页面手动完成一次验证，应用不会代替你通过验证；这不是登录失效」。
**不做代答**：既不可靠，也不该做。真机确认：验证消失后通道恢复可用，s14 最终 10/10。

### 9.3 环境事故与顺带修掉的缺陷

- 证据排序：点名文件固定排第一位；`EngineeringEvidence` 新增可选 `totalLines` / `partial`。
- `engineeringMaterial()`：证据头部带上「全文共 N 行 / 只读了前 256 KB」，并独立成段
  写【点名文件统计】——真机第二轮证明统计埋在括号里时 14b 的主导人接不住，
