## 轮询与等待

`DEFAULT_TUNING.pollMs = 400`（原来 700）。答案一停就返回的快路径来自
Phase B 之前的性能修复：同一句问题末答由 13.7s 降到 9.8s、开始提问由
4.3s 降到 3.7s。本轮没有重复基准，沿用那次的实测结论。

Phase K 的 Hybrid 真机（4 个来源：1 本地 + 3 网页）一轮达到 `answered`，
但脚本没有记录端到端耗时，**不写具体毫秒数**。

## 写盘

- 主 journal `agent-store.json` 仍是每次 mutation 全量 `JSON.stringify` +
  临时文件 + `fsync` + `rename`。数据少时没问题，**没有做大文件基准测试**。
- 辩论与裁决改为每场一个独立文件（`debates/`、`verdicts/`），避免一轮 N 条
  发言把整个 journal 反复重写。这是结构上的规避，不是测出来的提速。
- 融合引擎、协作记录都在内存里算，不额外写盘。

## 已知瓶颈（未解决）

1. 主 journal 全量重写：会话变多后写盘成本线性增长。按天分文件或
   append-only 方案在计划里，未实施。
2. `page-driver.ts` 2579 行，选择器脚本 + CDP 操作混在一起，冷路径上手慢。
3. 短答案（纯数字）会被观点抽取的 12 字门槛全过滤，综合降级；这是正确性
   优先的取舍，不是性能问题，但会让纯计算类问题看不到「一致结论」。
4. 云端链路无 Key，流式延迟、429 退避、重试耗时**未真机测量**。
