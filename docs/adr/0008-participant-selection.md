# ADR 0008：参与者数量由任务决定

- 状态：Accepted
- 日期：2026-11-18
- 决策者：用户
- 相关：`AGENTS.md` 第 2 条、[协作架构](../architecture/COLLABORATION_ARCHITECTURE.md) §5.1

## 背景

`AGENTS.md` 第 2 条原先要求「所有已开启且可用的通道都要被问」。它修的是一个真实问题：
早期代码用 `isMultiChannel` + `usable.slice(0, 1)` 只问一个，界面却写着「单通道，只问 Gemini」，
用户看不到系统替他减少了视角。

但固定「全问」也有代价：简单事实问题要等最慢的通道，工程任务让网页模型陪跑，
模型多时延迟与成本不可控。

## 决策

参与者数量由 Planner 根据任务决定，但先受调用范围约束：

- 本地模式只调用本地模型；远端模式只调用远端模型；只有混合模式可同时使用两者。
- 网页是页面渠道，不是模型；是否参与由任务决定，不因混合自动加入。


- 简单事实或单点核对可以只用一个；
- 有争议、高风险、或用户明确要求多视角时，至少两个；
- 每次选择必须给出理由；被跳过的通道与原因对用户可见；
- 不得以「省成本」为唯一理由静默少问；
- 网页通道只收问题与数据；知识/通用可提问，工程只回答（见 ADR 0009）；
- 保留一个用户可开的「始终询问所有通道」开关，作为逃生口；它是 UI 层覆盖，
  不进入 `Policy`，也不改变 `modelScope`。

## 后果

正面：

- 简单问题更快、更便宜；
- 工程任务不必让网页模型陪跑；
- 选择本身成为可解释的产品行为。

负面与风险：

- 产品主张从「默认多视角」变成「按需多视角」；
- Planner 判断错误时，用户可能只得到一个视角；
- 需要 UI 展示理由、测试覆盖「高风险不单点」、以及可回退开关。

缓解：

- 风险下限：争议/高风险/多视角要求禁止降到 1 个；
- 用户可强制全问；
- 计划里记录选择理由，shadow 阶段观察选人是否合理；
- 数据与文档保留历史教训，避免退回「静默少问」。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 永远全问 | 简单问题成本与延迟不可控；工程任务浪费网页通道 |
| 全局配置「只问 N 个」 | 与任务无关，仍然是拍脑袋 |
| 只按能力过滤 | 不能回答「为什么不是其他通道」 |
