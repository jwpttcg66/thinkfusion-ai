# 第一部分：产品总目标与定位

## 1.1 唯一产品总目标

ThinkFusion 的唯一产品总目标是：

**帮助用户开发出自己想要制造的系统。**

用户可以通过自然语言、参考产品、需求文档、现有工程或其他方式表达自己的想法。

ThinkFusion 负责理解用户想制造什么，分析需求和工程现状，设计实现方案，组织开发任务，持续执行工程工作，验证实际结果，并最终交付符合用户预期的软件系统。

ThinkFusion 不只是代码生成工具、模型调用平台或一次性 Agent 执行器。

它是一个能够长期承担软件开发目标、持续组织工程活动、管理完整开发生命周期并最终交付软件系统的产品。

## 1.2 产品定位

ThinkFusion 是一个：

**用户目标驱动、持续运行、自主组织工程活动的软件开发系统。**

系统面向不同软件制造需求，包括但不限于：

- Web 网站和 Web 应用。
- 桌面软件。
- 移动应用。
- Java 后端服务。
- 企业管理系统。
- 数据处理系统。
- AI 应用和智能 Agent。
- 开发工具和平台。
- 现有软件系统改造。
- 大型复杂软件工程项目。

不限制用户希望制造的软件系统类型。

不要求用户必须具备专业的软件工程知识。

系统根据目标规模、复杂度、工程现状和用户授权，动态决定需要开展的工作。

## 1.3 产品核心价值

ThinkFusion 必须帮助用户完成从想法到实际软件系统的转化：

1. 将用户想法转化为可理解的需求。
2. 将需求转化为可实施的系统方案。
3. 将系统方案转化为工程任务。
4. 将工程任务转化为实际代码和工程成果。
5. 将开发成果转化为经过验证的软件系统。
6. 将验证结果转化为用户能够验收的交付物。

系统不能只停留在需求分析、架构设计或代码生成阶段。

必须具备从理解目标到实际交付的完整工程闭环。

## 1.4 产品成功标准

ThinkFusion 的成功不以 Agent 数量、模型数量、工具数量或架构模块数量衡量。

核心成功标准是：

用户提出一个软件制造目标后，ThinkFusion 能够理解目标、形成方案、组织工程任务、持续执行、处理失败、恢复进度、验证结果，并最终交付符合用户预期的软件系统。

# 第二部分：产品基本原则

## 2.1 用户目标优先

用户目标是系统所有工作的最终依据。

系统可以自主决定实现方法，但不能擅自改变用户希望制造的系统。

所有需求分析、技术决策、任务分解、执行和验证，都必须能够追溯到用户目标或经过授权的工程需要。

## 2.2 持续工程原则

ThinkFusion 必须能够长期承担一个软件开发目标。

工程任务可以持续数小时、数天甚至更长时间。

系统不能依赖单次模型请求、单个 Agent 进程或单次对话完成全部工作。

## 2.3 动态工作原则

工程工作不采用僵化的固定流水线。

系统根据任务情况动态选择：

- 理解。
- 分析。
- 设计。
- 规划。
- 开发。
- 测试。
- 验证。
- 修复。
- 重新设计。
- 重新规划。
- 交付。

简单任务可以快速完成。

复杂任务可以反复进入分析、设计、执行和验证循环。

## 2.4 Native-First 原则

ThinkFusion 必须具备自身的软件工程基础能力。

即使不安装外部 Agent，也应能够独立完成基础软件开发任务。

Native 能力是产品的基础，不是可有可无的备用方案。

## 2.5 External-Enhanced 原则

外部模型、Agent、插件和专业工具用于增强 ThinkFusion 的能力。

External 不得成为系统运行的必要前提。

Native 和 External 必须服从统一的目标管理、任务管理、权限治理、执行记录和验证体系。

## 2.6 真实结果原则

模型报告成功不代表工程成功。

代码修改成功不代表功能正确。

单个任务完成不代表整个系统完成。

必须依据真实工程状态、执行记录和验证证据判断工作结果。

## 2.7 用户控制原则

用户始终拥有：

- 目标决定权。
- 需求变更权。
- 重要设计确认权。
- 授权决定权。
- 暂停和取消权。
- 最终验收权。

系统的自主决策必须处于用户授权范围内。

## 2.8 架构适度原则

所有架构模块都必须服务于软件制造目标。

不为了概念完整而增加独立引擎。

不为了多模型协作而引入不必要的流程。

不为了长期演进而提前建设没有实际使用需求的复杂基础设施。

优先采用职责清晰、边界明确、可以逐步实现的模块化架构。

# 第三部分：核心工程能力

ThinkFusion 只设置六项核心工程能力。

这些能力是软件制造过程中需要具备的基本能力，不是六个独立 Agent，也不是六个固定执行阶段。

## 3.1 理解能力

负责理解用户需求和实际工程。

包括：

- 用户意图理解。
- 需求提取。
- 需求关联。
- 项目结构理解。
- 代码理解。
- 文档理解。
- 技术栈识别。
- 依赖关系理解。
- 运行环境理解。
- 工程现状识别。
- 已有成果识别。
- 理解盲区识别。

理解能力必须区分：

- 已经确认的事实。
- 从工程中采集的事实。
- 模型推断的结论。
- 尚未确认的信息。
- 需要进一步调查的问题。

不能把模型推测当成已经理解的工程事实。

## 3.2 分析能力

负责判断用户目标和当前工程情况。

包括：

- 需求完整性分析。
- 需求冲突分析。
- 技术可行性分析。
- 工程现状分析。
- 问题原因分析。
- 技术风险分析。
- 方案对比。
- 影响范围分析。
- 实施成本分析。
- 任务完成差距分析。

分析结果应能够支持后续设计和决策。

## 3.3 设计能力

负责形成满足用户目标的系统方案。

包括：

- 产品功能设计。
- 系统架构设计。
- 模块设计。
- 数据模型设计。
- 接口设计。
- 用户交互设计。
- 技术选型。
- 安全设计。
- 性能设计。
- 可维护性设计。
- 测试策略设计。

设计结果必须考虑实际实施条件，不能只产生无法落地的理论方案。

## 3.4 规划能力

负责把系统目标转化为可执行工程任务。

包括：

- 任务分解。
- 任务依赖。
- 任务优先级。
- 并行规划。
- 执行顺序。
- 资源预算。
- 风险控制。
- 验收条件。
- 任务调整。
- 动态重规划。

任务规划必须支持随着工程状态变化而调整。

## 3.5 开发能力

负责真正完成软件工程工作。

包括：

- 文件读取和修改。
- 代码搜索。
- 代码编写。
- 代码重构。
- 工程配置。
- Shell 命令执行。
- Git 操作。
- 项目构建。
- 依赖管理。
- 数据库操作。
- 测试执行。
- 模块集成。
- 问题修复。

开发能力必须能够通过 Native Engine 独立完成基础工程任务，并能够调用 External 能力增强复杂任务执行。

## 3.6 验证能力

负责确认工程结果是否满足要求。

包括：

- 代码验证。
- 编译验证。
- 单元测试。
- 集成测试。
- 系统测试。
- 接口验证。
- 运行验证。
- 用户界面验证。
- 数据正确性验证。
- 安全性检查。
- 需求覆盖检查。
- 最终验收。

验证能力必须能够产生可追溯证据。

# 第四部分：核心业务对象与数据关系

为了支持长期工程工作，必须统一业务对象。

核心对象包括：

- Goal
- Project
- Requirement
- Task
- Execution
- Evidence
- Decision
- Event
- Checkpoint

这些对象必须有明确的定义和生命周期。

## 4.1 Goal：用户目标

Goal 表示用户希望最终实现的结果。

例如：

开发一个包含用户管理、组织架构、权限管理、审批流程和报表功能的企业管理系统。

Goal 至少包含：

- goalId。
- 用户目标描述。
- 目标类型。
- 目标状态。
- 目标优先级。
- 需求集合。
- 验收条件。
- 用户约束。
- 目标版本。
- 创建时间。
- 更新时间。
- 当前工程进度。
- 未完成事项。
- 关联项目。

Goal 是长期对象。

Goal 不依赖单次对话或模型会话存在。

用户改变目标时，应通过目标版本和变更记录保存变化。

## 4.2 Project：工程项目

Project 表示实际的软件工程载体。

包含：

- 项目标识。
- 项目名称。
- 工程根目录。
- 代码仓库信息。
- 技术栈。
- 项目结构。
- 构建方式。
- 测试方式。
- 运行环境。
- 工程索引。
- 当前工程版本。
- 工作区状态。

Project 与 Goal 通过明确的关联关系连接。

一个 Goal 可以涉及多个工程项目。

一个 Project 也可能在不同时间服务于多个目标。

必须明确关联关系和项目修改范围，不能将所有项目文件变更都自动归属于当前 Goal。

## 4.3 Requirement：需求

Requirement 表示用户希望系统具备的具体能力或约束。

分为：

- 功能需求。
- 非功能需求。
- 性能要求。
- 安全要求。
- 兼容性要求。
- 用户体验要求。
- 工程约束。
- 交付要求。

每项需求应具有：

- requirementId。
- 所属 Goal。
- 需求描述。
- 优先级。
- 来源。
- 状态。
- 验收条件。
- 关联 Task。
- 变更历史。

需求不能只保存在模型上下文中。

## 4.4 Task：工程任务

Task 表示为了完成 Goal 而需要执行的工程工作。

例如：

- 分析现有项目。
- 设计数据库。
- 建立后端基础架构。
- 实现用户管理。
- 实现权限管理。
- 开发前端页面。
- 完成集成测试。

Task 必须支持：

- 父子关系。
- 前置依赖。
- 并行关系。
- 阻塞关系。
- 任务拆分。
- 任务合并。
- 任务替代。
- 任务取消。
- 任务重试。
- 任务重新规划。
- 验收条件。
- 任务负责人或执行能力分配。

任务关系必须采用支持 DAG 的模型，而不是仅依赖简单树结构。

任务图必须防止循环依赖。

## 4.5 Execution：执行实例

Execution 表示一个 Task 的一次实际执行尝试。

一个 Task 可以有多个 Execution。

例如：

Task：实现权限管理。

Execution 1：代码实现失败。

Execution 2：修复代码并通过单元测试。

Execution 3：进行集成验证。

Execution 至少记录：

- executionId。
- taskId。
- 执行器类型。
- 模型或 Agent。
- 执行状态。
- 开始和结束时间。
- 执行输入。
- 执行输出。
- 工具调用记录。
- 资源消耗。
- 错误信息。
- 取消信息。
- 相关证据。

Execution 正常结束不代表 Task 自动完成。

## 4.6 Evidence：工程证据

Evidence 用于证明实际工程工作和验证结果。

包括：

- 工程文件变化。
- Git 差异。
- 编译结果。
- 测试报告。
- 运行日志。
- 接口响应。
- 系统截图。
- 静态分析结果。
- 用户确认。
- 其他可追溯验证结果。

Evidence 必须记录：

- 证据来源。
- 证据类型。
- 关联 Goal、Requirement、Task 或 Execution。
- 采集时间。
- 对应工程版本。
- 验证范围。
- 结果。
- 有效性。

必须区分原始来源、采集事实、解析结果、模型推断和验证结论。

## 4.7 Decision：工程决策

记录影响工程方向的重要决定。

包括：

- 需求决策。
- 技术选型。
- 架构设计决定。
- 任务调整。
- 模型选择。
- 风险处理。
- 用户批准。
- 目标变更。

Decision 必须记录决策原因、依据、影响范围、提出者和确认状态。

## 4.8 Event：事件

Event 记录工程运行过程中的状态变化。

例如：

- GoalCreated。
- RequirementUpdated。
- TaskCreated。
- TaskStarted。
- ExecutionStarted。
- ExecutionFailed。
- CheckpointCreated。
- VerificationPassed。
- UserApprovalReceived。
- GoalCompleted。

事件记录用于审计、恢复、UI 轨迹和状态重建。

## 4.9 Checkpoint：检查点

Checkpoint 表示可以用于恢复工程工作的状态快照。

必须能够关联：

- Goal 版本。
- Task Graph 版本。
- Execution 状态。
- 工程文件状态。
- 关键 Decision。
- Evidence。
- Context Snapshot。
- 下一步工作信息。

Checkpoint 不是简单的聊天摘要。

# 第五部分：统一工程工作机制

## 5.1 统一工程循环

ThinkFusion 围绕用户 Goal 持续运行：

1. 理解用户目标。
2. 理解当前工程状态。
3. 分析目标与现状的差距。
4. 决定下一步工程活动。
5. 必要时重新分析或设计。
6. 制定或调整任务计划。
7. 调度执行能力。
8. 收集执行结果。
9. 验证实际工程结果。
10. 更新目标、任务和工程状态。
11. 复核目标完成情况。
12. 未完成则继续下一轮。
13. 满足验收要求后完成交付。

这是一套动态循环机制，不是固定流水线。

## 5.2 简单任务和复杂任务

简单任务不需要强制经历所有阶段。

例如：

修复一个明确的空指针问题，可以直接理解、分析、修改和测试。

复杂任务需要完整规划。

例如：

从零开发一个企业管理系统，需要深入需求分析、系统设计、任务分解、模块开发、集成测试和交付。

系统必须根据目标复杂度和风险动态决定流程深度。

## 5.3 目标优先级与范围控制

Decision Controller 必须区分：

1. 当前目标必须完成的工作。
2. 完成当前目标所必需的补充工作。
3. 用户明确要求的额外优化。
4. 系统主动发现的潜在改进建议。

主动发现不能自动扩大当前目标。

额外优化不能无限增加任务。

发现的问题如果不影响当前交付，可以记录为后续建议。

# 第六部分：持续工程运行控制系统

## 6.1 定义

Engineering Runtime 是 ThinkFusion 的核心运行控制系统。

它负责让一个用户目标能够持续推进，而不是依赖单次模型调用或 Agent 进程。

Engineering Runtime 必须统一管理：

- Goal 生命周期。
- Task 生命周期。
- Execution 生命周期。
- 工程决策。
- 任务调度。
- 执行监督。
- 上下文恢复。
- 检查点。
- 资源管理。
- 用户干预。
- 验证和目标完成判定。

它是持续工程能力的核心。

## 6.2 内部职责

### A. Goal Controller

负责：

- 创建和更新 Goal。
- 管理 Goal 状态。
- 管理目标版本。
- 管理需求集合。
- 管理验收条件。
- 识别目标变更。
- 管理目标暂停和取消。
- 维护 Goal 与 Project 的关系。

Goal Controller 保存目标事实，不负责决定具体执行步骤。

### B. Decision Controller

负责：

- 读取当前 Goal。
- 读取工程状态。
- 读取任务图。
- 读取历史决策。
- 读取验证结果。
- 读取资源和权限状态。
- 分析当前工作差距。
- 判断下一步行动。
- 判断是否需要重新分析或设计。
- 判断是否需要用户介入。
- 判断是否达到停止条件。

Decision Controller 是统一的工程决策职责。

不再另外建设互相竞争的 Goal Reasoning、独立任务决策引擎或多套循环决策系统。

### C. Task Scheduler

负责：

- 读取任务图。
- 识别可执行任务。
- 检查前置依赖。
- 控制并行度。
- 选择执行时间。
- 分配执行能力。
- 管理任务优先级。
- 管理任务阻塞。
- 管理任务取消。
- 根据工程变化调整任务调度。

Task Scheduler 不负责自行改变用户目标。

### D. Execution Supervisor

负责：

- 创建 Execution。
- 启动执行器。
- 监控执行状态。
- 收集实时事件。
- 管理超时。
- 管理心跳。
- 请求取消。
- 处理执行失败。
- 管理安全重试。
- 确认执行实例是否仍然有效。
- 将结果返回统一任务体系。

### E. Context Manager

负责：

- 为执行实例准备上下文。
- 获取必要工程信息。
- 管理上下文预算。
- 选择相关历史信息。
- 生成 Context Snapshot。
- 管理上下文压缩。
- 管理上下文重建。
- 防止旧上下文覆盖新工程事实。

模型上下文是临时执行材料，不是系统唯一记忆。

### F. Verification Controller

负责：

- 检查 Task 验收条件。
- 执行必要测试。
- 收集 Evidence。
- 评估验证结果。
- 识别未解决问题。
- 判断是否需要修复。
- 检查 Requirement 覆盖情况。
- 根据目标验收规则形成完成判定建议。

Goal 最终完成状态必须由统一目标管理机制依据验收规则、Verification 结果和用户确认要求确定，不能由模型自行宣布。

# 第七部分：长任务与持续运行架构

## 7.1 长任务是核心基础能力

ThinkFusion 必须从第一版核心架构就支持长任务。

长任务不是一个单独 Agent，也不是一个长时间模型请求。

长任务是一个持续存在的工程目标，由多个 Task 和多个 Execution 组成。

系统必须能够连续组织数小时、数天乃至更长时间的开发工作。

## 7.2 三层生命周期

### Goal Lifecycle

Goal 可以持续数天或数周。

直到：

- 用户目标完成。
- 用户取消。
- 用户明确替代原目标。
- 因不可解决的外部条件而终止。

### Task Lifecycle

Task 可以持续数分钟、数小时或更长。

直到：

- 验收通过。
- 被取消。
- 被替代。
- 达到明确失败条件。
- 等待用户或外部条件。

### Execution Lifecycle

Execution 是一次具体执行尝试。

可以：

- 正常完成。
- 失败。
- 超时。
- 被取消。
- 被意外中断。

Execution 结束不自动结束 Task。

Task 失败不自动导致 Goal 失败。

## 7.3 Goal 状态

建议状态：

- Draft：目标尚未明确。
- Active：正在推进。
- Blocked：被重要问题阻塞。
- WaitingUser：等待用户决定。
- Paused：用户暂停。
- Completed：达到验收要求。
- Cancelled：用户取消。
- Archived：归档。

状态变更必须有明确条件和事件记录。

## 7.4 Task 状态

建议状态：

- Pending：等待执行。
- Ready：依赖已满足。
- Running：正在执行。
- Blocked：存在阻塞。
- WaitingUser：等待用户。
- Verifying：正在验证。
- Completed：验收通过。
- Failed：达到失败条件。
- Cancelled：取消。
- Superseded：被替代。

Task 状态必须由任务管理机制统一维护。

## 7.5 Execution 状态

建议状态：

- Created。
- Queued。
- Running。
- Waiting。
- Succeeded。
- Failed。
- TimedOut。
- CancelRequested。
- Cancelled。
- Interrupted。

必须区分正常结束、任务失败和意外中断。

## 7.6 任务执行机制

一个数小时的 Task 不应该依赖单次长模型调用。

正确机制是：

1. Runtime 创建 Task。
2. Scheduler 创建 Execution。
3. Execution Supervisor 启动执行器。
4. 执行器完成一部分工作。
5. 返回结果和事件。
6. Runtime 保存执行结果。
7. 必要时执行阶段性验证。
8. 更新 Task 状态。
9. Decision Controller 判断下一步。
10. 创建新的 Execution 或其他任务。
11. 持续推进，直到 Task 验收完成。

因此，即使单次模型只能工作数分钟，ThinkFusion 也能组织持续数小时的工程任务。

## 7.7 长任务八项基础能力

必须具备：

1. 目标和任务持久化。
2. 持续循环执行。
3. 动态任务图和并行调度。
4. 检查点与恢复。
5. 上下文压缩与重建。
6. 实时进度和执行可观测性。
7. 用户中途干预。
8. 阶段性验证和动态修复。

这些能力不得被推迟为可选增强功能。

# 第八部分：任务图与并行工程管理

## 8.1 DAG 任务模型

Task Scheduler 必须支持有向无环任务图。

不能只支持简单的父子任务列表。

任务之间可以存在：

- 父子关系。
- 前置依赖。
- 并行关系。
- 阻塞关系。
- 替代关系。
- 汇合关系。

## 8.2 动态任务调整

执行过程中可以：

- 新增任务。
- 拆分任务。
- 合并任务。
- 调整依赖。
- 调整优先级。
- 取消任务。
- 替代任务。
- 重新规划未完成任务。

任务图变更必须保留版本和变更原因。

## 8.3 并行执行治理

并行任务不能无条件同时修改同一工程文件。

必须具备：

- 工作区隔离策略。
- 文件修改范围管理。
- 并行执行限制。
- 变更冲突检测。
- 合并协调。
- 集成验证。

对于无法安全并行的任务，必须按依赖关系顺序执行。

# 第九部分：上下文、记忆与工程事实

## 9.1 上下文管理原则

模型上下文具有容量限制和生命周期限制。

不能将全部工程历史持续累积在一个上下文中。

系统必须区分持久化工程事实和临时模型上下文。

## 9.2 信息保存分类

| 信息 | 主要保存位置 |
|---|---|
| 用户原始需求 | Goal 与 Requirement |
| 目标变更 | Goal 版本和 Event |
| 任务状态 | Task 数据 |
| 执行过程 | Execution 与 Event |
| 设计决定 | Decision |
| 工程文件 | 实际项目工作区 |
| 工程结构 | 项目索引 |
| 验证结果 | Evidence |
| 当前工作摘要 | Context Snapshot |
| 下一步工作 | Task 与运行状态 |
| 用户确认 | Decision 与审批记录 |

## 9.3 上下文重建

创建新 Execution 时，Context Manager 根据当前任务准备必要信息。

至少考虑：

- 用户目标。
- 相关需求。
- 当前工程事实。
- 相关代码和文档。
- 任务目标。
- 前置任务结果。
- 重要设计决定。
- 最近验证结果。
- 当前工程差距。
- 用户约束。
- 可用权限。
- 下一步要求。

不应无差别注入全部历史对话。

## 9.4 工程事实治理

必须区分：

- 原始来源。
- 采集事实。
- 解析结果。
- 模型推断。
- 用户确认。
- 验证结论。

所有重要工程事实应有来源、时间和适用范围。

当代码版本或工程状态发生变化时，必须识别可能失效的旧结论。

# 第十部分：检查点、持久化和故障恢复

## 10.1 持久化要求

必须保存：

- Goal 和 Requirement。
- Goal 版本。
- Project 关联。
- Task Graph。
- Task 状态。
- Execution 记录。
- Decision。
- Event。
- Evidence。
- Checkpoint。
- Context Snapshot。
- 资源消耗。
- 权限和审批记录。

不能只依靠 Electron 内存状态或模型对话保存进度。

## 10.2 检查点内容

Checkpoint 至少包含：

- Goal 版本。
- Requirement 版本。
- Task Graph 版本。
- 已完成任务。
- 正在执行任务。
- 未完成任务。
- Execution 状态。
- 关键 Decision。
- 最近 Evidence。
- 工程文件状态。
- Git 状态。
- Context Snapshot。
- 下一步工作建议。
- 权限和资源状态。

## 10.3 恢复流程

应用启动后：

1. 扫描未完成 Goal。
2. 加载任务图和事件日志。
3. 读取最近有效 Checkpoint。
4. 检查工程工作区。
5. 确认实际文件和代码变化。
6. 查询运行中的 Execution。
7. 判断执行实例是否仍然有效。
8. 将失效执行实例标记为中断或失败。
9. 重建必要上下文。
10. 重新评估 Task 状态。
11. 重新评估工程目标。
12. 决定继续、重试、修复或等待用户。

恢复的是工程目标和真实工程状态，不是简单重放模型对话。

## 10.4 故障恢复场景

必须支持：

- 模型调用失败。
- 模型服务不可用。
- Agent 进程退出。
- 工具执行失败。
- Shell 超时。
- 应用意外关闭。
- 电脑重启。
- 上下文超限。
- 执行部分成功。
- 并行任务部分失败。
- 外部服务中断。

## 10.5 防止重复执行

对于非幂等操作，必须具备：

- 操作意图记录。
- 操作唯一标识。
- 执行结果核对。
- 重复执行检测。
- 安全恢复策略。

例如数据库迁移、文件删除、远程发布和数据写入不能默认安全重放。

# 第十一部分：工程执行架构

## 11.1 Native Engine

Native Engine 是 ThinkFusion 自身的基础工程执行能力。

必须逐步具备：

- 文件系统访问。
- 文件读取和修改。
- 代码搜索。
- 代码理解。
- 代码编辑。
- Shell 执行。
- Git 操作。
- 项目构建。
- 测试执行。
- 工程上下文准备。
- 执行状态管理。
- 执行结果回收。

Native 必须达到独立完成基础软件工程任务的标准。

## 11.2 External Engine

External Engine 用于接入外部增强能力。

包括：

- 外部 Agent。
- 外部模型。
- 专业开发工具。
- 外部插件。
- 专业服务。

External 能力必须声明：

- 支持的能力。
- 不支持的能力。
- 输入和输出格式。
- 上下文限制。
- 事件能力。
- 取消能力。
- 恢复能力。
- 权限边界。
- 资源消耗。
- 验证要求。

## 11.3 统一执行管理

Native 和 External 必须共享：

- Goal。
- Project。
- Requirement。
- Task。
- Execution。
- Evidence。
- Decision。
- Event。
- Checkpoint。
- Permission。

不允许每种 Agent 各自维护一套独立任务系统。

## 11.4 外部执行权限

统一接口不代表统一权限。

外部 Agent 可能在内部直接调用工具、访问文件或执行 Shell。

ThinkFusion 必须根据实际接入能力确定权限边界。

无法完整拦截外部 Agent 内部操作时，应采用隔离工作区、受限执行环境或降低授权范围。

不得将无法控制的外部执行器描述为完全受统一权限治理。

# 第十二部分：用户交互与过程可观测性

## 12.1 用户交互目标

用户不仅需要看到最终回答，还需要知道整个工程正在发生什么。

主工作界面应该围绕 Goal 和工程任务组织，而不是只展示对话记录。

## 12.2 必须展示的信息

- 用户最终目标。
- 当前工程状态。
- 目标完成进度。
- 任务列表。
- 任务依赖。
- 当前执行任务。
- 正在运行的模型和 Agent。
- 工具执行情况。
- 不同模型的独立输出。
- 工程变更。
- 测试和验证结果。
- 当前阻塞原因。
- 等待用户的事项。
- 预计后续工作。

进度必须根据真实任务状态计算。

不能单纯依据模型生成的百分比。

## 12.3 用户干预

必须支持：

- 暂停 Goal。
- 继续 Goal。
- 取消 Goal。
- 暂停 Task。
- 取消 Execution。
- 修改需求。
- 调整任务优先级。
- 批准方案。
- 否决方案。
- 提供新信息。
- 修改执行约束。

## 12.4 中途交互

用户可以在工程运行期间随时提出新要求。

系统需要判断：

- 是否只是补充信息。
- 是否改变当前 Task。
- 是否影响其他任务。
- 是否改变 Goal。
- 是否需要重新设计。
- 是否需要重新规划。
- 是否需要暂停当前执行。

不能简单地把新消息追加到模型上下文，而不更新工程状态。

## 12.5 过程与结果分离

UI 应当能够分别展示：

- 对话。
- 工程轨迹。
- 任务进度。
- 模型输出。
- 工具活动。
- 统计信息。
- 验证结果。

多模型输出必须能够区分来源。

所有重要活动都应有可追溯记录。

# 第十三部分：用户授权、资源和运行治理

## 13.1 用户授权原则

系统只能在用户授权范围内执行工程工作。

必须区分：

- 普通技术决策。
- 影响产品功能的重要决策。
- 影响用户体验的重要决策。
- 破坏性操作。
- 外部付费操作。
- 权限扩张操作。
- 不可逆操作。

普通技术细节可以自主处理。

重要产品选择应根据用户授权和影响范围请求确认。

破坏性操作、外部成本和权限扩张必须遵守明确授权要求。

用户已经明确授权的范围内，不应无意义地重复询问。

## 13.2 资源治理

必须管理：

- 模型调用额度。
- Token 消耗。
- 外部服务费用。
- 执行时间。
- 并行数量。
- 重试次数。
- 上下文预算。
- 磁盘和计算资源。

系统不得为了持续完成长任务而自动突破用户的费用或订阅限制。

资源不足时应保存状态，并等待用户或资源恢复。

## 13.3 执行安全

必须具备：

- 超时控制。
- 取消控制。
- 重试上限。
- 失败熔断。
- 工作区隔离。
- 文件变更保护。
- 命令权限控制。
- 高风险操作确认。
- 执行日志。
- 异常恢复。

持续运行不意味着无限运行。

---

# 第十四部分：验证与目标完成判定

## 14.1 Task 完成判定

Task 完成必须满足该 Task 的验收条件。

例如：

实现用户管理模块，不能只以代码已经生成作为完成依据。

还需要检查：

- 必要功能是否实现。
- 编译是否通过。
- 测试是否通过。
- 接口是否正确。
- 代码变更是否符合要求。
- 是否存在未解决的关键问题。

## 14.2 Goal 完成判定

Goal 完成必须综合：

- 用户需求覆盖情况。
- 必要任务完成情况。
- 关键依赖完成情况。
- 系统集成结果。
- 必要测试结果。
- 运行验证结果。
- 重要风险。
- 遗留问题。
- 用户确认要求。
- 最终交付物。

## 14.3 目标完成状态

建议区分：

- Completed：验收要求全部满足。
- PartiallyCompleted：部分目标完成。
- Blocked：存在无法继续的阻塞。
- WaitingUser：等待用户确认。
- Cancelled：用户取消。

对于无法验证的要求，不得默认视为通过。

对于用户明确豁免的条件，必须记录豁免依据。

## 14.4 结束条件

系统达到目标后必须停止自动扩展工作。

主动发现的优化建议可以作为后续候选任务，不得自动无限追加到当前 Goal。

这是核心控制层。

负责：

- Goal Controller。

# 第十六部分：辩论、多模型和辅助能力定位

这些能力服务于核心软件制造目标，不拥有独立产品总目标。

## 16.1 多模型协作

用于提高复杂问题的分析、设计和执行质量。

根据任务需要动态选择参与模型。

不能要求所有模型都参与所有任务。

## 16.2 辩论能力

辩论是可选决策辅助机制。

只有存在重要技术分歧、证据冲突、方案风险或重大设计选择时才启动。

没有实质争议时直接推进。

必须设置参与条件、结束条件和收益判断。

不得因为辩论或审核而无意义延长工程流程。

## 16.3 主动发现

用于识别可能影响目标完成的风险和问题。

发现内容应区分：

- 当前必须解决的问题。
- 重要风险。
- 建议改进。
- 未来优化机会。

不能自动将所有发现转化为当前工程任务。

## 16.4 记忆能力

用于保存有长期价值的工程上下文和决策。

不能替代 Goal、Task、Execution 和 Evidence 的正式持久化数据。

## 16.5 工程知识图谱

知识图谱、AST、LSP 和其他工程理解技术根据实际收益选择。

不要求为了架构完整而提前建设复杂知识图谱平台。

# 第十七部分：实施阶段与建设优先级

## 第一阶段：独立软件开发与基础长任务闭环

目标：ThinkFusion 能够独立完成基础软件开发任务。

必须完成：

- 用户目标管理。
- 需求管理。
- 项目理解。
- 基础工程分析。
- 系统设计。
- 任务分解。
- Task 状态管理。
- Execution 状态管理。
- Native 工程执行。
- 构建和测试。
- Evidence 管理。
- 持久化。
- 基础 Checkpoint。
- 上下文重建。
- 基础故障恢复。
- 用户暂停和继续。
- 过程可观测。
- 目标完成判定。

第一阶段必须具备真实长任务能力，不能只支持一次性任务。

## 第二阶段：复杂工程与持续运行增强

目标：能够承担更复杂的软件系统开发。

增强：

- 复杂 DAG 任务图。
- 多任务并行。
- 工作区隔离。
- 动态重规划。
- 多次 Execution。
- 更完善的故障恢复。
- 运行中任务治理。
- 更完整的上下文管理。
- 完整的系统集成验证。
- 更成熟的用户中途干预。

## 第三阶段：外部增强与智能协作

目标：提升复杂工程任务的能力和效率。

增强：

- External Agent 接入。
- 多模型动态协作。
- 专业模型路由。
- 按需辩论。
- 复杂工程理解。
- 记忆增强。
- 外部专业工具。

## 第四阶段：主动改进与长期演进

目标：提升系统持续改进能力。

增强：

- 主动发现工程风险。
- 架构优化建议。
- 技术演进建议。
- 工程质量持续改进。
- 长期项目知识沉淀。
- 用户授权下的持续优化。

各阶段可以根据实际工程进度调整，但不能将第一阶段的基础长任务能力推迟到后续阶段。

# 第十八部分：生产级验收标准

## 18.1 基础软件制造验收

必须证明：

1. 能接收用户软件制造需求。
2. 能形成可实施方案。
3. 能理解实际项目。
4. 能建立工程任务。
5. 能独立修改代码。
6. 能运行构建和测试。
7. 能收集验证证据。
8. 能交付工程成果。

## 18.2 长任务验收

必须通过：

- 连续运行至少两小时的真实工程任务。
- 多个相关 Task 连续执行。
- 至少一次模型或执行器失败。
- 至少一次上下文重建。
- 至少一次应用重启后的任务恢复。
- 恢复后核对真实工程文件状态。
- 继续完成剩余工程任务。
- 完成最终验证。

同时必须单独验证：

- 用户主动暂停。
- 用户主动取消。
- 部分执行成功后的恢复。
- 重复执行防护。
- 并行任务冲突处理。
- 资源额度不足时安全停止。
- 用户中途修改需求后的重新规划。

## 18.3 工程质量验收

必须证明：

- Task 完成有验收依据。
- Goal 完成有完整证据。
- 重要决策可追溯。
- 工程变更可追溯。
- 失败原因可识别。
- 未完成事项可展示。
- 恢复不会无条件重复危险操作。
- 模型报告不会替代实际验证。

## 18.4 用户控制验收

必须证明：

- 用户可以查看实际进度。
- 用户可以中途修改需求。
- 用户可以暂停和恢复。
- 用户可以取消任务。
- 用户可以批准重要决策。
- 用户可以控制外部费用和权限。
- 系统不会擅自扩大目标。

# 第十九部分：非目标与架构约束

## 19.1 当前非目标

ThinkFusion 当前不以建设以下产品为目标：

- 通用人工智能平台。
- 独立的多 Agent 组织模拟平台。
- 无限自主的自动化系统。
- 独立知识图谱产品。
- 复杂辩论平台。
- 多套并行的任务管理引擎。
- 为架构完整而建设的独立子系统。

## 19.2 不允许出现的架构问题

1. Goal、Task 和 Execution 生命周期混淆。
2. 模型会话成为长期任务的唯一状态来源。
3. Agent 各自维护独立工程目标。
4. Native 和 External 使用互不兼容的任务体系。
5. 任务完成和目标完成混为一谈。
6. 模型报告成功直接作为验收结果。
7. 上下文摘要代替真实工程状态。
8. 任务进度只保存在内存。
9. 应用重启后无法恢复工程。
10. 用户暂停只改变 UI 状态，不停止实际执行。
11. 多任务并行导致工程文件无控制冲突。
12. 资源不足时无限重试。
13. 主动发现无限扩大用户目标。
14. 辩论和审核成为无意义的固定流程。

# 第二十部分：架构演进治理

## 20.1 总体原则

产品总目标保持稳定。

总体架构在没有重大理由时不随意改变。

技术实现可以持续演进。

## 20.2 架构变更要求

重大架构变化必须经过：

1. 明确现有问题。
2. 说明用户价值。
3. 评估现有架构影响。
4. 评估兼容性。
5. 评估实施成本。
6. 形成架构决策记录（ADR）。
7. 明确迁移方案。
8. 明确验收标准。

## 20.3 文档层级

后续文档应形成以下层级：

- 产品总目标与总体架构规范：定义产品方向和架构约束。
- 技术总体设计：定义技术选型、运行模型和模块关系。
- 子系统设计文档：定义具体模块职责和接口。
- 实施任务书：定义代码实施顺序和验收标准。
- ADR：记录重大架构决策及原因。
- 测试验收规范：定义可重复的质量验证方法。

下层文档不得随意改变上层产品目标。

# 第二十一部分：最终架构基准

ThinkFusion V4.0.0 的核心定义如下：

## 一个产品目标

帮助用户开发出自己想要制造的系统。

## 六项核心工程能力

理解、分析、设计、规划、开发、验证。

## 一个持续工作机制

围绕用户目标持续决策、组织任务、执行工程工作、验证结果并动态调整。

## 五个核心业务对象及其运行记录

Goal、Project、Task、Execution、Evidence，以及 Requirement、Decision、Event、Checkpoint 等必要对象。

## 一个核心运行控制系统

Engineering Runtime，统一管理目标、决策、任务、执行、上下文、验证和恢复。

## 两种工程能力来源

Native Engine 和 External Engine。

## 六个逻辑架构层

用户交互、目标与项目管理、持续工程运行控制、工程能力执行、工程理解与验证、持久化与运行基础设施。

## 一项不可延期的基础能力

持续数小时乃至更长时间的工程任务管理、执行、持久化、上下文重建和故障恢复。

# 最终产品定义

**ThinkFusion 是一个用户目标驱动的持续软件开发系统，帮助用户将想法转化为真正可用的软件系统。**

它能够自主理解需求、分析问题、设计方案、规划任务、持续执行工程工作、验证实际结果，并通过持久化进度、上下文重建、动态任务调度和故障恢复，长期承担复杂的软件开发目标。

它可以使用自身的 Native 工程能力，也可以根据需要调用 External 模型、Agent 和工具增强能力。

在整个过程中，用户始终拥有目标决定权和授权控制权。

ThinkFusion 以实际工程成果、验证证据和用户验收作为完成依据。

**所有架构、模块、模型、Agent、工具和技术选型，都必须服务于同一个目标：帮助用户制造出自己真正想要的系统。**
