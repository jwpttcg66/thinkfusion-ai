# 目标契约与证据闭环 UI 规格

**状态：** `DESIGN`，未实现。  
**基线：** `main@9026e0e`  
**设计：** [V3-GOAL-CONTRACT-EVIDENCE-CYCLE.md](../architecture/V3-GOAL-CONTRACT-EVIDENCE-CYCLE.md)  
**契约：** [GOAL_CONTRACT_EVIDENCE_CONTRACTS.md](GOAL_CONTRACT_EVIDENCE_CONTRACTS.md)  
**状态：** 当前实现见 [STATUS.md](../implementation/STATUS.md)。

本文只定义界面行为、信息层级和可追溯性，不重复类型定义。

## 1. 原则

1. 主活动区继续使用最新连续文档式对话流，不恢复独立定位轨，不把内容重新做成大卡片堆叠。
2. 每个阶段标题必须对应真实事件；没有发生的阶段显示“未发生”，不能从投影补造。
3. 用户目标、Goal Version、Criterion 和决策原因必须可见，不能只显示“已完成”。
4. 模型推断、工程事实、用户确认和系统约束必须用文字标签区分；不能把模型推断画成用户要求。
5. 未知 Token/费用/证据显示“未提供”，不显示 0。
6. 目标变更、接受未验证、放弃目标等有副作用的操作必须有明确确认入口。

## 2. 主活动区顺序

按真实事件顺序呈现：

```text
用户目标
→ 目标理解与确认
→ 本轮目标复核
→ 分析
→ 设计与方案取舍
→ 按需方案辩论
→ 计划
→ 工具执行与结果
→ 独立评审
→ 验证证据
→ 本轮结论
→ 目标符合度（逐条 Criterion）
→ 下一步决策及原因
```

实现要求：

- 标题是文档式小标题，不是带边框/底色的卡片。
- 模型正文、工具输出、评审问题、证据各自保留来源；不能互相冒充。
- 工具输出可展开，保留命令、参数、退出码、stdout/stderr、耗时。
- 步骤用一行前缀 + 可展开详情；不把每条输出拆成独立卡片。
- 阶段跳过显示原因，例如“无实质方案争议”“问答场景无实现阶段”。

## 3. 目标区

当前落地：工程任务主会话顶部的 `GoalContractCard`（`components/engineering/GoalContractCard.tsx`）。它只读 `projectGoalDrivenWorkbench` 的事件投影；修改成功标准走 `task:revise-goal`，删减标准二次确认。

位置：主活动区顶部，或在工程任务头附近；不新增独立流程轨。

显示：

| 字段 | 展示 |
| --- | --- |
| 原始请求 | 原文，不改写 |
| Goal Version | `v1`、`v2`；变更后保留旧版本入口 |
| 用户意图 | 文本 + 来源标签 |
| 最终目标 | 文本 + 来源标签 |
| 目标价值 | 文本 + 来源标签 |
| 成功标准 | Criterion 列表，逐条状态 |
| 隐含约束 | 文本 + 来源标签 |
| 可行性 | 文本 + 来源标签 |
| 未确认假设 | 可见，不可折叠成“无” |
| 目标风险/阻塞 | 可见，不能只显示“进行中” |

来源标签固定为：`用户明确`、`用户确认`、`模型推断`、`工程证据`、`系统约束`、`未确定`。颜色不是唯一区分手段。

## 4. Criterion 展示

每条标准显示：

```text
[优先级] 描述
状态：已满足 / 部分满足 / 未满足 / 未验证 / 已豁免 / 待判定
验证方式：...
证据：N 条（可展开）
来源：用户明确 / 模型推断 / ...
```

规则：

- `已满足` 必须能展到证据；没有证据不允许显示绿色勾。
- `未验证` 与 `未满足` 分开；不能用灰色都表示。
- `已豁免` 必须显示授权人和原因。
- 目标版本变化后，旧版本 Criterion 仍可通过版本切换查看。
- 没有 Criterion 时显示“尚未建立成功标准”，不能显示“目标已达成”。

## 5. Goal Fit 汇总

显示计数：已满足、部分满足、未满足、未验证、已豁免、阻塞风险、证据完整度。

总体标签：

- `目标已达成`：所有 MUST MET 且无阻塞风险。
- `带风险达成`：有授权豁免或已记录风险，核心目标满足。
- `部分达成`：存在未满足/未验证但未阻塞。
- `目标未达成`：存在未处理 UNMET 或阻塞。
- `无法判断`：没有 Criterion 或证据不足。

禁止把 `task.completed` 直接画成“目标已达成”。

## 6. 下一步决策区

显示：

```text
下一步：修复 / 重新规划 / 重新设计 / 重新分析 / 澄清目标 / 等待你 / 阻塞 / 完成 / 终止
原因：...
依据证据：...
目标版本：vN
```

- `等待你` 必须显示需要用户决定的具体问题。
- `阻塞` 必须显示外部条件与解除方式。
- `完成` 必须同时显示 Goal Fit；两者矛盾时显示冲突警告，不能静默覆盖。

## 7. 目标变更确认

入口：目标区“修改目标/成功标准”。

流程：

1. 展示旧版本与新版本差异（新增/删除/修改的 Criterion）。
2. 明确“删除标准属于重大变更”，要求用户确认。
3. 用户确认后显示新 Goal Version；拒绝则保留旧目标并显示“未变更”。
4. 变更后受影响任务显示“需重规划”，已完成且不受影响的成果保留。

不能通过修改任务摘要或隐藏 IPC 偷偷改变目标。

## 7.5 目标物与交付文件

目标区/最终结论必须显示“目标物”栏，遵循 `AGENTS.md` §8.2：

- 列出全部轮次执行报告并集的产出文件、目录和构建产物；
- 不只看最后一轮；
- 没有记录时明确写“没有记录到交付文件”，不能隐藏整栏；
- 目标达成不替代交付文件；Goal Fit 和交付文件分别显示。

## 8. 提交与未验证收尾

- 完全权限下允许未验证收尾，但 Criterion 和总体 Goal Fit 必须保持 `未验证`/`部分达成`，摘要写明缺口。
- 非完全权限保留“继续修复 / 重新判定 / 接受未验证”出口。
- “接受未验证”不是“目标达成”；界面必须显示风险与未验证项。

## 9. 页面分工

- **对话**：连续文档式主活动区，含目标、分析、设计、执行、评审、证据、结论、目标符合度、决策。
- **输出**：原始事件、参数、结果、文件改动、完整证据。
- **轨迹**：阶段/调用/决策顺序；可重放，但不替代主活动区事实。
- **统计**：模型、工具、耗时、Token/费用；未知显示未提供。

不增加第五个页面或独立定位轨。

## 10. 可访问性与可追溯性

- 阶段标题、Criterion 状态、决策类型不能只靠颜色区分。
- 每个模型输出保留 model/participant 身份；每条工具结果保留 stepId/callId；每条证据保留 evidenceId/criterionId。
- 目标变更、决策、证据链接都有可展开详情和事件来源。
- 长文档流不自动折叠真实事件；只允许用户主动收起。
