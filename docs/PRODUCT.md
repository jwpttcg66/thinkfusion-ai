# 产品定位

> **ThinkFusion AI · 多模型协作智能工作平台**
> **Many Minds. One Intelligent Workflow.**
>
> 汇集多个 AI 模型、工具和知识源，围绕用户目标自主组织协作，通过持续探索、信息整合
> 和证据验证，完成从问题理解到最终交付的全过程。

一句话：**用户提出目标，ThinkFusion 组织协作；模型决定如何探索，系统负责协调、取证、
验证和交付。**

它不是让多个模型轮流发表意见，而是让多个模型真正参与同一个任务。

> 本文是产品方向 V3（2026-11-18），取代此前「可验证的多模型审辩平台」的定位。
> 新定位已经冻结。代码主体已迁移到协作引擎、工程空间与证据链；
> 实际阶段状态以 [implementation/STATUS.md](implementation/STATUS.md) 为准。
> 长任务与上下文压缩仍是设计，未实施；迁移背景见
> [架构/迁移计划](architecture/MIGRATION_PLAN.md)。

## 1. 为什么不再用「多模型辩论平台」做定位

辩论是一个有效的协作行为，但它不是产品本体。把它当成定位，会带来三个结构性错位：

| 现象 | 根因 |
| --- | --- |
| 一个简单问答也要走「独立作答 → 质疑 → 修订 → 裁判」 | 流程先于任务：所有任务被压进同一条辩论流水线 |
| 工程任务开场就冻结一份「辩论基线」，但用户要的是改代码 | 辩论的取证方式被当成了工程的工作方式 |
| 用户要先选「真理发现 / 对抗辩论 / 专家评审 / 方案竞争」 | 协作方法被暴露成产品入口，用户被迫替系统做调度 |

真正的问题不是「辩不辩」，而是：**系统能不能围绕一个目标，自己决定该做什么、谁来做、
做到什么程度算完成。**

## 2. 定位

**ThinkFusion AI 是一个多模型协作智能工作平台。**

用户只描述目标。系统理解目标与交付标准，组织多个模型、工具和知识源协作，
持续探索、整合信息、验证结论，直到交付一个可检查的结果。

四个层次：

1. **任务理解** —— 目标是什么、约束是什么、交付物长什么样、什么算完成。
2. **动态协作** —— 谁参与、怎么分工、并行还是递进、下一步做什么，由任务与运行时状态决定。
3. **证据与知识** —— 代码、网页、工具结果、执行结果、历史结论都进入同一套证据引用体系。
4. **验证与交付** —— 重要结论必须被验证；分歧、不确定性与未核验项随交付物一起给出。

一句话反定义：

> 它不是「多开几个网页然后总结」，也不是「多个模型投票」，更不是「所有任务都先辩一场」。

## 3. 一个协作引擎，三个工作空间

引擎是同一个，空间只决定**第一手材料从哪来、交付物是什么**。

```
                    ┌──────────────────────────────┐
                    │        统一协作引擎           │
                    │  任务理解 · 模型协作 · 动态规划  │
                    │  工具调用 · 证据管理 · 结果验证  │
                    └──────────────┬───────────────┘
          ┌────────────────────────┼────────────────────────┐
          ▼                        ▼                        ▼
   知识学习空间              工程工作空间              通用协作空间
   研究 / 学习 / 沉淀        代码 / 方案 / 改动         问答 / 分析 / 比较
          │                        │                        │
          └────────────────────────┴────────────────────────┘
                                   ▼
                    Web / Local / Cloud / CLI · Runtime
                    Evidence · Memory · Storage
```

| 空间 | 回答什么问题 | 典型工作 | 交付物 |
| --- | --- | --- | --- |
| **知识学习** | 关于世界的问题 | 主题研究、资料整合、知识沉淀、缺口发现、历史结论复用 | 研究报告、知识卡、知识地图 |
| **工程工作空间** | 这个仓库该怎么办 | 代码理解、架构分析、方案设计、CLI Agent 协作、修改、测试、评审、Git/Worktree | 工程分析、改动方案、代码改动、测试报告、评审结论 |
| **通用协作** | 日常的问题 | 问答、技术选型、比较、规划、综合研究 | 答案、对比表、方案与依据 |

三个空间共用同一套证据与交付契约；**不各造一套 Runtime、审批、Journal 或证据格式。**

知识学习与工程空间已经有一部分能力（见 ROADMAP「现在的位置」），但作为完整产品形态尚未完成；
版本安排与缺口见 [ROADMAP.md](ROADMAP.md)。

## 4. 协作引擎做什么

引擎的职责是治理，不是替模型思考：

- 判断任务需要什么：事实、代码、工具、还是持续研究；
- 决定哪些模型/工具参与，以及它们各自拿到什么上下文；
- 拆分任务、安排依赖、并行或递进；
- 根据结果决定继续探索、换角度、还是停止；
- 识别信息缺口与证据矛盾；
- 整合多个模型的结果，验证重要结论；
- 形成符合交付标准的最终产物。

**辩论、质疑、反例、交叉评审、方案竞争都只是可使用的协作行为**，由任务和运行时状态决定，
不是每个任务的必经阶段。没有矛盾就不辩；有矛盾才组织交叉审查。

协作行为目录与调度规则见
[COLLABORATION_ARCHITECTURE.md](architecture/COLLABORATION_ARCHITECTURE.md)。

## 5. 三条不可让渡的原则

### 5.1 任务决定流程，而不是流程决定任务

同一个 ThinkFusion，可以完成一句话问答，也可以开展持续数小时的工程研究。
系统不能强迫它们经过相同的轮次、相同的角色、相同的提示词次序。

### 5.2 模型负责理解与探索，系统负责治理与验证

不为了「本地解析能力的完整性」去造一套覆盖所有语言的语义引擎。
代码索引、搜索、文件读取、LSP 提供事实；模型根据任务动态理解与探索；
系统确保权限、证据、可追溯与可复验。

### 5.3 协作结果不是辩论胜负，而是用户目标是否完成

有时最好的结果来自多个模型互相补充，有时来自某个模型找到关键证据，有时来自激烈交锋。
系统不预先规定哪一种才算成功；**交付物是否满足目标、结论是否可检查**，才是判据。

主活动区按用户理解结果的顺序组织，而不是按「谁正在跑」：

1. 核心结论  
2. 关键意见与真实争议（无争议不展示空辩论）  
3. 评审问题与验证证据（有内容，不只状态）  
4. 协作过程（紧凑）  
5. 完整轨迹与原始输出（按需进入）

Debate / Review / Verification 是可选协作行为，不是每个任务的必经舞台。细节见
[`docs/spec/V3-MAIN-ACTIVITY-COLLABORATION-RESULT-TASK-BOOK.md`](spec/V3-MAIN-ACTIVITY-COLLABORATION-RESULT-TASK-BOOK.md)。

### 5.4 不使用任务提示词，不冻结流程基线

- 用户问题原样发出；工具契约、权限规则、输出 schema 是**契约**，不是话术。
- 不在任务开始时创建共享「基线」；工程状态由任务自己持有（commit、快照、diff、测试）。
- 这两条是硬约束，写进 [AGENTS.md](../AGENTS.md) 第 6 节；违反的实现不应合入。

### 5.5 参与者数量由任务决定，但不能静默

- 先守调用范围：本地只调本地模型，远端只调远端模型，混合才可同时使用两者。
- 网页是页面渠道，不是模型；是否参与由任务决定，不因混合自动加入。
- 简单问题可以只用一个 Agent；有争议、高风险或用户要求多视角时，不得只用一个。
- 为什么选这些、为什么跳过其他，必须对用户可见；不允许以省成本为唯一理由少问。
- 关键阶段（计划、重规划、辩论触发）可以引入模型审核，但审核是契约与数据，不是话术。

## 6. 交付物

| 交付物 | 必须带什么 |
| --- | --- |
| 答案 / 研究报告 | 结论、依据、分歧、不确定性、未核验项 |
| 知识卡 / 知识地图 | 主题关系、结论出处、时效（版本/时间）、已知缺口 |
| 工程分析 | `路径:行号` 证据、影响面、识别方法 |
| 改动方案 / 代码改动 | 计划、审批记录、diff、测试、执行断言 |
| 测试 / 评审报告 | 真实执行结果、失败项、回退方式 |

没有证据的结论必须被标成「断言」；没有跑过的测试不能被说成通过。

## 7. 不做什么

| 不做 | 原因 |
| --- | --- |
| 把辩论当产品入口 | 用户只需要说目标，不需要选择协作方法 |
| 所有任务套同一条固定流程 | 任务差异大于流程共性；固定流程会把工程变成辩论 |
| 让多模型轮流发言、再压缩一次 | 那是套壳，不是协作；没有分工与验证就没有增量 |
| 多模型投票定胜负 | 一致可能是同一个错误，票数不产生证据 |
| 要求网页模型执行 system / 工具协议 | 网页 Adapter 的技术限制；异构 Agent 必须按能力分配任务 |
| 无授权的自动执行 | 权限模型是产品底线，不是可配置项 |
| 新建第二套 Runtime / 审批 / Journal / TaskGrant / Verifier | 已有系统足够，重复建设只会制造两套事实 |

## 8. 成功的判据

- 同一个系统能接住一句话问答与数小时的工程任务，流程不同，但都不别扭。
- 用户不需要选择「辩论 / 评审 / 研究」模式，只需要说清目标。
- 每个交付物都能回答「凭什么」：结论 → 判断 → 证据 → 出处 → 执行。
- 模型可替换、通道可增减，主流程不改；网页只收问题与数据，知识/通用可提问，工程只回答；
  第一轮只发原话，网页不接收 `ContractInput`。
- 关掉本地 Runtime，知识学习与通用协作仍然完整可用。
- 工程任务的每次「已修复 / 已通过」都能追到真实执行断言与可回退路径。
- 第二次研究同一主题时，能复用上次结论并标明时效，而不是从零开始。
