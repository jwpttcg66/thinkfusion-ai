# 产品定位

> **一句话：让多个 AI 各自作答、定向互驳，最后给出一个能被证据检验的结论。**
> Many minds, one **verifiable** answer.

本文只写**目标形态**与**取舍原则**。当前代码做到哪一步，看根目录
[README](../README.zh-CN.md) 的「现在真的能做到什么」；先做什么、怎么算完成，看
[ROADMAP.md](ROADMAP.md)；技术怎么落地，看 [ARCHITECTURE.md](ARCHITECTURE.md)。

---

## 1. 要解决的不是「答案不够多」

单个模型已经能给出流畅、完整、语气笃定的回答。问题不在数量，在**可信度**：

| 失败形态 | 用户看到的现象 | 根因 |
| --- | --- | --- |
| 自信的错误 | 回答条理清晰，但结论是错的，且没有任何地方提示它可能是错的 | 只有一个视角，没有反例与质疑 |
| 被抹平的分歧 | 几个模型说法不同，汇总后变成一段四平八稳的综述 | 汇总等于压缩：一致处重复，分歧处取平均 |
| 不可验证 | 结论末尾写着「根据相关资料」，点不开、追不到、复核不了 | 结论没有绑定证据 |

「多开几个网页再总结」不会解决其中任何一个。它只是把三份未经检验的答案交给第四个模型，
再压缩一次——多出来的只有延迟。

---

## 2. 定位

**ThinkFusion AI 是一个可验证的多模型审辩平台。**
它不做「更多答案」，它做「更可信的结论」。

四个动作，缺一不可：

1. **独立作答** —— 每个模型在不知道彼此答案的前提下回答同一个问题，避免相互污染。
2. **定向辩论** —— 不搞笼统的「再问一轮」，只对真正有争议的主张分配质疑与修订。
3. **证据校验** —— 主张要么绑定可复核的证据（代码、执行结果、网页原文），要么被明确标为断言。
4. **条件化结论** —— 输出结论、依据、分歧、适用条件与缺失角度；不追求「所有模型达成一致」。

一句话反定义：

> 它不是「多开网页 + 固定提示词 + JSON 执行器」，也不是「多个模型投票」。

投票解决的是「相信谁」，审辩解决的是「凭什么」。

## 3. 目标形态：五段链路

```
用户的问题
   │
   ├─► ① 独立作答：所有已开启的通道，原话直发，互不可见
   │
   ├─► ② 主张与争议：抽出可单独判断真假的 Claim，检测谁和谁在什么点上冲突
   │
   ├─► ③ 定向辩论：只对高价值争议发起质疑，被质疑方带着反例修订
   │
   ├─► ④ 证据校验：把主张接到真实证据上（代码位置、执行断言、网页原文）
   │
   └─► ⑤ 裁判与结论：判定 supports / contradicts / context，保留分歧与不确定性
```

每一段的产物都必须能被下一段引用，也能被用户单独复核：

| 段 | 产物 | 不可跳过的理由 |
| --- | --- | --- |
| ① 独立作答 | 带来源与轮次的回答 | 一旦互相可见，后面的「分歧」就只是回声 |
| ② 主张与争议 | Claim + Dispute，指到具体两句 | 不落到句子，「分歧」就只是观感 |
| ③ 定向辩论 | 质疑、反例、修订后的主张 | 没有反例的辩论只是换个人复述 |
| ④ 证据校验 | Evidence Pack、执行断言、内容哈希 | 证据一旦可被静默改写，整条链就不可复核 |
| ⑤ 裁判与结论 | 方向判断 + 置信度 + 局限 | 结论不标注不确定性，就是把猜测包装成事实 |

## 4. 取舍原则

### 4.1 原话直发，不替用户改问题

用户问什么，页面就收到什么。不拼角色设定、不拼格式要求、不拼「几点要求」。
系统需要结构化，是系统自己从回答里抽，不是要求模型交 JSON。

### 4.2 结构化是内部产物

Claim、关系、证据、分歧都是应用侧的数据结构。抽取失败就降级为原文并列并明说，
不允许因为「没结构化成功」而中断一次研究，更不允许把降级结果当成结论。

### 4.3 分歧保留，不取平均

有价值的输出必须能回答：哪几句对不上、分歧点具体在哪、谁有证据、谁只是断言、
**哪个角度没人提到**。只做「把 N 个回答总结一次」不算综合。

### 4.4 证据先于结论

判定「A 反驳 B」不需要判断 B 对不对；判定「B 成立」才需要证据。
证据先算完，写作阶段只能引用，不能加分——否则写作模型会为了行文顺滑给弱证据打高分。

### 4.5 思考与执行分离，执行可选

协作与审辩不碰文件系统；只有确实要改动本地状态时，才生成可审批的计划，
交给独立 Runtime 执行。**拔掉 Runtime，问答、辩论与结论仍然完整可用**——
这是检验解耦是否真实的硬标准。

### 4.6 识别不等于授权

路由判成「要执行」只是生成计划；写文件、跑命令仍然要人点确认。
权限模型不为「让流程更顺」而放宽。

### 4.7 每条结论可回溯

用户要能回答「这个结论从哪来」：哪一轮、哪个模型、哪句原话、哪条证据、
哪次执行、哪个提交。追不到出处的结论，一律按断言处理。

## 5. 两个空间：知识学习与工程

同一个审辩与证据引擎，两种交付物：**知识学习交付可复用的知识，工程交付可验证的改动。**
两个空间不是两套产品，它们共用 Claim / Evidence / Pack / attestation，只是证据来源不同。

### 5.1 知识学习空间（后续主线：0.4）

这个空间回答「关于世界的问题」：技术原理、方案对比、资料冲突、排查思路。
一次结论只是起点，目标是让每一次研究都变成下一次的资产。

目标形态：

- **结论带证据与分歧**：交付的不是一篇综述，而是「谁主张什么、依据在哪、哪里仍有分歧」。
- **知识可积累**：Claim、Evidence、结论落库，按主题、来源、时间索引；第二次问同一主题，
  能带出上次的结论，并标明它依据的是哪个版本、哪个时间。
- **学习有路径**：从「一个问题」长成「一个主题的知识地图」——已知什么、争议什么、
  还缺什么；缺口反过来成为下一轮研究要补的问题。
- **多轮自主研究**：系统自己发现缺口、补问、更新结论；每一轮都写清为什么继续、为什么停。

判据：

- 第二次问同一主题，能复用上次的结论，并显式标注时效与依据；
- 能指出「这个问题还有哪几个角度没人回答」，而不是只给出已有答案；
- 旧结论被新证据推翻时，旧结论保留但标记为已被推翻，而不是悄悄覆盖。

### 5.2 工程空间（后续主线：0.5）

这个空间回答「这个仓库该怎么办」：理解、评审、修改。
严格按「只读 → 评审 → 写入」三层推进，不能跳级：

1. **理解（只读）**：代码智能——符号、引用、调用链、影响面、构建与依赖。
   结论必须带 `路径:行号`；读不到就停下来问，不凭常识猜。
2. **评审**：对方案与改动做独立评审——覆盖写、缺测试、步骤过多、边界条件。
   评审意见回到计划，不直接改代码。
3. **执行（可写）**：计划 → 人审批 → 独立 Runtime 执行 → 真实 `ExecutionReport`
   → attestation 进证据包。写文件、跑命令都要授权，每一步可复验。

目标形态：

- **代码智能是第一手材料**：不是把仓库丢给模型，而是先建索引、再按需取证据
  （符号、引用、影响面），让「它读过代码」有位置可查。
- **改动有证据链**：每个「已修复 / 已通过」都要能追到一次真实执行；
  没跑过的测试不能被说成通过。
- **多 Agent 工程协作**：理解、实现、评审、验证分角色，但共享同一份证据与任务边界；
  并发任务各有 worktree，不互相踩。
- **失败可回退**：快照、diff、回滚是产品能力，不是操作者的记忆。

判据：

- 对一次改动，能回答「改了哪些文件、为什么、影响面多大、哪条测试证明它」；
- 任何「已通过」的结论必须带执行断言；伪造或篡改能被发现；
- 只读分析不产生任何写操作；写入必须先有计划与审批。

### 5.3 共同底线

- 两个空间不各造一套证据格式：Claim、Evidence、Pack、attestation 是同一套。
- 执行仍然可选：关掉 Runtime，知识学习、审辩与结论完整可用。
- 空间只决定「第一手材料从哪来」（网页 / 仓库），不改变「结论必须可检验」这条底线。

## 6. 谁在什么场景用它

- **知识学习**：技术选型、原理研究、资料冲突、跨来源调研——需要的是分歧地图与可复用结论。
- **工程决策**：线上排障、方案评审、影响面分析——需要多个视角，更需要能落地的证据。
- **需要复核的技术结论**：安全评估、架构评审、事故复盘——结论必须能被别人重新走一遍。

共同的判据只有一条：**用户要为一个判断负责，所以他要能检查这个判断。**

## 7. 不做什么

明确划掉，避免反复讨论：

| 不做 | 原因 |
| --- | --- |
| 通用浏览器 | 内嵌网页只是模型接入手段，不是产品 |
| 「多开几个网页然后总结」 | 那是压缩，不是审辩；没有反例就没有增量 |
| 多模型投票定胜负 | 一致可能是同一个错误，票数不产生证据 |
| 无授权的自动执行 | 权限模型是产品底线，不是可配置项 |
| 要求模型每轮输出 JSON | 模型会去解格式题，而不是解用户的问题 |
| 把某个网页的 DOM 当系统接口 | 站点改版是常态，接口必须收在 Adapter 后面 |
| 第三方插件市场 | 内部能力插件化不等于对外开放安装；接口没稳之前开放就是负债 |
| 不做「知识库 = 向量库」 | 检索只是入口；没有 Claim 关系与时效标注的语料，召回得越多越像在猜 |
| 不做「AI 直接改仓库」 | 工程空间必须先理解、再评审、后执行；跳级写文件等于把证据链连根拔掉 |

## 8. 成功的判据

产品做对了，应该能被下面几条检验：

- 一次多模型研究里，能指出**至少一个只有某个 AI 提到的角度**，并给出原话与轮次。
- 能指出**一条被另一个 AI 用反例打掉的说法**，而不是把它悄悄删掉。
- 每条结论要么挂着证据，要么被显式标成「断言」；两者不能混在一起。
- 多模型给出同一条答案时，系统不把「一致」当成「正确」的证据。
- 用户追问「凭什么」，能得到一条可走通的路径：结论 → 判断 → 证据 → 出处。
- 关掉本地 Runtime，问答、辩论与结论仍然完整可用。
- 同一条争议换一个模型裁判，结论方向不应大幅翻转；翻转了要能解释为什么。
- **知识学习**：第二次问同一主题，能带出上次的结论，并明确指出「哪些已经过时、依据变了」。
- **工程空间**：一次改动说「已修复」，必须能追到具体执行断言与 `路径:行号`，而不只是一段说明。
