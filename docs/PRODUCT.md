# 产品定位

> 一句话：用户提出一个真实问题，ThinkFusion 判断它属于哪一类，组织多个 AI 与信息源分头思考、交叉质疑，最后综合出一个更好的答案——**只有在确实需要动本地文件时**，才生成一份可审批的执行计划。

这份文档定义产品是什么、不是什么、按什么原则做取舍。技术怎么落地见 [ARCHITECTURE.md](ARCHITECTURE.md)，先做什么见 [ROADMAP.md](ROADMAP.md)。

---

## 1. 为什么需要重新定位

现有实现把每一个用户任务都塞进同一条流水线：

```
用户输入
  → 固定提示词「你是本地任务规划引擎，输出 desktop-agent/v1 执行计划」
  → 解析 JSON
  → 人工审批
  → 本地 Runtime 执行
  → 执行报告回传，下一轮
```

后果不是"提示词写得不够好"，而是三条结构性错位：

| 现象 | 真实原因 |
| --- | --- |
| 问「Redis 连接数为什么高」，模型被迫编造读文件、写文件步骤 | 流水线里没有"回答问题"这个出口，只有"输出计划" |
| 网页版 AI 失去了正常对话能力 | 每一轮都被要求交 JSON，模型在解决我们的格式问题，而不是用户的问题 |
| 研究类任务无处落脚 | 系统只有"执行"这一种完成形态，没有"给出结论" |

根因是把**本地 Agent** 当成了产品本体。它其实只是一个可选子系统。

**ThinkFusion AI 的核心是编排与综合，不是执行。**

---

## 2. 产品定义

给定一个真实需求，系统要做的是四件事，顺序不能颠倒：

1. **理解意图** —— 这是要一个答案，还是要一次执行？两者需要的流程完全不同。
2. **组织思考** —— 把问题拆给多个 AI 与信息源，让它们从不同角度回答。
3. **交叉验证** —— 比较观点，找出分歧、缺失和没有依据的断言，必要时追问。
4. **综合输出** —— 给出结论、依据、分歧点与不确定性；需要动手时才落成计划。

### 一句话反定义

ThinkFusion AI **不是**：

> 网页内容读取器 + 固定提示词 + JSON 文件操作执行器。

它是：

> AI Orchestrator + Multi-AI Collaboration + Knowledge Synthesis + **Optional** Local Agent Runtime

`Optional` 是这句话里最重要的词。

---

## 3. 五类任务

产品必须能接住下面五类需求，而不是把后四类伪装成第五类：

| 用户说 | 系统应该做什么 | 需要本地执行 |
| --- | --- | --- |
| 帮我分析 Redis 连接数过高的原因 | 向 AI 提问，收集不同分析视角，交叉验证 | 否 |
| 比较 Envoy 和 Redis Enterprise Proxy | 分别研究，比较连接复用、性能、故障恢复、成本 | 否 |
| 帮我整理某个网页 | 提取内容，理解重点，生成总结 | 否 |
| 研究 Java 堆外内存持续增长的问题 | 收集资料、分析证据、提出排查路径，必要时追问 | 否 |
| 帮我修改工作区里的某个文件 | 理解目标 → 制定方案 → 确认权限 → 执行 | 是 |

**判据只有一条：前四类的交付物是「答案」，第五类的交付物是「计划」。**

混淆这两种交付物，就会出现"为了回答一个问题，先让模型编一份文件操作计划"的荒谬。

## 4. 产品原则

### 4.1 思考与执行分离

AI 协作引擎负责**思考**，Runtime 负责**执行**。两者不能混为一谈：

- 思考层可以无限追问、比较、推翻自己，产物是文本与结构化观点。
- 执行层只认已批准的计划，产物是文件系统上的真实变化。
- 执行层的权限模型、工具白名单、路径校验、sha256 复验**不为思考层放宽**。

一条推论：思考层永远不能直接碰文件。它只能提出"我想要这个结果"，由执行层判断能不能做。

### 4.2 不替用户改问题

用户问什么，就问 AI 什么。

- 不把用户的自然语言需求翻译成"任务规格说明"再发出去。
- 不因为系统内部有协议，就要求用户或模型迁就协议。
- 需要补充信息时，把问题交回给用户，而不是自行假设。

### 4.3 结构化是内部产物，不是对模型的要求

这是最容易复发的一条。

我们确实需要结构化的观点、证据、分歧——但那应该是**应用侧**的数据结构，由系统从自然语言里抽取、归纳、标注，**不是要求模型输出 JSON**。

一旦要求模型每轮交 JSON，就又回到了老路：模型在解格式题，不在解用户的问题。抽取失败时降级为纯文本，流程继续走，不阻塞。

### 4.4 分歧要保留

综合不是取平均。有价值的输出必须能回答：

- 哪几个 AI 说法不一致，分歧点具体在哪一句？
- 哪些结论有证据，哪些只是断言？
- 有哪些角度**没人提到**（缺失比冲突更危险）？
- 在什么条件下，少数派的判断才是对的？

只做"把 N 个回答交给另一个 AI 总结一次"不算综合，那是压缩。

### 4.5 评价标准是「发现了什么」，不是「是否一致」

「综合」这个词其实盖着三层能力，混在一起就会退化成总结：

| 层 | 回答的问题 | 产物 |
| --- | --- | --- |
| Answer Synthesis | 多个答案怎么合并成一段话 | 一段更通顺的答案 |
| Opinion Synthesis | 这些说法谁支持谁、谁反驳谁、谁在限定条件 | 观点关系图、争议清单 |
| Evidence-based Reasoning | 哪条说法有证据、边界在哪、还缺什么 | 证据链、可信度、适用条件 |

只有第三层产出单个 AI 给不出的东西。所以判据不是「几个模型达成一致」，而是**是否发现了单个 AI 没有发现的观点、证据、反例和边界条件**。

一致可以是结论的一部分，但不能当评价标准：多个模型可能读的是同一篇博客，也可能错在同一处。

### 4.6 默认不执行

任何会改变本地状态的步骤，默认不发生。

- 需要权限的操作必须经过授权，授权有范围、有期限。
- 计划要人点确认，不是模型说完成就完成。
- 执行报告必须来自真实执行，模型不得伪造结果。

### 4.7 每一步可回溯

用户要能回答："这个结论是从哪来的？"

- 每条观点挂在具体的来源与轮次上。
- 每次追问、每次改判都留痕。
- 历史任务可回看当时批了什么、依据是什么。

## 5. 用户看到的界面

保留左右分栏，但改变职责。

```
┌──────────────────────────────┬─────────────────────────────────────┐
│ 任务与协作                    │ 对话与研究结果                       │
│                              │                                     │
│ Redis Cluster 连接数优化研究   │ 你：分析连接数过高的原因和解决方案     │
│                              │                                     │
│ 研究中 · 已收集 3 个观点       │ DeepSeek                            │
│                              │ 首先要区分客户端连接数、代理连接数     │
│ AI 协作进度                   │ 和 Redis 后端连接数……                │
│  DeepSeek      已完成         │                                     │
│  ChatGPT       待分析         │ ThinkFusion 综合分析                 │
│  综合分析      等待中          │ 正在比较不同方案的连接复用与故障恢复   │
│                              │                                     │
│ ┌──────────────────────────┐ │ ┌─────────────────────────────────┐ │
│ │ 直接描述你想研究或完成的事… │ │ │ 继续追问，或补充研究条件…        │ │
│ └──────────────────────────┘ │ └─────────────────────────────────┘ │
│ 权限：只读 · 工作区修改 · 完全 │                                     │
└──────────────────────────────┴─────────────────────────────────────┘
```

三条界面判断：

1. **右侧是正常的对话工作区，不是 JSON 规划窗口。** 用户在这里读回答、追问、看综合结果。
2. **左侧是协作状态，不是任务列表。** 用户关心的是"收集到几个观点、还有谁没回、综合到哪一步"。
3. **网页视图退为"查看原始页面"的入口**，和现在的右缘来源栏同一个定位——它是取证用的，不是主界面。

## 6. 不做什么

明确划掉，避免后续反复讨论：

| 不做 | 原因 |
| --- | --- |
| 通用浏览器 | 内嵌网页只是 AI 接入手段，不是产品 |
| "多开几个网页然后总结"的套壳 | 那是压缩，不是综合；没有交叉质疑就没有增量 |
| 无授权的自动执行 | 权限模型是产品底线，不是可配置项 |
| 把某个网页的 DOM 结构当系统接口 | 站点改版是常态，接口必须抽象在 Adapter 后面 |
| 为了统一而让所有通道都吐同一种 JSON | 这是当前所有问题的源头，不能换个名字重来 |

## 7. 成功的判据

产品做对了，应该能用下面几条检验：

- 问一个纯知识问题，系统不会要求用户提供工作区路径。
- 问一个研究问题，输出里有**至少一处明确的分歧或不确定性**，而不是四平八稳的综述。
- 一次多通道研究的输出里，能指出「这个角度只有其中一个 AI 提到」或「这条结论被另一个 AI 用反例打掉了」——**这是综合有没有增量的唯一硬证据**。
- 每条结论都能追到具体原话；纯断言（没有依据的那部分）必须被单独标出来，而不是混在结论里。
- 追问一次，系统能带着上下文继续，而不是从头再来。
- 只有说"帮我改这个文件"时，才会出现计划与审批。
- 关掉本地 Runtime，问答与研究功能仍然完整可用。

最后一条是最硬的检验：**Runtime 拔掉不影响核心产品，才说明它真的被解耦了。**

## 8. V2.1 增量：两个顶层入口（2026-11-07）

本节是 V2.1 的增量说明，**不替换上面 1–7 节**：五类任务的判据（前四类交付「答案」、第五类交付「计划」）仍然成立。

产品增加两个顶层入口：

- **知识学习空间 Knowledge Workspace**：不要求选择工程目录、不要求权限预设。上面第 3 节的五类任务里，前四类住在这里。
- **工程工作空间 Engineering Workspace**：需要绑定一个项目目录，内部分两种任务：
  - Engineering Analysis：只读理解工程。系统必须真实读取文件，并给出带 `路径:行号` 的证据；读不到就停下来问，不让模型凭常识猜。
  - Engineering Execution：才进入「计划 → 审批 → 执行 → 验证」链路。

三条沿用到底的原则：

1. **第一手回答不因空间而改变**：用户问题原样发给所有已开启的网页通道。工程证据只在回答之后的汇总阶段作为材料出现。
2. **识别不等于授权**：判成 Execution 只是生成计划，写文件仍要人点确认。
3. **思考与执行分离**：Runtime 只认审批过的计划；模型输出永远不是 Shell 指令。

辩论仍是两个空间都能按需调用的全局能力，但新增了「自动 / 开启 / 关闭」三档开关：用户明确关闭时不强制启动。
