# 开发路线

定位见 [PRODUCT.md](PRODUCT.md)，架构见 [ARCHITECTURE.md](ARCHITECTURE.md)。

排序原则：**先把"能正常对话"做出来，再谈"多个 AI"。** 一个通道都聊不自然的时候，接十个通道只是把噪音放大十倍。

每个阶段给出的是**完成判据**，不是功能清单。判据不满足就不进入下一阶段。

---

## 现状盘点

先分清哪些是已经有了的、哪些是缺的——避免把已有能力当成待办，也避免把缺失说成已完成。

| 能力 | 状态 | 依据 |
| --- | --- | --- |
| 网页版 AI 的自动发问与回答提取 | ✅ 可用 | `deepseek-adapter.ts`；`check:sources` 等 59 项实机检查 |
| 回答归属（判断"这轮回答是哪段"） | ✅ 可用 | 消息数增量 + 连续 3 次稳定 + 未闭合 JSON 拒绝 |
| 渲染后 markdown 的协议解析 | ✅ 可用 | `extractJsonBlocks` 三级策略 + `repairJson` |
| 本地执行 Runtime + 权限 + sha256 复验 | ✅ 可用 | `src/agent/*`，`UtilityProcess` 隔离 |
| 多网页嵌入与切换 | ✅ 可用 | `shared/sources.ts` + 右缘来源栏 |
| **自然语言对话（不强制 JSON）** | ❌ 缺失 | `buildInitialPrompt` 无条件注入计划协议 |
| **意图识别 / 任务分类** | ❌ 缺失 | 无路由层，所有输入都当计划任务 |
| **多通道收集** | ❌ 缺失 | 只有 DeepSeek 一个通道，全局单队列 |
| **观点比较 / 分歧标注 / 综合** | ❌ 缺失 | 无综合层，只有"计划-执行"闭环 |
| **知识索引 / 历史复用** | ❌ 缺失 | 有事件日志，无检索索引 |

一句话：**执行子系统是成熟的，编排与综合是空的。**

### 第一轮落地情况（2026-10-31）

上面的盘点写于重构之前。第一轮改动已经把这几个缺口补上了，逐条对账：

| 项 | 状态 | 证据 |
| --- | --- | --- |
| 自然语言对话（不强制 JSON） | ✅ 已落地 | `shared/prompts.ts`；`check:conversation` 断言回答里没有协议块 |
| 意图识别 / 任务分类 | ✅ 已落地 | `shared/intent.ts` + 9 项 `test:intent` |
| 通道抽象 | ✅ 已落地 | `main/channels/`（types / web-page / registry / chatgpt 画像） |
| 多通道收集 | ✅ 代码就绪，待登录验证 | 注册表 + 每通道队列 + 全局并发上限；7 项 `test:runner` 覆盖单通道失败、忙、全失败 |
| 观点比较 / 分歧 / 缺口 | ✅ 规则版落地 | `shared/synthesizer.ts` + 8 项 `test:synthesis` |
| 执行子系统收敛为按需 | ✅ 已落地（未拆类） | 只有 `intent.kind === 'workspace'` 才进 `orchestrator.submit`；`test:runner` 断言工作区意图不碰任何通道 |
| 知识索引 / 历史复用 | ⏳ 未做 | P5 |

两处与本文档原计划的偏差，记录在案：

1. **M6 没有把 `AgentOrchestrator` 拆成独立的 `Executor` 类。** 达成的是可观察行为（只有工作区意图能进执行链路），而不是类结构。理由：拆分本身不改变行为，而当前编排类的状态机与守卫是踩过坑的，重排的收益小于风险。等 P4 真正需要多入口时再拆。
2. **多通道的实机验证被登录状态挡住。** 两个内嵌页面在验证时都处于未登录（DeepSeek 在 `/sign_in`，ChatGPT 停在 Google 登录），所以 `check:conversation` 的成功路径还没有跑过一次真实问答。编排逻辑已由 `test:runner` 用脚本化通道覆盖，但"两个真实网页同时回答并综合"这件事仍待一次登录后的验证。

### 第二轮：多通道实机跑通（2026-10-31）

上一轮留的"待登录验证"已经补上：两个真实页面同时回答、综合、出卡片，`check:conversation` 22 项全绿。这一轮修掉的都是**只有在真机上才会暴露**的问题：

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 对话卡在「收集中」三分钟 | chatgpt.com 现版 DOM 已经没有 `data-message-author-role`、`article`、`.markdown`（实测全为 0），只能走"文本增量"这条路；而那条路的门槛是旧协议标记 `desktop-agent/v1`，重建后提示词里不再出现，于是分支永远不可达——页面上的回答早已写完，程序还在等 | `selectAnswerText` 去掉协议标记依赖，改用「长度 ≥ 24 字 + 三轮稳定」判定；实机验证后 ChatGPT 正常返回 |
| 回答里混进我们自己的提示词 | 页面把 `你说：…ChatGPT 说：…` 拍平成一行，提示词被重排后精确匹配失效，echo 清理抓不到 | `cutSpeakerLabels`：按页面自己的说话人标签切到最后一个助手标签之后 |
| 回答里混进站点文案 | 升级横幅、免责声明在正文容器内，`innerText` 把它们粘在答案末尾 | `stripChrome`：整行按名单删，行内短语按短语删；代码缩进不动 |
| 引用角标变成 `- 2 - 5 - 8` 竖排 | 角标是内联 chip，`innerText` 每个占一行 | `normalizeAnswerText`：把「短横线 + 数字」成对删除，编号列表不受影响 |
| 状态条只显示已回答的通道 | `conversation.channels` 只在收到回答后才写入，正在等的通道完全不显示——看起来就是卡死 | 提问前就写入目标通道，先显示「提问中」 |
| 顶栏写着「0/2 通道就绪 · 页面尚未加载」 | 通道状态只在空闲时刷新，运行中一直是启动那一刻的旧值 | 运行中每 4 秒刷新一次 |
| 面板里混进另一个对话的消息 | `message.added` / `channel.phase` 事件没有按对话过滤 | 事件按 `conversationId` 过滤，只落到当前对话 |
| 检查脚本污染对话列表 | `check:conversation` 每跑一次就真建两条对话和一个任务 | 检查结束前自己删掉，并断言"没留下测试对话" |

界面这一轮也按"对比"重排：每个通道的回答是一张独立卡片（顶部色条区分通道、右上角标字数），`auto-fit` 网格在窄栏里自动降为单列。堆在一起的两段散文只能顺序读，并排的两张卡片才能对照。

### 第三轮：综合别说假话，界面要跟着窗口长（2026-10-31）

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 两个通道明明都在讲「连接池 / 数据库上限 / 80%」，综合却说"几乎没有重合" | 整句 bigram 的 Jaccard 对中文长句天然偏低（实测最高一对只有 0.143，阈值 0.34），两个改写句共享 8 个 bigram 但分母有 20 多 | 不再只靠句子相似度：**同一个数字**算共识（可打开两边核对），**共同主题词**进新的 `overlap` 字段（只证明"可比"），句子相似度仍是共识的主判据 |
| 只有共识、没有分歧/缺口时，原来的断言判它不合格 | 旧规则要求"综合必须含分歧或缺口"，但"两边都写 80%"本身就是合格结论 | 规则改为三选一：有分歧、有缺口、明确降级、或共识被标注为"未经验证" |
| `overlap` 吐出 `置过大`、`池配置`、`连接数持续` 这类碎片 | 把所有 2–5 字子串都当候选，`置过大` 是「池配置」「设置」两个词的共同尾巴 | 短语必须从词边界开始（标点后，或虚词/动词后），且动词不能做开头；边界表刻意不含 `配`、`设` |
| 窗口拉宽后正文列纹丝不动：可用区 954px，正文只有 660px，两张对比卡各 324px | `.inner` 写死 `max-width: 660px`，`.conversation` 又叠了一个 720px 的上限，两个上限互相打架 | `.inner` 改 `clamp(660px, 72vw, 1040px)`，`.conversation` 不再设宽度；卡片 324 → 453 |
| 短回答和长回答并排时，一张 115px 一张 428px，下面一大块空洞 | `.channel-grid` 用了 `align-items: start` | 改成 `stretch`，卡片等高、文字从同一基线开始，留白被收进边框里 |
| 右边偶尔整块变白，页面像是丢了 | 拖拽分栏时页面被临时移出窗口（`draggingPage`）；如果 `pointerup` 没送到，状态永远停在"拖动中"，页面就一直停在窗口外，而 DOM 仍然留着那块宽度 | 拖拽期间监听 `pointermove`：一旦 `buttons === 0` 说明手势早就结束，立即收尾 |
| `check:drag` 有两条一直红 | 脚本按 `split - GUTTER` 算页面宽度，但 `computePageBounds` 早就多减了一个来源栏（46px），差值正好都是 46 | 脚本改用和 `computePageBounds` 同一个公式，并把 46 写成具名常量 |

宽度改完按四档量过：窗口 2060（正文 1040 封顶、卡 514）、分栏 487（正文 918、卡 453）、900（正文 597、卡 293）、969（正文 513、卡 251），各档都等高、无横向溢出、无裁切。

### 第四轮：别把测试写进别人的账号（2026-10-31）

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 对话列表里反复出现「你是本地 ThinkFusion 的任务规划引擎……输出执行计划」 | `check:conversation` 为了验证"改文件仍走任务链路"，真的提交了一次工作区任务，于是 `buildInitialPrompt` 把规划提示词发到了网页。应用侧对话删得掉，网页自己的历史删不掉，每跑一次就多一条 | 新增 `conversation:classify`：只返回 `{intent, reason}`，不产生任何副作用。检查脚本改用它——路由判定照样验，交棒本身由 `check-runner` 用假注册表覆盖，一个字节都不离开本机 |
| 顶栏长期停在「0/2 通道就绪 · 页面尚未加载」 | 两个原因叠加：启动时只 `ensureSource` 当前那一个页面，另一个通道根本不存在；而状态只在挂载时读一次，之后空闲时不再刷新 | 启动时加载全部来源（当前页先加载，其余并行跟上）；状态改为常驻轮询，空闲 6s、运行中 4s |
| 综合卡上又出现 `每个` | 限定词能通过词边界规则 | 限定词并入停用词表 |

`check:conversation` 现在 26 项，其中两项专门盯顶栏：就绪数量必须与实际可用通道一致，且不许挂着过期的「页面尚未加载」。

### 第五轮：一个通道其实是零个通道（2026-10-31）

用户的原话是「怎么全卡住了」。查下去发现卡住只是症状，底下是两件互不相干的事：一个通道根本用不了，另一个通道其实答了但被判成失败。

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| ChatGPT 永远显示「未找到输入框，页面结构可能已变化」，多通道实际退化成单通道 | 未激活的页面是 `setVisible(false)` 的，而**隐藏的 `WebContentsView` 视口是 0×0**。视口为 0 时页面上每个元素的 `getBoundingClientRect().width` 都是 0，探针的可见性判断全部失败——页面是好的，是量它的人没有尺子。更糟的是这个状态自愈不了：用户没点过那个来源，它就永远不可用 | 启动时先把所有视图都建好，在窗口 `show()` 之前给每个视图一次真实尺寸（`primeViewports`）。视口一旦拿到，隐藏后仍然保留，所以后台通道可以被提问，而窗口显示出来时不会有第二个站点闪一下 |
| 提问后 80 秒界面一动不动，最后报「所有通道都没有给出回答」 | 等待上限是 90 秒，而这个问题的回答带联网搜索（翻了 13 个网页），写完远不止 90 秒。超时后两个通道都被判失败，可 DeepSeek 明明答了 | 上限提到 180 秒；等待期间芯片上显示已等待秒数（`提问中 1:05`），失败文案改成逐个通道列出原因，而不是一句"请检查是否已登录" |
| 超时文案分不清「还在写」和「什么都没找到」 | 两个分支共用一个说法 | 分开：还在变化 → 说明页面仍在生成、稍后会出现在右侧；没找到 → 说明页面当时几条消息、选择器命中什么、是否跳转过 |
| 0×0 视口被报成"页面结构可能已变化" | 探针不返回视口尺寸，只能猜 | 探针新增 `viewportWidth/Height`；为 0 时明确说"页面还没有分到尺寸" |
| `check:conversation` 每跑一次就往用户自己的 DeepSeek / ChatGPT 历史里写一条测试问题 | 检查为了验证"提问→回答→综合"真的发了一次问题，而网页侧的历史应用删不掉 | 默认不再发送任何问题：只验就绪数、路由判定、界面外壳、以及"这次检查什么都没创建"。完整链路要显式 `CHECK_LIVE_ASK=1` 才跑，并且脚本开头写明它会写进网页历史 |
| `check:split` 的"页面宽度"断言其实一直没执行 | 窗口不在前台时页面被判为 `hidden`，脚本按这个信号跳过断言；而 `visibilityState` 并不反映"合成器是否在跑"——三次缩放期间它一直说 `visible`，宽度却停在 644 | 改用 `document.hasFocus()` 判断：窗口真在前台才断言页面宽度，否则打一行 note，以视图 bounds 为准 |

关于 0×0 视口，走过两个弯路，记在这里免得再走：

1. 先把停靠页放到窗口外但保持 `visible`——视口仍然是 0×0。Chromium 不给窗口外的视图布局。
2. 再让所有页面占同一个屏内矩形、用层级盖住非当前页——视口有了，但**原生缩放从此只生效一次**，之后再怎么 `setBounds` 页面都停在旧宽度。

最终方案是"每个视图各自显示一次、然后回到只有一个可见"：既拿到视口，又保住了缩放。代价是启动顺序必须变成"建视图 → 给尺寸 → `show()` → 才加载网页"，否则会闪。

验证口径：单元 86 项、`check:sources` 26 项、`check:layout` 24 项、`check:drag` 16 项、`check:conversation` 12 项全绿；两个内嵌页面在"一次都没点过来源栏"的情况下都是 599×928。

### 第六轮：页面自己的那条栏（2026-11-02）

用户要两件事：网页上方要有一条状态栏，能放大、能吸附回来；还要一个「更新样式」，网页改版后能自己提取、修好。

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 内嵌页面上方没有任何可点的东西，只有一片空白 | 页面是原生视图，**画在文档之上**。任何 DOM 都会被它盖住，所以"在页面上方加一条栏"不是加个 `div` 就完事 | `layout.ts` 新增 `PAGE_HEADER_HEIGHT = 36`：主进程把视图整体下移 36px，渲染层在这条带子里画状态栏。两个数字来自同一个常量，`check:pane` 直接断言 `view.y === 36` 且栏宽等于视图宽 |
| 只有一个页面的宽度可调，"单独用某一个页面"做不到 | 之前只有分栏拖拽，最大也就把窗口切一半 | 「放大」把页面视图**重新挂到另一个窗口**（`removeChildView` → `addChildView`）。是搬不是复制：同一个 `webContents`、同一个登录、同一段正在写的回答。实测视口从 599×892 变成 1248×814 |
| 分离之后回不来 | 没有回头路 | 「吸附回来」把视图挂回主窗口；独立窗口的关闭按钮、Cmd+W、窗口里那颗按钮都走同一条 `closed` 事件，所以只有一条路径要维护。分离期间主窗口那一格换成说明卡，否则空着和"页面崩了"长得一样 |
| 分离后页面不会跟着变大 | 经验上 `WebContentsView` 重新挂载后视口可能停在旧尺寸——原生框跟着 `setBounds` 走，里面的页面不动 | 这次实测没问题（视口确实变成 1248×814），但仍然把断言写成"页面自己的 `innerWidth` 变大了"，而不是"窗口变大了"。差别在于后者永远不会失败 |
| 网页改版后只能等作者发新版本 | 选择器是写死的常量 | 新增 `DISCOVER_SCRIPT`：在页面里按"属性优先、类名兜底"重建选择器，再**用真实探针验证**，只有确实修好了某项才写进 `userData/selector-profile.json`。内置选择器永远排在前面（`mergeProfile` 追加不前置），所以修复不会把本来正常的页面改坏 |
| 「更新样式」按下后卡了 20 秒 | 两个原因：冷启动时页面还在加载就跑了三段脚本；`[class*="message"]` 在真实页面上命中上千个节点，而每个节点都读 `innerText` / `getBoundingClientRect`——这两样都会强制同步布局 | 页面 `isLoading()` 时直接返回"还在加载"；批量扫描改用 `checkVisibility()` + `textContent`，只保留最后 400 个候选，且只对胜出的那一组量一次。实测从 >90 秒降到 21ms；另加 8 秒超时，卡住时按钮会报错而不是永远转 |
| 「回答区域仍没找到」这句话在空对话里是误导 | 空对话本来就没有回答可以校准，而输入框和发送键都是好的 | 单独一条文案：输入框和发送键都正常，回答区域要等页面上有一条回答才能校准 |
| 结果文字挤在页面栏里，被截成「…回答区域要等页面上有一条…」 | 栏在页面格子里，格子能被拖到 380px，按钮之后的宽度放不下那句话 | 改成弹窗：一句结论 + 三项角色各自的状态（已重新提取 / 正常 / 未找到）+ 实际写入的选择器 + 页面尺寸。原来只显示一句"已重新提取 2 项"，用户没法核对；现在能看见到底写了什么 |
| 「放大 / 吸附回来」两个四字标签占掉栏的大半 | 中文标签在 380px 的格子里没有余地 | 换成图标：向外四角＝放大，箭头回到竖线＝吸附回来。刻意不用"展开/收起"那一对，因为它们是两件不同的事，不是同一个按钮的两个状态 |

关于"只改一处"这件事：`check-split` 原来断言"页面视图满高"，现在页面视图必然不满高。这条断言没有删掉，改成断言 `view.y === PAGE_HEADER_HEIGHT` 且 `height === 视口高 - 36`——原来的失败点变成了新的守卫点。

验证口径：单元 96 项（新增 `check-selectors` 10 项）、`check:pane` 32 项、`check:sources` 26 项、`check:layout` 26 项、`check:drag` 16 项、`check:conversation` 12 项全绿。

### 第七轮：把网页那一格折起来（2026-11-02）

用户先指出「吸附回去的图标没有更换」，接着要「一个收缩框，可以把网页那部分收缩起来」。

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 按钮写着「吸附回来」，画的还是"向外四角" | 两个原因叠在一起：主窗口的图标换了，**独立窗口工具栏里那颗还是文字按钮**；而 `check:pane` 只读第一条 `path`，而"箭头回到竖线"是两个 path，所以只读一条时断言"看起来对" | path 数据提到 `src/shared/icons.ts`，主窗口的 React 组件和主进程拼的 `data:` 文档都从那里取；检查脚本把多条 path `join` 起来，并新增"独立窗口的按钮也是图标""两个窗口的图标一致""按钮有可读的名字" |
| 吸附回来后页面挤在左边，右边一大片空白 | 视图换了父节点，原生框跟着 `setBounds` 走，里面的 document 停在独立窗口的 1248px 视口——它不会自愈，因为之后每次 `setBounds` 推的都是同样的数字 | 挂回后做一次"差 1px 再差回来"的强制 resize（32ms 后回到目标值）。实测视口 1248 → 599 |
| 网页那一格收不起来 | 收起按钮长在页面栏里，而页面栏就在那一格里：折掉整格，按钮跟着没了，没有回去的入口 | 折叠后留下 `PAGE_STUB_WIDTH = 30` 的窄缝：一颗朝左的尖角按钮 + 竖排的来源名 + 状态点。它既是回去的入口，也是"页面还活着"的唯一提示 |
| 折叠时视图怎么处理 | 直觉是"把宽度设成 0" | 0 会让应用列钻到右侧轨道下面；更要紧的是**被塞进 0 宽矩形的视图会失去视口**，页面里每个元素量出 0，探针就会说"找不到输入框"。所以折叠走"切换来源"那条现成分支：停到窗口外、保留盒子、`setVisible(false)`。`check:pane` 断言折叠后视图宽度和页面 `innerWidth` 都与折叠前一致 |
| `split` 一个数字表达不了"折起来了" | 折叠时右侧仍要留轨道和窄缝，所以那个数很小但不是 0；只看"是不是 0"的渲染层会在没有页面的地方画一条页面栏 | `LayoutInfo` 与 `PageState` 各加一个 `collapsed`。`split` 说留多宽，`collapsed` 说那里有没有页面 |

顺带修了一处检查脚本的口径：`check:conversation` 原来断言"每个已配置来源都是可用通道"，而 DeepSeek 登录过期时它必然失败——这条断言其实想守的是"页面结构没坏"，不是"谁的会话还活着"。改成只对**结构性不可用**报警，登录态导致的不可用单独打印原因。

验证口径：单元 120 项、`check:pane` 59 项、`check:sources` 26 项、`check:layout` 26 项、`check:drag` 16 项、`check:conversation` 12 项、`check:new-task` 10 项全绿。

### 第八轮：账号行、可改的网址，和每个来源自己的开关（2026-11-02）

用户先要「修改成这种账号系统，网页可以设置」——「规划的 deepseek, chatgpt, kimi, workbuddy 都需要可以选和更新网址」；随后补了一句把规则说全：「每个网页源都可以设置是否开启。开启后才可以用，并且通道要保持一致。」

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 侧栏底部写着「本地工作区」，没有账号，也没有设置入口 | 没有身份概念，设置无处可放 | 换成账号行：首字母头像 + 系统用户名 + 「页面诊断」「设置」两颗图标按钮。身份来自 `os.userInfo()` 与 `os.hostname()`——**这不是登录**，没有后端也没有密码，界面照实写「这个应用只跑在这台机器上」。**第九轮改掉了取名字的来源**，见下 |
| 网址写死在常量里，站点一搬家就只能等新版本 | 来源列表是一份常量 | `BUILTIN_SOURCES`（出厂）+ `userData/sources.json`（用户增量）→ `resolveSources()` 纯函数合并。**只存 delta**：存解析后的整份列表，等于把今天的内置项钉死，将来修 URL、加来源对已安装的人永远不可见 |
| 改网址时若重建视图，用户会被悄悄退出登录 | partition 属于**来源 id**，不属于 URL；换视图 = 换 session | 改址走 `loadURL`，还是同一个 `WebContentsView`。登录、滚动位置、正在写的回答都留着 |
| 改了网址，页面却拒绝导航到新地址 | 允许列表是构造时定死的 `Set` | `hostsFor()` 保留声明过的 hosts 并**追加**新 host：替换会破坏 OAuth 跳转，不追加会拒绝刚填的地址。`DeepSeekAdapter` 的 `hosts` 改成 `() => Set`，每次 `isAllowed` 现算 |
| 开关拨了，通道数不变 | 注册表在启动时建好一次 | `ChannelRegistry.replaceAll()`——是替换内容而不是换对象，因为 `ConversationRunner` 持有的是同一个实例，换对象会让持有者永远读旧列表 |
| 「规划通道」的开关是灰的，点不动 | 把「Agent 得有地方问」写成了「这一行不许关」 | 改成「**至少留一个**」：`planningSource()` 优先选开着的规划来源，其次任一开着的来源；关掉最后一个会被拒绝，理由落在表单里。「规划通道」标签跟着 `planningId` 走，而不是跟着出厂标记——否则关掉 DeepSeek 之后标签还挂在它身上，指着一个已经不用的页面 |
| 刚打开的来源报「未找到输入框，页面结构可能已变化」 | 运行时新建的视图从没上过屏，视口是 0×0；而 `layout()` 紧接着就把它停到窗口外，它自己好不了 | `primeViewport()`：先按页面尺寸显示一帧，再交给 `layout()`。`createSourceView` 一律把视图插到栈**最底层**——z 序不影响布局，所以它能拿到视口，又不会盖住用户正在看的那一页 |
| 被拒绝的理由出现在应用底部的错误条里 | IPC 把异常包成 `Error invoking remote method '…': Error: …` | `ipcErrorText()` 剥掉外壳，句子放在被拒的那张表单旁边：改哪个地址出错，就在哪个地址下面说 |
| 网址显示成 `/https://chat.deepseek.com` | 想用 `direction: rtl` 让长网址从右边截断 | 去掉 `direction`。URL 的斜杠顺序会被双向算法打乱，看起来像坏地址 |
| 「设置」图标在 13px 读作太阳 | 「轮毂 + 八条放射线」和亮度图标同形 | 圆环 + 轮毂 + 8 齿：齿在圆环外面，任何尺寸下都读作机械件 |

「开启后才可以用」是三层一起成立的，缺一层就会漏：来源栏只列开着的（点不到）、`activateSource` 对没开的来源直接拒绝、`rebuildChannels` 只把开着的变成通道。所以「通道和来源是同一份清单」这条断言在 `check:settings` 里写成两半：开 Kimi → `chatgpt,deepseek,kimi`，关 Kimi → `chatgpt,deepseek`。

顺带修的是检查脚本自己的两处脆弱：`check:settings` 现在开跑前先把状态归位（而且**先开后关**，否则上一轮死在「只剩一个来源」时，这一轮第一步就会撞上自己定的规则）；面板被误关时会自动重开——它跑在真人的桌面上，点一下遮罩就没了，那不该算作被测功能的失败。

验证口径：单元 138 项（新增 `test:sources-config` 18 项）、`check:settings` 39 项、`check:pane` 59 项、`check:sources` 27 项、`check:layout` 26 项（窗口不在前台时 25，脚本会打 note 说明跳过的是哪一条）、`check:drag` 16 项、`check:conversation` 12 项、`check:new-task` 10 项全绿。

### 第九轮：名字由用户给，不再问系统要（2026-11-03）

用户的要求只有两句：「不允许出现本机用户名等字样，记住这个规则，左下角进行修改」。第一句是底层规则（已写进跨项目记忆，本文档也不复述那个字符串），第二句指的是侧栏底部那一行——它当时显示的是操作系统的登录名。

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 侧栏底部显示的是系统登录名，机器名在 tooltip 里 | `identity()` 读 `os.userInfo().username` 和 `os.hostname()`。这个应用没有账号，却把系统给的名字画到了屏幕上，然后它会进截图、录屏、发给别人的报错 | 名字改成用户自己起的，默认「本机用户」，存在 `userData/profile.json`。**一个 OS 调用都不留**：不读用户名，也不读机器名 |
| 「通用设置」里的「当前用户」是一行死文字 | 那一块只是把 identity 打印出来 | 换成可编辑的输入框 + 「保存」+「恢复默认」。空串就是恢复默认，语义写在按钮上而不是靠占位符暗示 |
| 空名字如果被存下来，侧栏底部会空一行 | 空行读起来是「未登录」，而这个应用没有可登录的地方 | 主进程拒绝空名字，理由（「名字不能是空的」）落在输入框下面，不进应用底部的错误条 |
| 改名字要重启才生效 | 名字存在主进程内存里，渲染层拿的是启动时那一份 | `app:set-name` 返回**存好之后**的 identity（含 trim 与首字母），`App` 直接 `setIdentity`——面板和侧栏不会各说一套 |
| 面板里输入「小柯」，头像还是「本」 | 头像取的是已保存的名字 | 头像跟着草稿走：`initialOf(draftName)`。打什么就看到什么，否则是在提前撒谎 |

名字单独一个文件，不塞进 `sources.json`：改名字和"有哪些页面"没有关系，一个坏掉的 profile 也不该能带倒来源列表。最坏情况是名字退回默认值，一次点击就能改回来。

验证口径：单元 148 项（新增 `test:identity` 10 项）、`check:settings` 50 项（新增改名 9 项：默认名、不是系统用户名、提示是平台、改名后侧栏与头像同步、空名被拒、拒绝后不变、恢复默认）、`check:pane` 59 项、`check:sources` 27 项、`check:layout` 26 项（窗口不在前台时 25）、`check:drag` 16 项、`check:conversation` 12 项、`check:new-task` 10 项全绿。

`check:settings` 里那条「账号行不是系统用户名」是拿 `os.userInfo().username` 现算来比的，**不写字面量**——写了就等于在检查脚本里重新引入它要防的东西。

## P0 · 自然语言任务输入与动态对话

**目标**：用户问一个问题，系统就把这个问题发给 AI，把回答给用户看。中间不出现 JSON、不出现"计划"、不要求工作区路径。

**要做的**

1. 拆 `buildInitialPrompt` → `buildRolePrompt`（稳定角色）+ `buildStagePrompt`（本轮动态内容）。角色提示词只描述"你是协作研究伙伴"，不描述输出格式。
2. 新建 `IntentRouter`，默认分支为 `answer`。
3. 新建 `ConversationRunner`：发问 → 等回答 → 落事件 → 渲染。
4. 右侧界面从网页视图改为对话视图；来源栏保留为"查看原始页面"。

**完成判据**

- 问「Redis 连接数过高的常见原因有哪些」，回答里**没有** `desktop-agent/v1`、没有 `plan`、没有 JSON 代码块。
- 不填工作区、不选权限，也能正常提问。
- 连续追问两轮，第二轮能引用第一轮的内容。
- 现有的执行链路仍然可用（回归 59 项检查全绿）。

**为什么排第一**：这是产品定位的第一句，也是当前所有错位的直接来源。

---

## P1 · 网页通道的健壮性

**目标**：把"能发出去、能读回来"从"大多数时候行"变成"失败时知道为什么"。

**要做的**

1. `AiChannel` 接口落地，`DeepSeekAdapter` 按接口拆分（选择器 / 探测 / 发送 / 归属）。
2. `ChannelStatus` 暴露 `probeVersion`、命中选择器、最近一次失败原因。
3. 归属失败与发送失败分开上报——现在两者都表现为"没拿到回答"。
4. 站点改版后的自愈：选择器全灭时退化为结构探测，并在界面上明确说"正在用结构回退"。

**完成判据**

- 断网、登出、页面改版三种故障，界面上给的是三条不同的提示，而不是同一个"页面异常"。
- 任一通道失败，不影响其他通道的回答收集。
- 新增一个通道只需实现 `AiChannel`，不改 `ConversationRunner`。

---

## P2 · 多来源、多 AI 观点收集

**目标**：同一个问题，同时问 2–3 个 AI，把各自的回答并排呈现。

**要做的**

1. 接入第二个通道（ChatGPT 网页版，复用现有原生视图与分区隔离）。
2. `pageQueue` 全局串行 → 每通道队列 + 全局并发上限（默认 3）。
3. 队列满返回 `ChannelBusy`，编排层决定跳过还是重试；**不排队等待**。
4. 左侧协作进度：每个通道的进行状态、已收集观点数。

**完成判据**

- 两个通道同时提问，回答不串（`attribution` 可回溯到具体通道）。
- 一个通道卡住时，另一个通道的结果照常返回并展示。
- 同时开 3 个通道时内存与响应速度可接受，开第 4 个会明确拒绝而不是拖死。

**前置**：P1。没有通道抽象就接第二个，等于把 892 行复制一遍。

---

## P3 · 观点比较、冲突分析与综合

**目标**：输出里出现"谁跟谁不一致""哪一点没人提到"。

**要做的**

1. `Synthesizer` 规则版：句子切分、实体对齐、否定词与限定词检测。
2. `Synthesis` 五段：`consensus` / `disputed` / `unique` / `gaps` / `recommendation`。
3. 冲突触发追问：对分歧点定向再问一次（`stage: 'challenge'`），而不是重问整个问题。
4. 抽取失败降级为原文并列，流程继续。

**完成判据**

- 任一次多通道研究的输出里，`disputed` 或 `gaps` 至少有一项非空——两项都空，说明综合没起作用。
- 每条 `recommendation` 能追到具体的 `Claim`。
- 结构化失败时界面显示"未能结构化"，但回答仍然可读、可复制。

**这条是产品的价值主张所在。** 只做并排展示（P2）不做综合，产品就退化成"多开几个网页"。

---

## P4 · 本地 Agent Runtime 收敛为按需

**目标**：Runtime 从主流程降级为可选子系统。

**要做的**

1. `AgentOrchestrator` 拆出 `Executor`，输入从"用户任务"变成"已确认的执行意图"。
2. `desktop-agent/v1` 协议后缀只在 `intent.kind === 'workspace'` 时注入。
3. 计划审批、授权 TTL、工具白名单、路径校验、sha256 复验**全部不动**。
4. 旧任务标记 `legacy`，只读可回看，不尝试续跑。

**完成判据**

- 关掉 Runtime（不启动 `UtilityProcess`），问答与研究功能完整可用。
- 说"帮我改这个文件"，才出现计划与审批。
- 说"帮我分析这段代码"，不出现计划。

**注意**：这一阶段是"收敛"，不是"重写"。执行子系统的成熟度是现有资产，别在重构里弄丢。

---

## P5 · 知识索引与历史复用

**目标**：三个月前研究过的结论，能找回来并说清依据。

**要做的**

1. `Synthesis` 落库并建立检索索引（按主题、实体、时间）。
2. 新问题先检索历史结论，作为上下文的一部分，而不是从头再问一遍。
3. 结论过期提醒：来源时间、是否被后续研究推翻。

**完成判据**

- 提出一个做过的问题，系统能引用上次的结论与分歧点。
- 能回答"这个结论是什么时候、基于哪些来源得出的"。

---

## P6 · 多轮自主研究

**目标**：系统自己决定"还差什么"，继续追问，直到够用或预算耗尽。

**要做的**

1. 研究预算：每个任务的最大提问次数、最大轮次、超时。
2. 自主决定下一步：补缺失 → 定向质疑 → 收敛。
3. 停止条件可解释："因为三个通道在这一点上一致，且都有依据"。

**完成判据**

- 一次研究能在无人干预下完成 ≥2 轮追问，且每轮都有明确目的。
- 预算耗尽时给出"还缺什么"，而不是假装完成。

## 明确不排期的事

| 事项 | 原因 |
| --- | --- |
| 接入 API 型模型（OpenAI / Claude API） | 网页通道跑通前，接 API 只是把"通道问题"换成"额度问题"，不解决定位问题 |
| 移动端 | 桌面端定位没稳之前不做 |
| 插件市场 / 第三方扩展 | 接口还没稳定，开放出去就是负债 |
| 多用户 / 协作 | 单机产品先做对 |
