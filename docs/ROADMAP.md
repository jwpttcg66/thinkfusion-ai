# 路线

定位见 [PRODUCT.md](PRODUCT.md)，协作机制见
[architecture/COLLABORATION_ARCHITECTURE.md](architecture/COLLABORATION_ARCHITECTURE.md)，
迁移步骤见 [architecture/MIGRATION_PLAN.md](architecture/MIGRATION_PLAN.md)。

**排序原则：先冻结产品与协作架构（P0），再让协作引擎跑起来（P1），然后依次补齐知识学习（P2）、
工程能力（P3）、证据与质量（P4）、模型与通道（P5）。**

辩论不再单独占据产品主线，它只是 P1 里的一种按需协作行为。

每个阶段给的是**完成判据**，不是功能清单。判据不满足，不进入下一阶段。

## P0 产品与协作架构重构

交付的不是功能，而是**一套不会把任务压成辩论的骨架**。

| 里程碑 | 内容 | 完成判据 |
| --- | --- | --- |
| P0.1 定位冻结 | PRODUCT V3、协作架构 V1、工程空间 V1、迁移计划 | 四份文档评审通过；与现有代码的冲突点逐条列出 |
| P0.2 任务模型 | Goal / TaskSpec / Assignment / Observation / EvidenceRef 类型草案 | 类型能覆盖三类空间，且不需要第二套证据格式 |
| P0.3 能力描述 | Web / Local / Cloud / CLI 的 AgentCapabilities | 网页通道「只收原话」被类型化，而不是口头约定 |
| P0.4 迁移开关 | 新旧路径切换点 | 旧路径仍为默认，任何新路径都能一键关闭 |

判据：**不改生产行为的前提下，四项设计可评审、可回滚；typecheck 与现有测试全绿。**

## P1 多模型协作能力

| 里程碑 | 内容 | 完成判据 |
| --- | --- | --- |
| P1.1 任务图调度 | 由 `collaboration/` 升级出 DAG：依赖、并发、超时、预算 | 计划可展示、可解释；简单问题不被过度拆分 |
| P1.2 协作行为 | 独立、并行、递进、交叉验证、反例、方案评审 | 每种行为有明确的「何时用 / 怎么停」 |
| P1.3 辩论降级 | 只在成对未定论争议时触发 | 不给辩论入口，也不强制每个任务辩论 |
| P1.4 重规划 | 每波 Observation 后决定继续 / 补证据 / 收敛 | 能指出「为什么停」，且停止条件可验证 |
| P1.5 参与者治理 | 第一手覆盖所有已启用可用通道；后续任务按能力分配 | 跳过、失败、降级全部显式可见 |

判据：**同一个问题，旧路径与新调度器的结论质量不降；计划里能看懂谁在做什么、为什么停。**

## P2 知识学习空间

| 里程碑 | 内容 | 完成判据 |
| --- | --- | --- |
| P2.1 知识索引 | 主题、Claim、证据、结论落库，按版本 / 时间索引 | 能查「这个结论是谁在什么时候、依据什么说的」 |
| P2.2 结论复用 | 同主题第二次研究带出旧结论与时效 | 明确标出哪些依据已过时 |
| P2.3 缺口驱动 | 未回答的角度变成下一轮问题 | 研究能收敛，也能诚实说「补不到」 |
| P2.4 知识地图 | 已确认 / 有争议 / 未回答三块 | 每块都能点到证据与出处 |

判据：**第二次研究同一主题不从头开始；旧结论被推翻时保留并可追溯。**

## P3 工程工作空间

| 里程碑 | 内容 | 完成判据 |
| --- | --- | --- |
| P3.1 工程任务状态 | commit、dirty、snapshot S1/S2、diff、测试报告 | 不再依赖「辩论基线」；状态由工程任务持有 |
| P3.2 Agentic Search | 搜索、读取、符号、引用、影响面按需取证 | 结论带 `路径:行号`；读不到就停下问 |
| P3.3 CLI 协作 | Qoder / Claude 作为参与者，worktree 隔离 | 并发任务不共享工作区 |
| P3.4 改动闭环 | 计划 → 审批 → 执行 → 验证 → 评审 | 「已修复 / 已通过」都有执行断言 |
| P3.5 回退 | 快照、diff、回滚 | 失败能退回 S1，而不是靠记忆 |

判据：**一次真实改动走完整条链路，第三方能按证据复验。**

## P4 证据与质量体系

| 里程碑 | 内容 | 完成判据 |
| --- | --- | --- |
| P4.1 统一引用 | 网页 / 代码 / 执行 / 知识 / 工具证据同一套 `EvidenceRef` | 跨空间引用共享哈希与来源 |
| P4.2 验证计划 | 从 Claim 推导验证方式 | 无法验证的结论标「未核验」，不默认成立 |
| P4.3 质量门槛 | 辩论、协作、工程共用可回归的门槛 | 门槛能拦住「无证据 → 判通过」 |
| P4.4 追溯与回放 | 结论 → 判断 → 证据 → 出处 → 执行 | 同输入重复校验得到同一结论 |

判据：**任一交付物都能回答「凭什么」；篡改证据能被发现并定位。**

## 1.0 判据

- 一句话问答与数小时工程任务都能接住，流程不同但不别扭；
- 用户不需要选择协作模式，只说目标；
- 每个交付物都能追到证据与执行；
- 模型可替换、通道可增减，主流程不改；
- 关掉 Runtime，知识学习与通用协作仍完整可用；
- 知识学习能复用旧结论并标时效；
- 工程改动可验证、可回退。

## 明确不排期

| 事项 | 原因 |
| --- | --- |
| 多用户 / 云端协作 | 单机产品的结论可信度先做对 |
| 移动端 | 桌面端定位没稳之前不做 |
| 第三方插件市场 | 内部能力插件化已完成，对外安装接口未稳 |
| 「更多模型」竞赛 | 模型数量不是差异化，协作与证据才是 |
| 通用浏览器 | 内嵌网页只是接入手段 |

## 怎么判断一个阶段真的完成

1. 判据能在**真实模型、真实仓库、真实执行**下跑通，不是脚本桩；
2. 失败路径有明确输出：拒绝、降级、未核验，三者不能混成「成功」；
3. 计划可解释：谁参与、为什么、何时停，都能被用户读懂；
4. 文档与代码对得上：`docs/architecture/` 与 `docs/spec/` 的契约改了就同步改。
